# Choose and review the opening

Choose one `primaryHookType` for each new or substantially rewritten synopsis candidate. Read the [18 catalog entries](opening-hook-types.json) and choose what the viewer can actually do in the opening. Seeing an unexplained split in one row of steamed dumplings suggests `cause_mystery`. Seeing a finished dumpling and wanting to learn the fold suggests `finished_result_first`. Keep an explicit user choice. Candidates can share a type when their stories differ.

## Hand the choice to the next author

- **Synopsis.** Give each alternative a unique `direction` such as `D1` or `D2`, complete `text` in the story language and one catalog ID. Call `scenario_check {synopses:[{direction,text,primaryHookType}, ...]}`. Read the returned findings and fix missing or invalid IDs. Finish the [reality check](synopsis-reality-check.md), then run the review below before presenting each candidate. Deliver the prose, localized label and ID, disposition, evidence and current receipt. A chat-only synopsis creates no files.
- **Scenario.** Keep the candidate's ID in its fenced `scenario-json` object. Select by copying that object into `storyboard/scenario.md`. Check the candidates and the selected file with `scenario_check {path,authoring:true}` or the equivalent [authoring CLI](character-scenarios.md#scenario-file-scenario-v2). Resolve structural findings before handing it off.
- **Storyboard.** The first `story_sequence` inherits the selected scenario's ID. A direct board with no selected file supplies `primaryHookType` on that first write. For a recording, choose an opening the source actually contains. In later sequence writes omit the field to preserve the selection. When the user changes it, update the selected scenario first, then send the new ID, `previousPrimaryHookType` and `expectedSha256` from the preceding board read. The board saves the result in `STORY.primaryHookType`. Cover copy, the cover's `hookType`/`hookForm` and the format-specific `STORY.opening` plan have their own fields. A legacy board can be read unclassified. Enroll it when rewriting its opening.

## Challenge a finished opening

Run `story_opening_review` once the synopsis exists, and again once the board's shots, action, speech and timing exist. A direct board starts at the second stage. Use the same run for all candidates and the selected board, including unattended work and a continued chat.

1. **Prepare.** Send `action:"prepare"`, stage (`synopsis` or `storyboard`), surface, audience and the actual playback condition (`playback:"sound_on"` or `"muted"`). Set `policy.combined:true` at the start of a synopsis-to-board request. Inline, send `synopses` with the checked fields and an `opening` array of timed cues. Each cue has `start`, `end`, `kind` (`visual`, `speech`, `text` or `sound`) and literal `text` drawn from the synopsis opening. Estimate timing and identify the source sentence for each cue. For a board, send its absolute `path` and current `expectedSha256`. Carry the latest inline `receipt` into the next call and into file-backed handoff. Preserve the audience, surface and policy across revisions.
2. **Read blind.** Start three separate, fresh host reviewer contexts for each candidate. Give each the [opening-only task](../../../agents/storyboard-reviewer.md#opening-only-task) and the `packets[].packet` value. Keep the enclosing receipt with the author. Use `[0, 3.0 s)` in playback order. Include a second shot that begins at 2.5 s and exclude a shot beginning at 3.0 s. Credit only the part of a line that fits. Honor silence, muted playback and any packaging the viewer would already have encountered. Keep the type, ending, prior verdicts and target in the author's context. Read the three replies before showing reviewers any author material.
3. **Record.** Send `action:"record"`, `stage`, `runId`, `direction`, `sourceRevision`, `packetDigest` and `policyVersion`. For an inline record include the latest `receipt`. For a file record send `path` and `expectedSha256`. Supply `verdicts` with all three distinct `reviewerId` values and five evidence-backed ratings each. Let the tool compute the median editorial risk in **points**. Its pilot ceiling is 40 points. Equality clears the ceiling. An above-ceiling result is `high`. Qualified exact-version, same-surface abandonment can use a separately agreed ceiling in **percent** and minimum eligible sample size. Identify Instagram Reels explicitly when using its skip-rate metric. Do not infer that rate from Shorts' initial-seconds metric or a six-second view. Check the selected type against the opening and its actual payoff after the blind reads. Set `eligibleForRestore:false` and give the concrete mismatch in `editorialFinding` when the version conflicts with the type, facts or payoff. A low risk score can coexist with an opening that cannot be restored. Correct the problem in the authored story.
4. **Revise.** On `high`, call `action:"reserve_revision"` with `expectedReceiptRevision`, a stable `requestId` and `candidates:[{direction,sourceRevision}, ...]` sorted by direction. Use the reserved round to edit the observed problem in the actual opening. Keep passing alternatives, the selected type, facts and payoff. Recheck affected facts. Prepare the revised artifact and collect three fresh reads. Retrying the same reservation, acquiring missing timing or rereading the same draft uses no additional round.

## Count revisions and recover

The original assessment at each stage costs zero revisions. The run shares **five** rounds across both stages and all candidates. Fixing two high-risk alternatives together costs one round. On a combined request, at most four rounds can go to the synopsis. Two synopsis edits leave three board edits. The board gets its own assessment even when an earlier synopsis-only run used all five.

Stop revising when the result clears the ceiling or the allowance runs out. At `limit_reached`, recover the best valid reviewed opening and report its metric, units, edits used, revision and remaining reason to leave. For a board, merge the leaf changes in `bestDraft.restorePatch` into the current board using its SHA and check each expected value before writing. Preserve unrelated edits. Assess the restored source before presenting its verdict as current. Deliver the best supported result and continue already-authorized work.

A missing reviewer, unusable timing or absent receipt cannot establish a pass. Repair the evidence and retry once on the same revision. If review is still unavailable, record an `incompleteReason` and report `incomplete` along with the reason. Changed material makes an earlier verdict `stale`. On resume, load the board's `opening-review.json` or the selected synopsis receipt. If the previous allowance cannot be recovered, report the unknown budget and show the current draft without starting another five edits. For an explicitly requested new board review, use `prepare` with `startNewRun:true`, a previously unused `runId`, the current board SHA and `expectedReceiptRevision`. The ledger retains the preceding run. Run the standalone HTML exporter after the board or receipt changes.
