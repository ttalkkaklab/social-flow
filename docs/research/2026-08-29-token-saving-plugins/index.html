토큰 절감 플러그인, 진짜 재봤다

쇼츠 하나가 클로드 플러그인 3개를 깔면 사용량이 절반으로 준다고 했다. 셋 다 실제로 존재하는 도구다. 그런데 영상이 말한 절감은 우리 실측에서 재현되지 않았다 — 줄어든 건 토큰이 아니라 코드 줄 수였다.

주장과 반대 ponytail

코드는 확실히 줄인다 — 우리 CLAUDE.md 규칙 위에서도 −85%. 하지만 입력 토큰과 비용은 10~13% 늘어난다.

기준이 문제 graphify

파일을 통째로 읽는 것보다 60~106배 싸다. 그런데 실무 기준인 grep과 비교하면 이점이 사라진다.

토큰은 준다, 돈은 아니다 headroom

입력 토큰 −13%는 진짜다. 하지만 청구 비용은 거의 그대로였다 — 줄인 토큰이 싼 구간에 있었다.

ponytail — 에이전트가 코드를 덜 쓰게 만드는 스킬

과제 3개를 각각 3번씩, 플러그인을 켠 채와 끈 채로 돌렸다(총 18회). 두 조건 모두 다른 플러그인과 MCP를 끄고 저장소 밖에서 실행해, 차이가 ponytail 하나에서만 나오게 했다.

코드 품질은 떨어지지 않았다. 양쪽이 만든 이메일 검증기를 같은 테스트 9개에 돌렸더니 둘 다 9/9 통과했다. ponytail 버전은 5분의 1 길이로 같은 일을 했다. 줄인다는 약속은 지킨다 — 줄이는 대상이 토큰이 아닐 뿐이다.

우리 지침과 겹치는 도구는 아니다. 첫 A/B의 OFF arm은 --setting-sources "" 때문에 사용자 CLAUDE.md까지 빠진 맨바닥이었다. 그래서 두 arm 모두에 "필요한 만큼만 만든다" 절을 넣고 다시 쟀더니, 규칙만으로 58줄이던 결과가 ponytail을 얹자 8줄이 됐다(−85.2%). 같은 테스트 11개에서 5줄짜리가 11/11을 통과했다 — 짧아진다고 무너지지는 않는다. 대신 입력 토큰 +10.1%, 비용 +12.2%는 그대로다.

영상이 바꿔 말한 지점이 여기다. 저장소가 내건 −54%는 코드 줄 수고, 같은 표에서 토큰은 −22%다. 영상은 코드 줄 수 감소를 "사용량 절감"으로 옮겨 말했다. 우리 실측에서 코드는 −60.5%로 저장소 값과 맞았고, 토큰은 −4.9%였다.

graphify — 코드베이스를 지식 그래프로 만들어 질의

우리 저장소를 실제로 인덱싱했다. 87개 파일이 2.3초에 950개 노드로 들어갔고 API 비용은 0원이다. 그다음 답을 이미 아는 질문 3개를 세 갈래로 물었다.

영상이 한 말

"전체 코드 파일을 그래프로 연결해서 토큰을 70% 덜 쓰게 돼요"

저장소가 한 말

질의당 71.5배 적은 토큰 (원본 파일 읽기 대비)

우리가 잰 값

통파일 대비 60~106배 · grep 대비 0.55~2.07배

71.5배는 사실이지만 비교 대상이 이상하다. 파일을 통째로 문맥에 넣는 사람은 없다. 실제로는 grep을 먼저 친다. 그 기준으로 재면 세 질문 중 둘은 grep이 더 쌌다.

정확성 구멍도 하나 잡혔다. handlers.ts:1102의 sns.youtubeInsights() 호출을 graphify는 놓쳤다 — 네임스페이스를 거쳐 부르는 형태라 추출기가 연결을 못 만들었다. grep은 잡았다. "누가 이걸 부르나"를 graphify 답만 믿고 판단하면 호출부를 빠뜨린다.

문서 트리에서는 목차 수준, 타입스크립트에서는 의존성 지도다. 파일을 건너뛰는 연결이 문서 위주인 skills/에서는 1141개 중 26개뿐이었다. 반면 server/src에서는 1609개 중 318개였다. 코드다운 코드베이스에서만 의존성 지도가 실제로 그려진다.

headroom — 모델에 닿기 전에 도구 출력을 압축하는 프록시

두 가지로 쟀다. 실제 페이로드 6종을 라이브러리로 직접 압축했고, 프록시를 띄워 같은 작업을 프록시 경유와 미경유로 3번씩 교대로 돌렸다.

영상이 한 말

"불필요한 줄을 전부 압축하고 제거해서 훨씬 적은 토큰으로 같은 결과"

저장소가 한 말

코딩 15~20% · JSON 60~95% 절감

우리가 잰 값

입력 토큰 −13.0% · 비용 −3.9% (부호 불안정)

MCP 도구가 뱉는 JSON에서 가장 잘 듣는다. 41%는 실제 절감이고 필요한 키도 살아남았다. 반대로 Read로 읽은 파일은 라우터가 아예 손대지 않는다 — 사람이 콕 집어 요청한 내용이라 손실 압축을 피하는 설계로 보인다. 우리 작업은 파일 읽기 비중이 커서 6종 합계는 8%에 그쳤다.

자체 대시보드와 청구서가 어긋난다. headroom savings는 29.5% 절감했다고 표시했지만, 같은 기간 실제 비용은 3.9% 움직였을 뿐이다. 지운 토큰 대부분이 캐시 읽기 구간에 있었기 때문이다 — 그 구간은 원래 요금이 10분의 1이라, 토큰을 지워도 돈이 그만큼 빠지지 않는다. 캐시가 차갑던 단발 실행에서는 오히려 비용이 12.6% 늘기도 했다.

그런데 우리 작업은 어떻게 생겼나

절감률은 워크로드에 달렸다. headroom의 자체 감사 도구로 이 저장소의 클로드 코드 기록 1,677세션을 훑어, 도구가 뱉은 바이트가 어디서 나오는지 셌다.

도구 출력 바이트 비중. MCP 도구는 전부 합쳐도 1.5%다 — headroom이 가장 잘 압축하는 층이 우리에겐 가장 작다.

정작 큰 낭비는 압축이 아니라 중복이었다. Read 바이트의 19.1%(7.7MB·847콜)가 "읽고 나서 편집한 파일"이다 — 이미 바뀐 내용을 문맥에 그대로 들고 있다. 줄 번호 접두사가 5.3%를 더 먹고, 한 번 읽은 파일은 중앙값 72턴(상위 10%는 650턴) 동안 따라다닌다. 플러그인을 깔기 전에 여기부터 손대는 게 값이 크다.

그래서 뭘 켤까

세 도구를 다 켜는 건 답이 아니다. 우리 워크로드 분포와 실측 델타를 겹쳐 보면 각자 자리가 다르다.

켠다 — headroom

입력 −13%·지연 −11%가 실측이고, 겨냥하는 낭비(stale read·줄번호)가 우리에게 실제로 있다. 대신 비용은 거의 안 준다. 정액 구독이면 얻는 건 돈이 아니라 문맥 여유다.

골라 켠다 — ponytail

코드를 쓰는 세션에서는 값어치가 확실하다(우리 규칙 위에서도 −85%). 그런데 우리 작업은 Read의 58%가 문서·텍스트다. 상시로 두면 안 쓰는 세션까지 입력 +10%를 낸다.

CLI 로만 쓴다 — graphify

grep을 못 이기고 호출부를 놓친다. 다만 인덱싱이 2초에 공짜라, server/src를 크게 손볼 때 한 번 돌려 지도로 쓰는 값은 있다. 상시 스킬 등록은 뺀다.

영상이 말한 "같은 구독으로 훨씬 오래 버틴다"에 가장 가까운 건 headroom 하나다. 그마저 −13%지 절반이 아니고, ponytail을 같이 켜면 그 −13%를 +10%가 도로 까먹는다. 셋을 한 번에 설치하라는 게 이 영상의 결론인데, 우리 숫자로는 셋을 한 번에 켜는 게 가장 나쁜 조합이다.

측정 조건

  • 모델 claude haiku 4.5 — ponytail 자체 벤치와 같은 급
  • 표본 과제 3개 × 3반복 × 2조건 = 18회. 프록시는 6회 교대
  • 격리 두 조건 모두 다른 플러그인·MCP를 끄고 저장소 밖에서 실행
  • 지표 Claude Code가 돌려주는 usage·cost 원값, 코드는 빈 줄 뺀 실제 줄 수

한계

  • 표본 3은 방향 신호지 판결이 아니다. 특히 비용 부호는 캐시 상태에 흔들린다
  • 과제가 작다. 큰 과제일수록 ponytail이 유리해지는 기울기가 실제로 보였다
  • 모델을 sonnet·opus로 올리면 출력 단가 비중이 커져 결과가 달라질 수 있다
  • 측정 중 두 실행이 파일을 상위 디렉토리에 써서, 그 줄 수를 되찾아 귀속했다

측정 뒤 정리한 상태

  • ponytail·graphify는 지웠다 — 플러그인·마켓플레이스·CLI 패키지와 ~/.claude/CLAUDE.md에 심겼던 3줄까지. user scope는 이 머신의 모든 클로드 세션(buzz 봇 포함)에 들어가기 때문이다
  • headroom만 남겼다. 설치만 된 상태고 아무 트래픽도 거치지 않는다. 켜려면 headroom wrap claude
  • 맥미니 두 대(taskube·astrabot)와 codex·grok 설정에는 애초에 흔적이 없었다 — 확인만 하고 손대지 않았다
  • 저장소에 남은 파일도 없다 — graphify 인덱싱 산출물은 밖으로 옮겼다
