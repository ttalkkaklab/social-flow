# Field evidence: what practitioners and researchers have learned about agent skills and agent tools (2025–2026)

Evidence labels used on every finding:
- **[M]** measurement (numbers from an experiment, scan or benchmark)
- **[A]** anecdote or incident report
- **[O]** opinion or vendor guidance without published data
- **(snippet)** the claim comes from a search-result summary; the primary page was not fetched, so treat it as unverified until checked.

All sources were accessed 2026-10-18.

## 1. Skills vs. tools vs. subagents vs. CLAUDE.md/AGENTS.md vs. slash commands vs. hooks: when to use each, and the trade-offs

### Takeaway
Vendors now publish a clear split. Always-on files (CLAUDE.md/AGENTS.md) hold short "always do X" facts. Skills hold on-demand procedures and reference material. Subagents isolate context. MCP tools give access to external systems. Hooks are the only deterministic option. The one controlled comparison (Vercel) found that passive always-on context beat on-demand skills for general framework knowledge, because skills were often never invoked. A separate ETH study found that always-on context files mostly add cost without raising success. Both results point to a short always-on file plus on-demand detail.

### Cited Findings
- [O] Claude Code's official comparison table: CLAUDE.md loads in full at session start and is charged on every request. Skills load descriptions at start and the full content when used. MCP loads tool names at start with schemas deferred. Subagents get an isolated context. Hooks run externally with "Zero, unless hook returns additional context." — [Claude Code docs, Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- [O] Hook vs skill, same page: hooks fire "without Claude deciding"; for skills, "Claude interprets the instructions; outcome can vary." Also: "An instruction like 'never edit `.env`' in CLAUDE.md or a skill is a request, not a guarantee. A `PreToolUse` hook that blocks the edit is enforcement." — [Claude Code docs](https://code.claude.com/docs/en/features-overview)
- [O] Escalation ladder recommended by Anthropic: a convention gotten wrong twice goes into CLAUDE.md; a prompt typed repeatedly becomes a user-invocable skill; a playbook pasted for the third time becomes a skill; output that floods the conversation goes through a subagent; "You want something to happen every time without asking" becomes a hook. — [Claude Code docs](https://code.claude.com/docs/en/features-overview)
- [O] "Keep CLAUDE.md under 200 lines. If it's growing, move reference content to skills or split into `.claude/rules/` files." Path-scoped rules load only for matching files. — [Claude Code docs](https://code.claude.com/docs/en/features-overview); repeated in [Steering Claude Code blog, 2026-06-18](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)
- [O] Steering blog: an unscoped rule is "mechanically identical to putting the content in CLAUDE.md"; subagents suit side tasks like "deep search, log analysis, or dependency audit", while skills suit work where you want to "see and steer each step"; custom output styles can drop the default software-engineering instructions. — [claude.com blog](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)
- [O] Use `disable-model-invocation: true` "for workflows with side effects that you want to trigger manually". It also removes the description from context. — [Claude Code best practices](https://code.claude.com/docs/en/best-practices); [Claude Code skills docs](https://code.claude.com/docs/en/skills)
- [O] "CLI tools are the most context-efficient way to interact with external services" (e.g., `gh` instead of a GitHub MCP server). — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- [M] Vercel (Jude Gao, 2026-01-27), Next.js 16 eval with APIs absent from training data. Pass rates: baseline 53%, skill (default) 53%, skill + explicit instructions 79%, AGENTS.md compressed docs index 100%. The index was compressed from ~40KB to 8KB with no loss. No sample size or variance was published. — [Vercel blog](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)
- [O] Vercel's working theory for why passive context won: no decision point about whether to look something up, the content is available on every turn, and there are no sequencing issues. They still recommend skills for "vertical, user-triggered workflows" such as upgrades and migrations. — [Vercel blog](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)
- [M] ETH Zurich, "Evaluating AGENTS.md" (Gloaguen et al., arXiv 2602.11988). Context files "do not generally improve task success rates" and raise inference cost "by over 20% on average". LLM-generated files reduced success in 5 of 8 settings (−0.5 to −2% in the later version, about −3% in v1). Developer-written files gave +2.4%, not statistically significant (p = 0.21; v1 reported about +4%). Repository overviews "are not helpful". Agents tend to follow the files, which leads to broader exploration. The authors recommend "only minimal requirements (e.g., specific tooling to use with this repository)." (snippet; numbers differ between versions, so cite the version) — [arXiv 2602.11988](https://arxiv.org/abs/2602.11988)
- [O] Codex has the same split. A skill's name, description and path load at startup and the full SKILL.md loads on use. Skills can be invoked explicitly (`$skill`, `/skills`) or implicitly. `allow_implicit_invocation: false` turns off model-initiated use. — [OpenAI/ChatGPT docs, Build skills](https://learn.chatgpt.com/docs/build-skills)
- [O] Anthropic: skills come in two types. "Capability-uplift" skills teach what the base model can't do; "encoded-preference" skills sequence steps the model already knows according to a team's process. The second type "are more durable but only as valuable as their fidelity to the actual workflow." — [Improving skill-creator, claude.com blog, 2026-03-03](https://claude.com/blog/improving-skill-creator-test-measure-and-refine-agent-skills)

### Inferences
- The Vercel and ETH results look like they conflict but don't. Vercel's always-on content was a compact retrieval index to docs the model lacked (capability uplift). ETH's context files were mostly repo overviews the agent could infer. So: keep always-on files short and limited to things the agent can't infer, and point to detail rather than inlining it.
- Skill vs AGENTS.md is mainly about who decides to load the content. Content that must apply in every relevant situation shouldn't depend on the model choosing to invoke a skill (see section 2), unless something enforces the invocation, such as a slash command or hook.

### Gaps
- No independent replication of Vercel's 100% result, and no published sample sizes.
- No controlled study compares subagents with in-context skills on quality, only on context cost.

## 2. Skill triggering in practice: failures, fixes and measured trigger rates

### Takeaway
Under-triggering is the most frequently reported failure. Measured baseline auto-invocation ranges from about 0–20% (Haiku 4.5, synthetic) to about 50–55% (Sonnet 4.5, real Claude Code binary), and Vercel saw 56% of cases with no invocation at all. The fixes with data behind them are a UserPromptSubmit hook that forces an explicit per-skill evaluation (100% on Sonnet 4.5 standard prompts, zero false positives), explicit instructions in AGENTS.md (95%+), description tuning (5 of 6 Anthropic skills improved), and explicit slash or `$` invocation. Newer Claude models can over-trigger when the prompt uses forceful language.

### Cited Findings
- [M] Vercel: the skill "was never invoked" in 56% of eval cases; adding explicit instructions raised the trigger rate to "95%+". — [Vercel blog](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)
- [M] Instruction wording mattered. "You MUST invoke the skill" made the agent read the docs first and anchor on doc patterns, so it missed project context (e.g., missing `next.config.ts` changes). "Explore project first, then invoke skill" did better. — [Vercel blog](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)
- [M] Scott Spence, Nov 2025: synthetic API tests, Claude Haiku 4.5, 4 SvelteKit skills, 5 prompt types × 10 runs. Activation was 20% (10/50) with a simple instruction hook, 80% (40/50) with an LLM pre-classifier hook and 84% (42/50) with a "forced eval" hook (state YES/NO per skill, call Skill(), then implement). Simple hooks failed on multi-skill prompts. — [scottspence.com](https://scottspence.com/posts/how-to-make-claude-code-skills-activate-reliably)
- [M] Spence follow-up, 2026-02-08: real `claude -p` binary in Daytona sandboxes, Sonnet 4.5, 22 prompts × 2 runs, about 250 invocations, $5.59 total. Activation: no hook 55%/50%, simple hook 59%/50%, forced-eval 100%/100%, llm-eval 100%/100%, "type-prompt" hook 55%/41%. On 24 harder prompts (5 needing no skill), forced-eval scored 75% with 0 false positives, and llm-eval scored 67% with 4 false positives (1 of 5 true negatives). When a skill activated, it was always the right one. The author found failures depend on keywords: prompts with explicit skill keywords activate, indirect phrasing often doesn't. — [scottspence.com follow-up](https://scottspence.com/posts/measuring-claude-code-skill-activation-with-sandboxed-evals)
- [O] Spence warns that the synthetic numbers shouldn't be treated as predictions for a project, because the sandboxed real-binary results differed (update dated 2026-09-13). — [scottspence.com](https://scottspence.com/posts/how-to-make-claude-code-skills-activate-reliably)
- [A] Claude Code issue tracker (read via mirrors; current GitHub status not verified): #9716, Claude can list installed skills but doesn't use them when a request matches; a coderabbit-workflow report, a request matching the trigger text almost word for word was handled manually (closed 2026-01-30); #15136 and #19308, Claude skips the Skill tool despite explicit "BLOCKING REQUIREMENT" instructions (v2.0.70). Users report `/skill-name` invocation as the reliable fallback. — [claudeissues.com #9716](https://claudeissues.com/issue/9716-bug-claude-code-assistant-not-aware-of-available-skills-in-claude-skills-directo); [#20986](https://claudeissues.com/issue/20986-claude-ignores-skill-triggers-even-when-user-request-clearly-matches-skill-descr); [#15136](https://claudeissues.com/issue/15136-bug-claude-fails-to-invoke-skills-immediately-despite-explicit-instructions); [#19308](https://claudeissues.com/issue/19308-critical-claude-systematically-ignores-skill-tool-despite-explicit-blocking-requ)
- [M] Anthropic: description tuning with skill-creator's optimization loop improved triggering on "5 out of 6 public skills" in its document-creation set. No baseline or after rates were published. — [claude.com blog, 2026-03-03](https://claude.com/blog/improving-skill-creator-test-measure-and-refine-agent-skills)
- [O] "If descriptions are vague or overlap, Claude may load the wrong skill or miss one that would help. To tell Claude to use a specific skill, invoke it with `/<name>`." — [Claude Code docs](https://code.claude.com/docs/en/features-overview)
- [O] Codex: write "concise descriptions with clear scope and boundaries" and "Front-load the key use case and trigger words so a host can still match the skill if descriptions are shortened"; test prompts against the description. — [OpenAI docs](https://learn.chatgpt.com/docs/build-skills)
- [O] Truncation failure mode: Claude Code cuts the combined `description` + `when_to_use` at 1,536 characters in the skill listing, so the key use case goes first. — [Claude Code skills docs](https://code.claude.com/docs/en/skills)
- [O] Silent configuration failures: if frontmatter doesn't start on line 1, the whole file is treated as content; if the YAML doesn't parse, the skill loads "with no fields set"; unrecognized field names are ignored without an error. — [Claude Code skills docs](https://code.claude.com/docs/en/skills)
- [O] Over-triggering on newer models: "Claude Opus 4.5 and Claude Opus 4.6 are also more responsive to the system prompt than previous models. If your prompts were designed to reduce undertriggering on tools or skills, these models may now overtrigger. The fix is to dial back any aggressive language. Where you might have said 'CRITICAL: You MUST use this tool when...', you can use more normal prompting like 'Use this tool when...'." Also: "Instructions like 'If in doubt, use [tool]' will cause overtriggering." — [Claude prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)

### Inferences
- Trigger rate depends on the model. The same setup went from 0–20% to 50–55% between Haiku 4.5 (synthetic) and Sonnet 4.5 (real binary). Any trigger fix needs re-measuring after a model change.
- The hook fix works through a structured commitment step (evaluate each skill, then activate), not through louder wording alone. Spence's "type-prompt" hook, which only injected text, did no better than no hook.
- The two pieces of advice pull in different directions. Forceful wording raised triggering in Spence's hook on Haiku and Sonnet 4.5, while Anthropic says forceful wording causes over-triggering on Opus 4.5+, and Vercel found "You MUST invoke" caused anchoring. Wording effects are model-specific, so they need evals, not folklore.

### Gaps
- No public trigger-rate data for Opus 4.5+ or for Codex implicit invocation.
- No large-N study of description wording variables (length, "use when" phrasing, examples). Anthropic's "5 of 6" has no effect sizes.
- Spence's work covers a single domain (SvelteKit) with author-written prompts.

## 3. Context bloat: token overhead of many tools and skills, and deferred loading

### Takeaway
The token cost is well measured. A typical multi-server MCP setup spends 55K–134K tokens on tool definitions before any work starts. Deferred loading cuts this by about 85% and also raised tool-selection accuracy in Anthropic's internal evals (Opus 4: 49% → 74%). Code-execution approaches report up to 98.7% savings in one example. Academic work shows selection accuracy collapses as tool lists grow (13.6% baseline vs 43.1% with retrieval). Claude Code and Codex now defer MCP schemas and cap the skill listing by default.

### Cited Findings
- [M] Five-server MCP setup: GitHub (35 tools) ~26K tokens, Slack (11) ~21K, Sentry (5) ~3K, Grafana (5) ~3K, Splunk (2) ~2K, for 58 tools and about 55K tokens. Jira adds ~17K. Anthropic internally saw tool definitions reach 134K tokens before optimization. — [Anthropic, Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)
- [M] Tool Search Tool: ~77K tokens upfront in the traditional setup vs ~8.7K with search, an 85% reduction. MCP-eval accuracy: Opus 4 49% → 74%, Opus 4.5 79.5% → 88.1%. Recommended when definitions exceed ~10K tokens or there are 10+ tools; less useful under 10 tools or when every tool is used in every session. — [Anthropic, Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)
- [M] Programmatic tool calling: average tokens on complex research tasks 43,588 → 27,297 (−37%); internal knowledge retrieval 25.6% → 28.5%; GIA benchmark 46.5% → 51.2%. The post is inconsistent on its expense example (50KB vs 200KB). — [Anthropic, Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)
- [M] Code execution with MCP (presenting tools as a filesystem of code APIs): one example went from ~150,000 to ~2,000 tokens (98.7%). Caveat: it needs a sandbox, resource limits and monitoring, which adds operational and security overhead. Cloudflare reported similar results under the name "Code Mode". — [Anthropic, Code execution with MCP, 2025-11-04](https://www.anthropic.com/engineering/code-execution-with-mcp)
- [M] RAG-MCP (Gan & Sun, arXiv 2505.03275): retrieving relevant tools before prompting cut prompt tokens by over 50% and raised selection accuracy from 13.62% to 43.13%. Retrieval precision degrades as the registry grows to thousands of tools. (snippet; one secondary summary says 73% token reduction instead) — [arXiv 2505.03275](https://arxiv.org/html/2505.03275v1)
- [M] Microsoft Research survey of 1,470 MCP servers: most servers have four or fewer tools; the largest has 256; GitHub MCP has 91 tools and Playwright-MCP 29. The blog cites external studies reporting "up to 85%" performance degradation with large tool spaces. — [Microsoft Research blog](https://www.microsoft.com/en-us/research/blog/tool-space-interference-in-the-mcp-era-designing-for-agent-compatibility-at-scale)
- [O] Claude Code now loads only MCP tool names and server instructions at start ("Tool search is on by default, so idle MCP tools consume minimal context"); `/context all` shows per-tool cost; `/skill-doctor` reports each skill's cost and usage. — [Claude Code docs](https://code.claude.com/docs/en/features-overview); [skills docs](https://code.claude.com/docs/en/skills)
- [O] Anthropic: too much context "can also add noise that makes Claude less effective; skills may not trigger correctly, or Claude may lose track of your conventions." — [Claude Code docs](https://code.claude.com/docs/en/features-overview)
- [O] Codex skill-list budget: "at most 2% of the model's context window, or 8,000 characters when the context window is unknown"; when many skills are installed, "Codex shortens skill descriptions first" and may omit skills with a warning; `skills.max_context_tokens` raises it "up to 10,000 tokens". — [OpenAI docs](https://learn.chatgpt.com/docs/build-skills)
- [O] Claude Code tool responses are capped at 25,000 tokens by default. — [Anthropic, Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents)

### Inferences
- Bloat hurts in two ways: token cost, and selection accuracy and attention (see section 4). Deferred loading helps both, but only as far as names and descriptions stay distinctive, because similarly named tools remain the main search failure (section 6).
- With both hosts budgeting the skill listing, a large skill catalog doesn't fail loudly. Descriptions get shortened or skills get dropped, which shows up as under-triggering.

### Gaps
- Anthropic's GitHub figure (35 tools) and Microsoft's (91 tools) refer to different server versions or configurations, and the token cost of the 91-tool version wasn't measured.
- No independent replication of the Tool Search accuracy gains outside Anthropic's internal eval.
- I didn't verify the commonly cited per-session tool caps (OpenAI 128 tools, older Cursor and VS Code limits). A trade article mentioned the OpenAI cap, but I couldn't confirm it in a primary source.

## 4. Instruction-following decay in long documents and rule-heavy prompts

### Takeaway
Instruction-following degrades as instruction count and context length grow. The best models reach about 68% at 500 simultaneous instructions, Claude Sonnet 4 decays linearly, and earlier instructions are favoured. Anthropic's own docs say bloated CLAUDE.md files make Claude ignore rules, that emphasis stops working when applied to many lines, and that newer models over-react to "CRITICAL/MUST". Giving the reason behind a rule is the officially recommended alternative. No study isolates "explaining why" against shouting as a controlled variable.

### Cited Findings
- [M] IFScale (Jaroslawicz et al., Distyl AI, arXiv 2507.11538, NeurIPS 2025): 20 models, 10 to 500 keyword-inclusion instructions. The best frontier models reach about 68% at 500. Decay patterns: threshold for reasoning models (o3, gemini-2.5-pro), linear for gpt-4.1 and claude-sonnet-4, exponential for gpt-4o and llama-4-scout. Models favour earlier instructions up to a saturation point. (snippet) — [arXiv 2507.11538](https://arxiv.org/html/2507.11538v1)
- [M] AgentIF (Qi et al., NeurIPS 2025): 707 instructions from 50 real agentic apps, averaging 1,723 words (max 15,630) and 11.9 constraints each. "Current models generally perform poorly, especially in handling complex constraint structures and tool specifications." The abstract gives no per-model scores. — [arXiv 2505.16944](https://arxiv.org/abs/2505.16944)
- [M] Chroma "Context Rot" (2025-07-14): across 18 LLMs (including Claude 4, GPT-4.1, Gemini 2.5), performance became increasingly unreliable as input length grew, even on trivial tasks with constant difficulty. Topically related distractors hurt more. (snippet; secondary blogs carry inconsistent numbers) — [Chroma research](https://research.trychroma.com/context-rot)
- [O] "Bloated CLAUDE.md files cause Claude to ignore your actual instructions!"; "If Claude keeps doing something you don't want despite having a rule against it, the file is probably too long and the rule is getting lost." The suggested test for each line: "Would removing this cause Claude to make mistakes?" — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- [O] On emphasis: "If Claude keeps skipping one instruction, add emphasis such as 'IMPORTANT' to that line alone. If you emphasize many lines, none of them stands out." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- [O] On system-prompt appends: "the more instructions you provide using this method, the less strictly Claude will follow them"; always-on lines "dilute adherence" to the important ones. — [Steering Claude Code blog](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)
- [O] On giving reasons: "Providing context or motivation behind your instructions, such as explaining to Claude why such behavior is important, can help Claude better understand your goals." Example: replace "NEVER use ellipses" with "Your response will be read aloud by a text-to-speech engine, so never use ellipses since the text-to-speech engine will not know how to pronounce them." — [Claude prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- [O] Same doc: dial back "CRITICAL: You MUST" for Opus 4.5/4.6 to avoid over-triggering, and tune down anti-laziness prompting because "Claude 4.6 models are more proactive and may overtrigger on instructions that were needed for previous models." — [Claude prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- [O] "Keep `SKILL.md` under 500 lines. Move detailed reference material to separate files." Loaded skill content stays in context across turns. — [Claude Code skills docs](https://code.claude.com/docs/en/skills)
- [M] ETH: agents "tend to respect" context-file instructions, so extra always-on rules raise steps (+3.34 on average for developer-written files) and cost (up to +19%) without a significant success gain. — [arXiv 2602.11988](https://arxiv.org/abs/2602.11988) (snippet)
- [O] Context loss: Claude "may start 'forgetting' earlier instructions" as context fills; after two failed corrections, `/clear` and rewrite the prompt. Compaction drops the oldest invoked skills first. Subdirectory CLAUDE.md files and path-scoped rules are lost until their directory is touched again. — [Claude Code best practices](https://code.claude.com/docs/en/best-practices); [Steering blog](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)

### Inferences
- A rule set's compliance depends on its total size, not just on each rule's wording. Stacking "absolute rules" lowers both the share any one rule gets and the value of emphasis. This follows from IFScale's density curves plus Anthropic's "none of them stands out".
- The primacy bias in IFScale suggests putting the most important constraints first in long documents. This is an inference from one benchmark using keyword constraints; it hasn't been tested on agent rule files.

### Gaps
- No controlled experiment compares the same rule written as "MUST/NEVER" vs with a stated reason on agent compliance. The evidence is vendor guidance plus model-specific anecdotes.
- The often-quoted claim that "frontier LLMs can follow about 150–200 instructions" (HumanLayer's CLAUDE.md blog) wasn't verified. It appears to extrapolate from IFScale and shouldn't be cited as a measurement.
- No per-model AgentIF scores were retrieved.

## 5. Deterministic enforcement: moving rules from prose into scripts, hooks, linters and schemas

### Takeaway
Every vendor source agrees that prose instructions are advisory and that hooks, permissions, managed settings and validators are the only way to make a rule hold every time. The empirical support is indirect. Measured trigger gains come from hook-injected structure (Spence), and measured failures come from prose-only approaches (Vercel's 56% never-invoked rate, issue reports of ignored "BLOCKING REQUIREMENT"). I found no head-to-head study measuring compliance with the same rule as prose vs as a hook.

### Cited Findings
- [O] "Use hooks for actions that must happen every time with zero exceptions … Unlike CLAUDE.md instructions which are advisory, hooks are deterministic and guarantee the action happens." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- [O] "If Claude already does something correctly without the instruction, delete it or convert it to a hook." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- [O] "Put guardrails in hooks … If a rule must hold every time, make it a hook rather than a prompt instruction." CLAUDE.md and output styles: "Claude follows both as instructions, so neither is enforced." — [Claude Code docs](https://code.claude.com/docs/en/features-overview)
- [O] "A real guardrail needs to be deterministic." A `PreToolUse` hook "can inspect a call and exit with code 2 to block it"; managed settings are "the only way to enforce a deterministic, organization-wide guardrail"; "The model choosing to run a formatter is different from the formatter running automatically." Prompted rules can fail "under pressure, in long sessions, in ambiguous situations, or through prompt injection in a file." — [Steering Claude Code blog](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)
- [O] Verification as a gate: a Stop hook "runs your check as a script and blocks the turn from ending until it passes"; "Claude stops when the work looks done. Without a check it can run, 'looks done' is the only signal available." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- [M] Hook-forced structure vs prose: on Sonnet 4.5 with the real binary, a forced-eval UserPromptSubmit hook raised skill activation from 50–55% to 100% on standard prompts. A hook that only injected text did not help (41–55%). — [Spence follow-up](https://scottspence.com/posts/measuring-claude-code-skill-activation-with-sandboxed-evals)
- [A] Prose-only failure: users report Claude ignoring explicit "BLOCKING REQUIREMENT" skill instructions (#19308, via mirror). — [claudeissues.com #19308](https://claudeissues.com/issue/19308-critical-claude-systematically-ignores-skill-tool-despite-explicit-blocking-requ)
- [O] Strict schemas and data models for tool parameters, plus actionable validation errors, are recommended so the tool catches malformed calls itself. — [Anthropic, Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents)
- [O] Anthropic's own caution against over-gating: a reviewer subagent "prompted to find gaps will usually report some, even when the work is sound … Chasing every finding leads to over-engineering"; it advises flagging only gaps that affect correctness or stated requirements. — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- [O] AEVAL (arXiv 2607.16345) argues for keeping the skill executor and grader separate, so an agent can't fix its own output mid-run and then grade it as passing. (snippet) — [arXiv 2607.16345](https://arxiv.org/pdf/2607.16345)

### Inferences
- What to move into code: invariants that can be checked mechanically (file paths, schemas, banned commands, formatting, required tests). Judgment-heavy guidance (style, creative structure) can't be checked deterministically. Encoding it as a hard gate risks false blocks and the over-engineering Anthropic warns about.
- A hook that only appends reminder text is not deterministic enforcement. It is still a prompt, and Spence's "type-prompt" result suggests such reminders may be deprioritised.

### Gaps
- No controlled measurement of compliance for the same rule as prose vs a hook or linter. Teams wanting a number would need their own eval.
- No data on how often hooks misfire (false blocks) or on their latency cost in practice.

## 6. Tool-side failures and documented fixes

### Takeaway
The best-documented tool failures are overlapping or colliding names, huge responses, opaque IDs, errors returned without an error flag, and ambiguous parameters. The documented fixes are workflow-level tool consolidation, namespacing, returning human-readable names alongside IDs, a concise/detailed response mode, pagination and truncation, actionable error text and usage examples. Anthropic measured +18 percentage points from examples and a 3× token cut from concise responses.

### Cited Findings
- [M] Microsoft survey of 1,470 servers: 775 tools have colliding names ("search" appears on 32 servers; get_user 11, execute_query 11, list_tables 10). Response length over 2,443 calls: median 98 tokens, mean 4,431, top tool average 557,766. 16 tools exceed 128K tokens in a single call. Of 5,983 results with no error flag, GPT-4.1 judged 3,536 to contain errors. Schema depth averages 2.24, max 20. — [Microsoft Research blog](https://www.microsoft.com/en-us/research/blog/tool-space-interference-in-the-mcp-era-designing-for-agent-compatibility-at-scale)
- [O] Microsoft's recommendations: namespaces generated from server names, caching schemas for RAG-style tool selection, summarizing or paginating long results, and an "MCP Server card" that lists expected token output, latency and the models and clients the server was tested with. The talk adds: expose as few tools as possible, keep responses short, use unique descriptive names. — [Microsoft Research blog](https://www.microsoft.com/en-us/research/blog/tool-space-interference-in-the-mcp-era-designing-for-agent-compatibility-at-scale)
- [M] Concise vs detailed response: 72 vs 206 tokens in Anthropic's Slack example, about ⅓. — [Anthropic, Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents)
- [O] Names vs IDs: mapping UUIDs to semantic names or 0-indexed IDs "improved retrieval precision by reducing hallucinations"; a `response_format` enum lets the agent request IDs when a later call needs them. — [Anthropic, Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents)
- [O] Consolidation: build tools around workflows, e.g. `schedule_event` instead of `list_users` + `list_events` + `create_event`, and `search_logs` instead of `read_logs`. Namespacing (`asana_search`, `asana_projects_search`): prefix vs suffix "changed evaluation results", so test it per model. Parameter naming: `user_id`, not `user`. Errors: return actionable guidance and correct examples, "not opaque codes or tracebacks." — [Anthropic, Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents)
- [A] Anthropic reports that precise refinements to tool descriptions helped Claude Sonnet 3.5 reach state of the art on SWE-bench Verified (no figure given). — [Anthropic, Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents)
- [M] Tool Use Examples: complex-parameter accuracy 72% → 90% in internal tests; 1–5 examples per tool recommended. The main failure Tool Search hit was similarly named tools ("notification-send-user" vs "notification-send-channel"). — [Anthropic, Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)
- [M] Secondary, cited by Microsoft: Anthropic used a tool-testing agent to rewrite defective tool descriptions, which cut task completion time by 40%; Composio reported +47% from flattening parameters. I didn't fetch either primary source. — [Microsoft Research blog](https://www.microsoft.com/en-us/research/blog/tool-space-interference-in-the-mcp-era-designing-for-agent-compatibility-at-scale)
- [O] Intermediate results that pass through the model waste tokens and cause "copying errors"; filtering in code before returning helps. — [Anthropic, Code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp)
- [O] Use MCP tool annotations to flag open-world or destructive tools. — [Anthropic, Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents)

### Inferences
- Name collisions aren't only a single-server problem. A user who installs several servers, or a plugin bundling many tools, ends up with collisions the author never saw. Distinctive, namespaced names and descriptions that say when not to use a tool help both selection and deferred search.
- Errors without an error flag (3,536 of 5,983) suggest servers often put failures in normal content. Setting `isError` and writing actionable error text are cheap fixes.

### Gaps
- No public numbers for Anthropic's Slack and Asana human-written vs Claude-optimized server comparison; the post shows charts only.
- No controlled data on how tool description length affects selection.

## 7. Security incidents and defenses for authors

### Takeaway
Tool descriptions, tool outputs and skill files all act as prompt-injection channels, and real incidents exist on each: tool poisoning and rug pulls (Invariant demos), line jumping (Trail of Bits), toxic agent flows through the official GitHub MCP server, the first malicious MCP npm package (postmark-mcp, September 2025), and large-scale malicious skills on ClawHub (2026). Scans find about a quarter to a third of public skills have some issue. Bundled scripts double the odds of a vulnerability. The defenses with the most support are architectural: avoid the "lethal trifecta", pin and hash tool definitions, least privilege, and treat skills as a software supply chain.

### Cited Findings
- [A] Invariant Labs, 2025-04-01, tool poisoning demo: a poisoned `add` tool in Cursor told the agent to read `~/.cursor/mcp.json` and SSH keys and pass them in a `sidenote` parameter. The confirmation UI hid the full arguments. **Rug pull**: "a malicious server can change the tool description after the client has already approved it." **Shadowing**: a malicious server's description redirected a trusted `send_email` tool from another server, and "the malicious tool never needs to be called." Mitigations: visible descriptions, version pinning with hashes or checksums, and cross-server dataflow controls. — [Invariant Labs](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks)
- [A] Trail of Bits, 2025-04-21, "line jumping": injection in `tools/list` descriptions or server instructions reaches the model at connection time, before any tool is called and before the user can deny the server. Payloads included conversation-history exfiltration and ANSI terminal escape sequences that hide instructions. Defense: `mcp-context-protector` with trust-on-first-use pinning and description validation. (snippet) — [Trail of Bits blog](https://blog.trailofbits.com/2025/04/21/jumping-the-line-how-mcp-servers-can-attack-you-before-you-ever-use-them/); [ToB, 2025-07-28](https://blog.trailofbits.com/2025/07/28/we-built-the-security-layer-mcp-always-needed/)
- [A] Invariant Labs, 2025-05-26, GitHub MCP "toxic agent flow": a malicious issue in a public repo hijacked Claude 4 Opus in Claude Desktop into copying private-repo data (salary, relocation plans) into a public PR. Invariant: "this is not a flaw in the GitHub MCP server code itself." Mitigations: least-privilege repo access, one repo per session, runtime monitoring. Model alignment alone was insufficient. — [Invariant Labs](https://invariantlabs.ai/blog/mcp-github-vulnerability)
- [O] Simon Willison, "lethal trifecta" (2025-06-16): private data + untrusted content + external communication means exfiltration is easy. Guardrails that claim 95% detection are "very much a failing grade"; "once an LLM agent has ingested untrusted input, it must be constrained". Most vendor fixes closed the exfiltration channel. — [simonwillison.net](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- [A] postmark-mcp (September 2025): an npm package impersonating Postmark's MCP server published 15 clean versions, then v1.0.16 added one line that BCC'd every email to the attacker. About 1,643 downloads before removal. Koi called it "the world's first sighting of a real world malicious MCP server." (snippet) — [Koi Security](https://koi.ai/blog/postmark-mcp-npm-malicious-backdoor-email-theft); [The Register](https://www.theregister.com/2025/09/29/postmark_mcp_server_code_hijacked/)
- [M] Liu et al., "Agent Skills in the Wild" (arXiv 2601.10338, 2026-01-15): 31,132 of 42,447 skills from two marketplaces analyzed. 26.1% had at least one vulnerability across 14 patterns; data exfiltration 13.3% and privilege escalation 11.8% were most common. Skills that bundle executable scripts are 2.12× more likely to be vulnerable (OR=2.12, p<0.001). 5.2% show high-severity patterns suggesting malicious intent. — [arXiv 2601.10338](https://arxiv.org/abs/2601.10338)
- [M] Snyk ToxicSkills (2026-02-05): 3,984 skills from ClawHub and skills.sh. 1,467 (36.82%) had some security issue, 534 (13.4%) at least one critical issue, and 76 had confirmed malicious payloads. Prompt injection appeared in 91% of confirmed malicious skills but 0% of the top-100 skills.sh skills. 10.9% of ClawHub skills contain hardcoded secrets. Observed techniques: password-protected ZIP malware, base64/Unicode-obfuscated exfiltration, `curl | bash`, instructions fetched at runtime that can change after review, and memory-file poisoning. Snyk notes skills have "no code signing, no security review, and no sandbox by default." — [Snyk](https://snyk.io/blog/toxicskills-malicious-ai-agent-skills-clawhub/)
- [M] Koi Security ClawHavoc (February 2026): 341 malicious skills among 2,857 audited on ClawHub, 335 from one campaign. A larger figure of "over 1,184 malicious skills" appears in an arXiv paper and a CSA note with different date ranges, so these counts may overlap. (snippet) — [CSA research note](https://labs.cloudsecurityalliance.org/research/csa-research-note-ai-skill-supply-chain-attacks-20260624-csa/); [arXiv 2604.02837](https://arxiv.org/html/2604.02837v1)
- [O] "Towards Secure Agent Skills" notes that a single adversarial sentence in a SKILL.md can redirect agent behavior. A May 2026 study reports metadata-only manipulation (no code) can skew skill discovery and evade classifiers. (snippet) — [arXiv 2604.02837](https://arxiv.org/html/2604.02837v1); [CSA note on SKILL.md poisoning](https://labs.cloudsecurityalliance.org/research/csa-research-note-skill-md-agent-context-poisoning-20260506/)
- [O] Author-side defenses with vendor backing: flag destructive or open-world tools with annotations ([Anthropic](https://www.anthropic.com/engineering/writing-tools-for-agents)); `disable-model-invocation: true` for skills with side effects, which Claude Code also blocks if Claude tries to call them ([Claude Code skills docs](https://code.claude.com/docs/en/skills)); audit with `uvx mcp-scan@latest --skills` and vet skills like npm/PyPI packages ([Snyk](https://snyk.io/blog/toxicskills-malicious-ai-agent-skills-clawhub/)).

### Inferences
- For skill authors, the bundled-script finding (2.12×) and Snyk's runtime-fetched instructions finding point the same way: scripts that are pinned, reviewed and local are safer than scripts or instructions fetched at run time.
- An MCP tool that reads untrusted content and can also send data out (posting, emailing, publishing) meets two of the three trifecta conditions by itself. A publishing tool should require explicit user authorization per action rather than rely on prompt-level rules.

### Gaps
- Malicious-skill counts conflict across sources (76, 341, over 1,184) because of different scopes, dates and confirmation methods. One reviewer criticized a May 2026 report for thin confirmation.
- No data on how often rug pulls happen in practice, as opposed to demonstrations.

## 8. Maintenance: versioning, keeping docs and code in sync, drift, and CI testing

### Takeaway
The main practices with any support are evals for each skill (with-skill vs without-skill, blind A/B comparison, pass-rate, time and token benchmarks) rerun on every model change, held-out test sets for tools, and treating CLAUDE.md like code (prune, observe behavior, review on failure). Tooling for CI skill testing exists but is early. There is little evidence on how many teams run it or on drift-detection metrics.

### Cited Findings
- [O] Skill-creator (2026-03-03) adds evals, a benchmark mode (pass rate, elapsed time, tokens), parallel runs in clean contexts, and blind comparator agents for skill vs skill or skill vs no-skill. "Running evals against a new model gives an early signal when a skill's behavior shifts." — [claude.com blog](https://claude.com/blog/improving-skill-creator-test-measure-and-refine-agent-skills)
- [O] Obsolescence check: if the base model passes evals without the skill loaded, "The skill isn't broken; it's just no longer necessary." This applies to capability-uplift skills. — [claude.com blog](https://claude.com/blog/improving-skill-creator-test-measure-and-refine-agent-skills)
- [O] Tool evals: realistic multi-step tasks with verifiers; track accuracy, runtime, call count, tokens and tool errors; treat redundant calls as a sign of pagination or limit problems; use held-out sets against overfitting; feed transcripts back to Claude Code "to refactor tools and descriptions together." — [Anthropic, Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents)
- [O] "Treat CLAUDE.md like code: review it when things go wrong, prune it regularly, and test changes by observing whether Claude's behavior actually shifts." `/doctor` proposes cuts for content derivable from the codebase; `/skill-doctor` reports per-skill cost and usage. — [Claude Code best practices](https://code.claude.com/docs/en/best-practices); [skills docs](https://code.claude.com/docs/en/skills)
- [O] Microsoft recommends server cards that list the models, agents and clients a server was tested with and any known incompatibilities, which is a form of versioned compatibility metadata. — [Microsoft Research blog](https://www.microsoft.com/en-us/research/blog/tool-space-interference-in-the-mcp-era-designing-for-agent-compatibility-at-scale)
- [O] Drift hazards in the host itself: Claude Code silently ignores misspelled frontmatter fields and loads a skill with no fields set when the YAML fails to parse. Codex may need a restart to pick up skill changes. Both hosts truncate descriptions under budget pressure. — [Claude Code skills docs](https://code.claude.com/docs/en/skills); [OpenAI docs](https://learn.chatgpt.com/docs/build-skills)
- [O] Vendor and tooling material: a skill can cut tokens while quietly dropping steps and still look fine on a quick read; the recommended check is a fixed prompt set run with the skill on and off, comparing traces ([FutureAGI blog](https://futureagi.com/blog/agent-skill-regression-testing/)). SkillCI (Go, v0.1–0.3) targets model-update regressions in CI ([pkg.go.dev](https://pkg.go.dev/github.com/kabirnarang39/skillci@v0.3.0)). AEVAL treats each skill change as a CI test event against a declared eval contract ([arXiv 2607.16345](https://arxiv.org/pdf/2607.16345)). (snippet)
- [M] Trigger rates shifted between models in the same harness (Haiku 4.5 synthetic: 20% simple-hook activation; Sonnet 4.5 real binary: 50–59%), which is direct evidence that skill behavior drifts with model changes. — [Spence 2025](https://scottspence.com/posts/how-to-make-claude-code-skills-activate-reliably); [Spence 2026](https://scottspence.com/posts/measuring-claude-code-skill-activation-with-sandboxed-evals)

### Inferences
- Two separate kinds of drift need checks: text vs code drift (a skill describing tool parameters or behavior that changed), which a cheap deterministic check comparing the skill's references with the tool schema can catch; and model drift (the same text behaving differently), which only behavioral evals catch.
- Anthropic's own documentation runs to model-version-specific advice (e.g., "Opus 4.5/4.6 overtrigger"). Wording tuned for one model generation should be treated as a dated assumption and re-tested.

### Gaps
- No survey data on how many skill or MCP authors run evals in CI.
- No standard metric for skill drift. Proposed approaches (AEVAL, SkillCI) are new and unvalidated at scale.
- I found no practitioner incident write-up of a skill-vs-tool drift failure with measured impact.
