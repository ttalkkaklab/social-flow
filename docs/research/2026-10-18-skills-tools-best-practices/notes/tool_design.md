# Designing tools for LLM agents (MCP servers used by Claude)

Research date: 2026-10-18. "Latest" MCP spec resolved to revision **2026-07-28** (the rendered tools page links to `/specification/2026-07-28/...`; its changelog names 2025-11-25 as the previous revision). The `ToolAnnotations`, `Tool` and `CallToolResult` doc comments quoted below come from the raw `schema/2026-07-28/schema.ts` in the `modelcontextprotocol/modelcontextprotocol` GitHub repo, not from the rendered tools page (which omits the annotation fields).

Status tags used on every bullet:
- `[MUST]` / `[SHOULD]` / `[MAY]` = normative MCP spec text (RFC 2119 words as written in the spec).
- `[SPEC]` = MCP spec/schema text that defines fields, defaults or change history without an RFC 2119 keyword.
- `[API]` = documented behavior/limit of the Claude API or Claude Code (a fact about the platform, not advice).
- `[REC]` = vendor recommendation or opinion (Anthropic, OpenAI, Google, MCP non-normative guidance).
- `[DATA]` = measured number from an eval or benchmark.
- `[LOCAL]` = the two local skills (astra `tool-author` 5.25.0, plugin-dev `mcp-integration` copy `ea10b213686c`, mtime 2026-10-16), plus Anthropic's public `mcp-builder` skill.

## Q1. What Anthropic's engineering posts recommend (choosing, namespacing, returning context, token efficiency, descriptions, errors)

### Takeaway
Anthropic's core position: build a few consolidated, workflow-shaped tools matched to real eval tasks rather than one tool per API endpoint; namespace them; return high-signal, human-readable fields with a `response_format` knob; paginate/filter/truncate with defaults and steering messages (Claude Code caps MCP output at 25,000 tokens by default); write descriptions like onboarding a new hire; and make errors actionable. Anthropic's own `mcp-builder` skill partly contradicts the "don't wrap endpoints" advice.

### Cited Findings
**Sources and dates**
- "Writing effective tools for agents — with agents", published Sep 11, 2025, by Ken Aizawa (with Research, MCP, Product Engineering, Marketing, Design, Applied AI teams) — [Anthropic Engineering](https://www.anthropic.com/engineering/writing-tools-for-agents)
- Related posts: "Building effective agents" (Dec 19, 2024) — [Anthropic](https://www.anthropic.com/engineering/building-effective-agents); "Effective context engineering for AI agents" (Sep 29, 2025) — [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents); "Code execution with MCP" (Nov 4, 2025) — [Anthropic](https://www.anthropic.com/engineering/code-execution-with-mcp); "Advanced tool use" (Nov 24, 2025; beta header `advanced-tool-use-2025-11-20` at publication) — [Anthropic](https://www.anthropic.com/engineering/advanced-tool-use)

**Choosing which tools to build**
- [REC] "More tools don't always lead to better outcomes." Avoid tools that merely wrap existing API endpoints; build "a few thoughtful tools targeting specific high-impact workflows," matched to eval tasks — [Writing tools](https://www.anthropic.com/engineering/writing-tools-for-agents)
- [REC] Prefer `search_contacts` / `message_contact` over a `list_contacts` that returns everything. Consolidation examples: `list_users` + `list_events` + `create_event` → `schedule_event`; `read_logs` → `search_logs` (relevant lines plus surrounding context); `get_customer_by_id` + `list_transactions` + `list_notes` → `get_customer_context` — [Writing tools](https://www.anthropic.com/engineering/writing-tools-for-agents)
- [REC] Each tool needs a clear, distinct purpose; overlapping tools distract agents — [Writing tools](https://www.anthropic.com/engineering/writing-tools-for-agents)
- [REC] Tools should be "self-contained, robust to error, and extremely clear with respect to their intended use"; "bloated tool sets that cover too much functionality" are a common failure mode; "If a human engineer can't definitively say which tool should be used in a given situation", an agent can't do better; curate "a minimal viable set of tools" — [Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- [REC] Conflict: Anthropic's public `mcp-builder` skill says "Balance comprehensive API endpoint coverage with specialized workflow tools… Performance varies by client—some clients benefit from code execution that combines basic tools, while others work better with higher-level workflows. When uncertain, prioritize comprehensive API coverage." and "Keep tool operations focused and atomic" — [LOCAL/anthropics/skills mcp-builder SKILL.md](https://github.com/anthropics/skills/blob/main/skills/mcp-builder/SKILL.md), [mcp_best_practices.md](https://github.com/anthropics/skills/blob/main/skills/mcp-builder/reference/mcp_best_practices.md); contradicted by [Writing tools](https://www.anthropic.com/engineering/writing-tools-for-agents) ("avoid tools that just wrap existing API endpoints"). The Claude API docs side with consolidation (see Q2).

**Namespacing**
- [REC] Group related tools under common prefixes by service and resource (e.g., `asana_search`, `asana_projects_search`). Prefix- vs suffix-based naming has "non-trivial effects" on tool-use evals and the effect varies by LLM, so test your own scheme — [Writing tools](https://www.anthropic.com/engineering/writing-tools-for-agents)
- [REC] `mcp-builder`: snake_case, format `{service}_{action}_{resource}` (e.g., `slack_send_message`, `github_create_issue`), action-oriented verbs, avoid generic names that could collide — [mcp_best_practices.md](https://github.com/anthropics/skills/blob/main/skills/mcp-builder/reference/mcp_best_practices.md)
- [REC] Tool search matches names and descriptions, so descriptive names such as `search_customer_orders` outperform terse ones such as `query_db_orders` — [Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)

**Returning meaningful context**
- [REC] Return high-signal fields (`name`, `image_url`, `file_type`) over technical identifiers (`uuid`, `256px_image_url`, `mime_type`). Resolving UUIDs to natural-language names or a 0-indexed scheme improved Claude's retrieval precision by reducing hallucinations — [Writing tools](https://www.anthropic.com/engineering/writing-tools-for-agents)
- [REC] Conflict on identifiers: the Claude API docs say "Return semantic, stable identifiers (for example, slugs or UUIDs) rather than opaque internal references, and include only the fields Claude needs to reason about its next step" — [Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools). `mcp-builder` reconciles them: Markdown output should "Show display names with IDs in parentheses" — [mcp_best_practices.md](https://github.com/anthropics/skills/blob/main/skills/mcp-builder/reference/mcp_best_practices.md)
- [REC][DATA] Add a `response_format` enum (`"detailed"` / `"concise"`). In the post's Slack example a detailed response used 206 tokens and a concise one 72 (about one-third) — [Writing tools](https://www.anthropic.com/engineering/writing-tools-for-agents)
- [REC] Response structure (XML, JSON, Markdown) affects performance; the best choice varies by task and agent — [Writing tools](https://www.anthropic.com/engineering/writing-tools-for-agents). `mcp-builder` recommends supporting both `response_format="json"` and `"markdown"` (Markdown "typically default"; convert timestamps to human-readable; omit verbose metadata) — [mcp_best_practices.md](https://github.com/anthropics/skills/blob/main/skills/mcp-builder/reference/mcp_best_practices.md)
- [REC] When Claude writes code against tools (programmatic tool calling), "Document return formats": clearly specify return fields and types — [Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)

**Token efficiency**
- [REC] Use pagination, range selection, filtering and truncation with sensible defaults for potentially large responses. When truncating, steer the agent toward efficient strategies, e.g., "many small and targeted searches" instead of one broad search — [Writing tools](https://www.anthropic.com/engineering/writing-tools-for-agents)
- [API] Claude Code: "Claude Code displays a warning when MCP tool output exceeds 10,000 tokens and limits output to 25,000 tokens by default." Change with `MAX_MCP_OUTPUT_TOKENS`; "The warning threshold is fixed." Over the limit, a successful non-image result is saved to a file in the session's `tool-results` directory and replaced with a message naming the path — [Claude Code MCP docs](https://code.claude.com/docs/en/mcp)
- [API] Claude Code persists any successful text result over 50,000 characters to a file regardless of `MAX_MCP_OUTPUT_TOKENS`, unless the tool sets `_meta["anthropic/maxResultSizeChars"]` (hard ceiling 500,000 characters) in its `tools/list` entry; image-bearing results stay subject to `MAX_MCP_OUTPUT_TOKENS`. HTTP/SSE responses over 16 MiB fail ("return less data per response… for example by paginating results") — [Claude Code MCP docs](https://code.claude.com/docs/en/mcp)
- [REC] `mcp-builder` pagination defaults: "Always respect the `limit` parameter"; return `has_more`, `next_offset`/`next_cursor`, `total_count`; "Default to reasonable limits: 20-50 items is typical"; "Never load all results into memory" — [mcp_best_practices.md](https://github.com/anthropics/skills/blob/main/skills/mcp-builder/reference/mcp_best_practices.md)
- [REC] Tools must "promote efficiency, both by returning information that is token efficient"; prefer just-in-time retrieval by returning "lightweight identifiers (file paths, stored queries, web links, etc.)" that the agent dereferences later; tool result clearing is "one of the safest lightest touch forms of compaction" — [Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- [DATA] Code-execution pattern: a 2-hour meeting transcript can add ~50,000 extra tokens when intermediate results pass through the model; presenting MCP tools as a file tree of code APIs cut one example "from 150,000 tokens to 2,000 tokens" (98.7%). Suggests a `search_tools` tool with a "detail level parameter" — [Code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp)

**Prompt-engineering descriptions and parameters**
- [REC] Describe each tool as you would to a new hire: make implicit context explicit (query formats, niche terminology, relationships between resources). Use unambiguous parameter names (`user_id`, not `user`). Enforce inputs/outputs with strict data models. Small description refinements had large effects: Claude Sonnet 3.5 reached state of the art on SWE-bench Verified after precise description changes. For MCP, use annotations to disclose open-world access or destructive changes — [Writing tools](https://www.anthropic.com/engineering/writing-tools-for-agents)
- [REC] Tool definitions deserve "just as much prompt engineering attention as your overall prompts." Agent-computer interface (ACI) design: put yourself in the model's shoes; include example usage, edge cases, input requirements, boundaries between similar tools; write like a docstring for a junior developer; give the model enough tokens to think before committing; keep formats close to naturally occurring text; avoid formatting overhead (line counts in diffs, escaping code in JSON); poka-yoke the arguments. SWE-bench: the team spent more time optimizing tools than the overall prompt, and switching to absolute filepaths fixed relative-path errors — [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- [REC] Input parameters should be "descriptive, unambiguous, and play to the inherent strengths of the model" — [Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

**Errors that steer**
- [REC] Errors should state specific, actionable fixes rather than opaque error codes or tracebacks — [Writing tools](https://www.anthropic.com/engineering/writing-tools-for-agents)
- [REC] "Write instructive error messages. Instead of generic errors like `"failed"`, include what went wrong and what Claude should try next (for example, `"Rate limit exceeded. Retry after 60 seconds."`)." — [Handle tool calls](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)
- [REC] `mcp-builder` example: `Error: ${error.message}. Try using filter='active_only' to reduce results.`; also "Don't expose internal implementation details" — [mcp_best_practices.md](https://github.com/anthropics/skills/blob/main/skills/mcp-builder/reference/mcp_best_practices.md)
- [API] Claude Code truncates `isError: true` text longer than about 11,000 characters to its first 5,000 and last 5,000 characters with a removal marker — [Claude Code MCP docs](https://code.claude.com/docs/en/mcp)

### Inferences
- For a server like this repo's plugin (100+ tools), the advice points toward fewer, workflow-shaped tools with an `action`/mode parameter or consolidated "context" tools, plus `response_format`, `limit`/cursor defaults, and errors that name the next call.
- Put the most important wording at the very start of an error message: Claude Code keeps only the head and tail of very long error text.
- Returning both a display name and a stable ID (name first, ID in parentheses or a separate field) satisfies both Anthropic sources at once.

### Gaps
- The held-out Slack/Asana result charts in the Writing-tools post (human-written vs Claude-optimized) are images; numeric values were not extracted.
- The exact "unhelpful vs helpful" error example text and the precise `response_format` code sample from the post were not returned verbatim by the fetch.

## Q2. Claude tool-use API docs: descriptions, input_schema, input_examples, strict, tool_choice, parallel use, tool search, programmatic calling, token cost

### Takeaway
The Claude docs call detailed descriptions "by far the most important factor" (≥3–4 sentences), recommend consolidating related actions behind an `action` parameter, service-prefixed names, high-signal responses, `input_examples` for format-sensitive inputs (1–5, ~20–200 tokens each), `strict: true` for schema-guaranteed inputs, tool search once you pass ~10 tools or 10k definition tokens, and note that the newest models (Opus 5.5, Sonnet 5.5) reject forced `tool_choice`.

### Cited Findings
**Definition fields and names**
- [API] User tool fields: `name` "Must match the regex `^[a-zA-Z0-9_-]{1,128}$`", `description`, `input_schema`, optional `input_examples`; other optional properties include `cache_control`, `strict`, `defer_loading`, `allowed_callers` — [Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- [API] The API builds a tool-use system prompt containing "Here are the functions available in JSONSchema format:" followed by the definitions, then the user system prompt — [Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)

**Descriptions (verbatim best-practice list)**
- [REC] "**Provide extremely detailed descriptions.** This is by far the most important factor in tool performance." Include what the tool does, "When it should be used (and when it shouldn't)", what each parameter means, and caveats such as "what information the tool does not return". "Aim for at least 3–4 sentences for each tool description, more if the tool is complex." — [Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- [REC] "**Consolidate related operations into fewer tools.** Rather than creating a separate tool for every action (`create_pr`, `review_pr`, `merge_pr`), group them into a single tool with an `action` parameter. Fewer, more capable tools reduce selection ambiguity" — [Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- [REC] "**Use meaningful namespacing in tool names.**… prefix names with the service (for example, `github_list_prs`, `slack_send_message`)… especially important when using tool search." — [Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- [REC] "**Ask for an explanation, not reasoning.**" A parameter asking for the model's thinking or step-by-step reasoning "may lead to a `reasoning_extraction` refusal." — [Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- [REC] Good example: `get_stock_price` description of five sentences stating input constraints (US exchange tickers), return (latest trade price in USD), when to use, and what it won't return; poor example: "Gets the stock price for a ticker." — [Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- [REC] Steering trigger behavior from the system prompt: "Use the tools to investigate before responding." increases tool use; "Always call a tool first before responding." pushes further; "Use your judgment about whether to call a tool or respond directly." keeps it conservative — [Tool use overview](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)
- [API] Missing required params: "Claude Opus is much more likely to recognize that a parameter is missing and ask for it"; Claude Sonnet "might also infer a reasonable value" — [Tool use overview](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)

**input_examples**
- [API] Each example "must be valid according to the tool's `input_schema`. Invalid examples return a 400 error"; not supported on server tools or the computer/browser toolsets; "Token cost - Examples add to prompt tokens: ~20–50 tokens for simple examples, ~100–200 tokens for complex nested objects" — [Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- [REC][DATA] Accuracy on complex parameter handling rose from 72% to 90% with examples (internal testing). "Keep it concise: 1-5 examples per tool." "Focus on ambiguity (only add examples where correct usage isn't obvious from schema)." Show minimal, partial and full specifications with realistic data. Skip for simple one-parameter tools, standard formats (URLs, emails), or constraints better expressed as JSON Schema — [Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)
- [API] `input_examples` are expanded along with a deferred tool's definition when tool search discovers it — [Tool search tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)

**Strict tool use**
- [API] `strict: true` "guarantees Claude's tool inputs match your JSON Schema by constraining the model's token sampling to schema-valid outputs (a technique called grammar-constrained sampling)." Guarantees: input follows `input_schema`; `name` is always valid. Examples set `additionalProperties: false`. Without strict, Claude "might return incompatible types (`"2"` instead of `2`) or omit required fields" — [Strict tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/strict-tool-use)
- [API] Compiled schemas are "temporarily cached for up to 24 hours since last use"; do not put PHI in property names, `enum`, `const` or `pattern` values. Strict grammar builds from the full toolset, so `defer_loading` and strict compose without recompilation — [Strict tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/strict-tool-use), [Tool search tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)
- [API] "To eliminate invalid tool calls entirely, use strict tool use" — [Handle tool calls](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)

**tool_choice**
- [API] Options: `auto` (default with tools), `any`, `tool`, `none`. With `any`/`tool` the API prefills the assistant turn, so no text precedes `tool_use`, and forcing a tool "skips thinking". Manual extended thinking rejects `any`/`tool`. "Claude Opus 5.5, Claude Sonnet 5.5, Claude Fable 5.1, and Claude Mythos 5.1" return a 400 for `any`/`tool`; use `auto` with strict tool use or structured outputs instead. Changing `tool_choice` invalidates cached message blocks — [Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)

**Parallel tool use**
- [API] On by default; `disable_parallel_tool_use: true` lives inside `tool_choice` (with `auto`: at most one tool per response; with `any`/`tool`: exactly one). Return all `tool_result` blocks together in the next user message, before any text; separate user messages "teaches" Claude to avoid parallel calls. If you skip a call, still return a `tool_result` with `is_error: true` (e.g., "Not executed: the preceding write_file call failed."). Run independent read-only calls concurrently; tools with side effects or ordering needs sequentially — [Parallel tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use)
- [REC] Suggested system prompt: "For maximum efficiency, whenever you perform multiple independent operations, invoke all relevant tools simultaneously rather than sequentially. Prioritize calling tools in parallel whenever possible…" — [Parallel tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use)

**Tool results and errors**
- [API] `tool_result.content` may be a string or blocks of type `text`, `image`, `document`, `search_result`; `is_error: true` signals failure; tool_result blocks must immediately follow the tool_use turn and come first in the user message. "If a tool request is invalid or missing parameters, Claude will retry 2-3 times with corrections before apologizing to the user." — [Handle tool calls](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)

**Tool search and deferred loading**
- [API][DATA] "Claude's ability to pick the right tool degrades once you exceed 30–50 available tools." A GitHub+Slack+Sentry+Grafana+Splunk setup "can consume ~55k tokens in definitions"; tool search "typically reduces this by over 85 percent, loading only the 3–5 tools Claude needs" — [Tool search tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)
- [API] Variants `tool_search_tool_regex_20251119` (Python `re.search`, case-insensitive, max pattern 200 chars) and `tool_search_tool_bm25_20251119` (natural language, max 500 chars). Search covers tool names, descriptions, argument names and argument descriptions. Returns up to 5 `tool_reference`s by default (`limit` 1–10,000). Max 10,000 deferred tools per request. At least one tool must be non-deferred; a deferred tool can't carry `cache_control`. Deferred tools are excluded from the system-prompt prefix, so prompt caching is preserved. MCP connector: set `defer_loading` on the `mcp_toolset` `default_config` or per-tool `configs`. Custom search: return `tool_reference` blocks from your own tool — [Tool search tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)
- [REC] Use tool search when "You have 10 or more tools", definitions exceed 10k tokens, accuracy drops as the toolset grows, or "You aggregate multiple MCP servers (200+ tools)". Standard calling fits better with fewer than 10 tools, every tool used every request, or "less than 100 tokens total". "Keep your 3–5 most frequently used tools non-deferred"; prefix names (`github_`, `slack_`) "so one search matches the whole group"; "Use keywords in descriptions that match how users describe tasks"; add a system prompt line like "You can search for tools to interact with Slack, GitHub, and Jira."; "Monitor which tools Claude discovers to refine your descriptions." — [Tool search tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)
- [DATA] Internal MCP evals with tool search: Opus 4 49% → 74%, Opus 4.5 79.5% → 88.1%; ~77K → ~8.7K tokens before work begins (85% reduction); Anthropic saw definitions reach 134K tokens before optimization — [Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)

**Programmatic tool calling**
- [API][DATA] Add `code_execution_20250825` and set `"allowed_callers": ["code_execution_20250825"]` per tool; calls carry a `caller` field. Average tokens on complex research tasks 43,588 → 27,297 (37%); 20+ calls in one code block remove 19+ inference passes; internal knowledge retrieval 25.6% → 28.5%, GIA 46.5% → 51.2%. Best for large datasets needing aggregates, 3+ dependent calls, filtering before Claude sees data; not for single simple calls or when Claude must reason over every intermediate result. Opt in tools that are "parallel-safe or idempotent" — [Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)

**Token cost of tool definitions**
- [API] Billed input includes the `tools` parameter (names, descriptions, schemas), `tool_use` and `tool_result` blocks, plus a hidden tool-use system prompt: e.g., Claude Opus 5.5 286 tokens (auto/none), Claude Opus 5 286 (auto/none) / 406 (any/tool), Claude Sonnet 5 354 / 474, Claude Opus 4.7 675 / 804, Claude Haiku 5.5 286 / 406 — [Tool use overview](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)
- [API] Tool search is not metered separately; definitions it loads count as input tokens — [Tool search tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)

**Claude Code limits that bind MCP server authors**
- [API] Description truncation: "Server instructions, and the description of a tool that loads upfront: 4,096 characters"; "The description of a tool that Claude loads through tool search: 16,384 characters". "put critical details near the start"; search matching reads only the shorter-limit prefix, "so put the words Claude would search for near the start too." Before v2.1.296 the shorter limit was 2,048 characters. Override with `CLAUDE_CODE_MAX_MCP_DESCRIPTION_LENGTH` — [Claude Code MCP docs](https://code.claude.com/docs/en/mcp)
- [API] Tool search is on by default in Claude Code ("Only tool names and server instructions load at session start"); `ENABLE_TOOL_SEARCH=auto` defers once definitions reach 10% of context (`auto:N` for a custom %), `false` loads all upfront. "Claude Code doesn't impose a fixed per-server tool cap." Server authors can set `_meta["anthropic/alwaysLoad"]` per tool; users can set `alwaysLoad` per server. Server instructions should explain what category of tasks the tools handle, when to search for them and key capabilities — [Claude Code MCP docs](https://code.claude.com/docs/en/mcp)
- [API] Schema hygiene: root-level `anyOf`/`oneOf`/`allOf` are not accepted by the Claude API; Claude Code flattens them and prepends a sentence to the description ("keep validating the combination server-side"). Top-level property names must be 1–64 chars of ASCII letters, digits, `_`, `.`, `-`; schemas must validate against draft 2020-12; a full tool name (`mcp__<server>__<tool>`) over 128 chars is dropped. Plugin form: `mcp__plugin_<plugin-name>_<server-name>__<tool-name>` with chars outside `A-Za-z0-9_-` replaced by `_` — [Claude Code MCP docs](https://code.claude.com/docs/en/mcp)
- [API] `_meta["anthropic/requiresUserInteraction"]: true` forces a permission prompt on every call, even in `bypassPermissions`; no "don't ask again" — [Claude Code MCP docs](https://code.claude.com/docs/en/mcp)

### Inferences
- For Claude Code consumers, a tool's discoverable keywords must sit within the first 4,096 characters (upfront) and its essentials as early as possible; long descriptions are only safe for deferred tools.
- Because the newest Claude models reject forced `tool_choice`, tool designs that relied on forcing a specific tool now need either `strict` + `auto` with prompting, or structured outputs.
- `input_examples` and `strict` are Claude API features; an MCP server cannot set them through the MCP spec. Through MCP, the same information has to live in the description and JSON Schema (`enum`, `pattern`, `format`, `examples` keyword).

### Gaps
- The structured-outputs "JSON Schema limitations" page (unsupported keywords, limits on strict tools) was not fetched.
- The dedicated programmatic tool calling doc page was not fetched; current GA/beta status of PTC and `input_examples` beyond the Nov 2025 post is unverified.
- Whether Claude Code passes MCP JSON-Schema `examples` or `outputSchema` through to the model was not found.

## Q3. MCP specification (2026-07-28): tool fields, names, schemas, results, annotations, errors, pagination, progress, elicitation, resource links, recent changes

### Takeaway
The spec mandates little about tool design itself (names are SHOULD-level; schemas MUST be valid JSON Schema objects; output that declares `outputSchema` MUST conform) but is explicit on error placement (tool failures go in `isError: true` results so the model can self-correct), annotation defaults (destructive and open-world by default, and untrusted), deterministic tool ordering, and explicit state handles. The 2026-07-28 revision made MCP stateless and replaced server-initiated elicitation with multi round-trip `InputRequiredResult`.

### Cited Findings
**Tool definition fields**
- [SPEC] Tool = `name`, optional `title` (display), `description`, optional `icons`, `inputSchema`, optional `outputSchema`, optional `annotations`, `_meta`. Display name precedence: "`title`, `annotations.title`, then `name`." `description` "can be thought of like a "hint" to the model." — [MCP tools 2026-07-28](https://modelcontextprotocol.io/specification/latest/server/tools); [schema.ts](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/schema/2026-07-28/schema.ts)
- [SHOULD] Names: "Tool names **SHOULD** be between 1 and 128 characters in length (inclusive)"; "**SHOULD** be considered case-sensitive"; allowed chars A–Z, a–z, 0–9, `_`, `-`, `.`; "**SHOULD NOT** contain spaces, commas, or other special characters"; "**SHOULD** be unique within a server". Aggregating clients "**SHOULD** implement a disambiguation strategy such as prefixing tool names with a server identifier"; `serverInfo.name` "**SHOULD NOT** be relied upon for disambiguation" — [MCP tools](https://modelcontextprotocol.io/specification/latest/server/tools)
- [API] Conflict: MCP permits `.` in names, but the Claude API regex `^[a-zA-Z0-9_-]{1,128}$` does not. Claude Code documents replacing chars outside `A-Za-z0-9_-` with `_` in the plugin-bundled form `mcp__plugin_<plugin>_<server>__<tool>` (the rule for non-plugin tool names was not in the fetched text), and it drops any tool whose full `mcp__<server>__<tool>` name exceeds 128 chars — [Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools), [Claude Code MCP docs](https://code.claude.com/docs/en/mcp)
- [MUST] `inputSchema` "**MUST** be a valid JSON Schema object (not `null`)"; "`type: "object"` is required at the root"; defaults to JSON Schema 2020-12 when `$schema` is absent; any 2020-12 keyword allowed (composition, conditionals, `$ref`/`$defs`). No-parameter tools: `{ "type": "object", "additionalProperties": false }` is "**Recommended**" — [MCP tools](https://modelcontextprotocol.io/specification/latest/server/tools); [schema.ts](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/schema/2026-07-28/schema.ts)
- [MUST]/[SHOULD] Output schema: "Servers **MUST** provide structured results that conform to this schema. Clients **SHOULD** validate structured results against this schema." `structuredContent` may be any JSON value. "For backwards compatibility, a tool that returns structured content SHOULD also return the serialized JSON in a TextContent block." `structuredContent` "is unrelated to LLM "structured outputs"" — [MCP tools](https://modelcontextprotocol.io/specification/latest/server/tools)

**Result content types**
- [SPEC] `text`, `image` (base64 + mimeType), `audio`, `resource_link` (uri, name, description, mimeType), embedded `resource`. All support annotations (`audience`, `priority`, `lastModified`). "A tool **MAY** return links to Resources"; resource links "are not guaranteed to appear in the results of a `resources/list` request"; servers that embed resources "**SHOULD** implement the `resources` capability" — [MCP tools](https://modelcontextprotocol.io/specification/latest/server/tools)

**Annotations (verbatim from schema.ts)**
- [SPEC] "NOTE: all properties in `ToolAnnotations` are **hints**. They are not guaranteed to provide a faithful description of tool behavior (including descriptive properties like `title`). Clients should never make tool use decisions based on `ToolAnnotations` received from untrusted servers." — [schema.ts](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/schema/2026-07-28/schema.ts)
- [SPEC] `readOnlyHint`: "If true, the tool does not modify its environment. Default: false". `destructiveHint`: "If true, the tool may perform destructive updates… If false, the tool performs only additive updates. (This property is meaningful only when `readOnlyHint == false`) Default: true". `idempotentHint`: "If true, calling the tool repeatedly with the same arguments will have no additional effect… (meaningful only when `readOnlyHint == false`) Default: false". `openWorldHint`: "may interact with an "open world" of external entities… the world of a web search tool is open, whereas that of a memory tool is not. Default: true" — [schema.ts](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/schema/2026-07-28/schema.ts)
- [MUST] "clients **MUST** consider tool annotations to be untrusted unless they come from trusted servers." — [MCP tools](https://modelcontextprotocol.io/specification/latest/server/tools)

**Errors**
- [SHOULD] "Any errors that originate from the tool SHOULD be reported inside the result object, with `isError` set to true, _not_ as an MCP protocol-level error response. Otherwise, the LLM would not be able to see that an error occurred and self-correct. However, any errors in _finding_ the tool, an error indicating that the server does not support tool calls, or any other exceptional conditions, should be reported as an MCP error response." — [schema.ts CallToolResult](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/schema/2026-07-28/schema.ts)
- [SPEC] Protocol errors (JSON-RPC, e.g., `-32602 Unknown tool`): unknown tool, malformed requests, server errors. Tool execution errors (`isError: true`): API failures, "Input validation errors (e.g., date in wrong format, value out of range)", business-logic errors; example text "Invalid departure date: must be in the future. Current date is 08/08/2025." Clients "**MAY**" pass protocol errors to the model and "**SHOULD**" pass tool execution errors — [MCP tools](https://modelcontextprotocol.io/specification/latest/server/tools)

**Listing, ordering, caching, pagination, progress**
- [MUST] Servers with the `tools` capability "**MUST** respond to `tools/list`… but **MUST NOT** vary per-connection or as a side effect of other requests"; the set "**MAY** vary by the authorization presented on the request" — [MCP tools](https://modelcontextprotocol.io/specification/latest/server/tools)
- [SHOULD] "Servers **SHOULD** return tools in a deterministic order… improves LLM prompt cache hit rates" — [MCP tools](https://modelcontextprotocol.io/specification/latest/server/tools)
- [SPEC] `tools/list` supports pagination with an opaque `cursor`/`nextCursor`; results carry `ttlMs` and `cacheScope` (required since 2026-07-28 via `CacheableResult`) — [MCP tools](https://modelcontextprotocol.io/specification/latest/server/tools), [2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog); `Cursor` is "An opaque token used to represent a cursor for pagination" — [schema](https://modelcontextprotocol.io/specification/2026-07-28/schema)
- [SPEC] Progress: a request's `_meta.progressToken` asks for `notifications/progress`; "The receiver is not obligated to provide these notifications." Request-scoped notifications flow on that request's response stream — [schema](https://modelcontextprotocol.io/specification/2026-07-28/schema), [2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- [SHOULD] List-changed: servers that declared `listChanged` "**SHOULD** send" `notifications/tools/list_changed` to clients subscribed via `subscriptions/listen` — [MCP tools](https://modelcontextprotocol.io/specification/latest/server/tools)

**Elicitation / input during a tool call (MRTR)**
- [MAY] "Servers **MAY** respond to `tools/call` with an `InputRequiredResult`" (`resultType: "input_required"`, `inputRequests` such as `elicitation/create` form mode, optional `requestState`); the client retries with `inputResponses`; the retry's JSON-RPC `id` "**MUST** be different" — [MCP tools](https://modelcontextprotocol.io/specification/latest/server/tools)

**Stateful tools (non-normative guidance)**
- [REC] No protocol session exists, so return an explicit handle from a creation tool and accept it on later calls. Validate authorization against the handle on every call; use opaque, high-entropy handles; state the retention policy in the creation tool's description (e.g., "baskets expire after 24 hours of inactivity"); an expired handle should return a tool execution error saying so — [MCP tools](https://modelcontextprotocol.io/specification/latest/server/tools)

**Security section of the tools page**
- [MUST] Servers MUST "Validate all tool inputs", "Implement proper access controls", "Rate limit tool invocations", "Sanitize tool outputs". [SHOULD] Clients SHOULD prompt for confirmation on sensitive operations, show inputs before calling, validate results before passing to the LLM, implement timeouts, log usage. "there **SHOULD** always be a human in the loop with the ability to deny tool invocations." — [MCP tools](https://modelcontextprotocol.io/specification/latest/server/tools)
- [SHOULD] "Server developers **SHOULD NOT** mark sensitive parameters (passwords, API keys, tokens, PII) with `x-mcp-header`" — [MCP tools](https://modelcontextprotocol.io/specification/latest/server/tools)

### Inferences
- A server that wants clients to auto-approve read-only tools must set `readOnlyHint: true` explicitly; omitting annotations means clients see "may be destructive, open-world" by default.
- Returning input-validation failures as `isError: true` with a corrective message is now the normative route (since SEP-1303), not a JSON-RPC `-32602`.
- With sessions gone, any per-user state (jobs, carts, drafts) needs explicit handles, ownership checks and documented expiry in the creation tool's description.

## Q4. How many tools is too many? Evidence and mitigations

### Takeaway
Evidence agrees that accuracy falls and cost rises as the catalog grows: Anthropic puts the degradation point at 30–50 tools, OpenAI suggests fewer than 20 loaded at once, Google suggests 10–20; benchmarks show large drops (RAG-MCP baseline 13.62% selection accuracy; LongFuncEval 7–85% drops). Mitigations: defer and search (tool search, RAG over tool descriptions), consolidate, namespace, and move bulk data handling into code execution.

### Cited Findings
- [API][DATA] "Claude's ability to pick the right tool degrades once you exceed 30–50 available tools." — [Tool search tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)
- [DATA] Five-server setup = 58 tools ≈ 55K tokens (GitHub 35 tools ~26K, Slack 11 ~21K, Sentry 5 ~3K, Grafana 5 ~3K, Splunk 2 ~2K); Jira alone ~17K; definitions reached 134K tokens at Anthropic before optimization. Tool search: Opus 4 49% → 74%, Opus 4.5 79.5% → 88.1% — [Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)
- [DATA] RAG-MCP (Gan & Sun, arXiv 2505.03275, 6 May 2025): retrieving only the relevant MCP descriptions before the LLM call "significantly cuts prompt tokens (e.g., by over 50%) and more than triples tool selection accuracy (43.13% vs 13.62% baseline)"; uses an MCP stress test that varies the number of candidate tools — [arXiv](https://arxiv.org/abs/2505.03275)
- [DATA] LongFuncEval (arXiv 2505.10570): performance drops 7%–85% as the tool catalog grows, 7%–91% as tool responses get longer, 13%–40% as multi-turn conversations lengthen (from the abstract as summarized in search results; abstract page not opened directly) — [arXiv 2505.10570](https://arxiv.org/abs/2505.10570) (primary, not opened); figures seen via [fugumt summary](https://fugumt.com/fugumt/paper_check/2505.10570v1)
- [DATA] MCP-Bench (Accenture/UC Berkeley, arXiv 2508.20453; NeurIPS 2025): 28 live MCP servers, 250 tools; tasks rewritten into "fuzzy" variants without explicit tool names to test retrieval; across 20 LLMs, basic execution is robust but long-horizon planning, cross-domain orchestration and grounding remain hard (from search-result summaries) — [Hugging Face papers](https://huggingface.co/papers/2508.20453), [arXiv](https://arxiv.org/abs/2508.20453v1)
- [REC] OpenAI: "Aim for fewer than 20 functions available at the start of a turn at any one time, though this is just a soft suggestion." — [OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling)
- [REC] Google: "Keep active set to 10-20 tools maximum." — [Gemini function calling](https://ai.google.dev/gemini-api/docs/function-calling)
- [REC] Conflict on thresholds: Anthropic (degrades past 30–50; use search at ≥10 tools or >10k tokens) vs OpenAI (<20, soft) vs Google (10–20 max) — sources above.
- [REC] Mitigations (Anthropic): tool search with 3–5 hot tools non-deferred; consolidation into fewer tools with an `action` parameter; service prefixes; programmatic tool calling for large intermediate data; code-execution file tree with progressive disclosure — [Tool search tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool), [Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools), [Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use), [Code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp)
- [API] Claude Code defers all MCP tools by default and imposes no fixed per-server cap; the practical limit is context budget; `alwaysLoad` exempts a server or tool — [Claude Code MCP docs](https://code.claude.com/docs/en/mcp)
- [REC] OpenAI: use namespaces to group tools by domain and tool search (gpt-5.4+) to defer "large or infrequently used parts of your tool surface" — [OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling)

### Inferences
- With deferral on by default in Claude Code, the raw tool count matters less than (a) whether the right tool's name/description wins a regex/BM25 search and (b) overlap between near-duplicate tools. Distinct names, front-loaded keywords and good server instructions become the main levers.
- Splitting one large server into several smaller servers mostly helps when the client loads per-server (e.g., `alwaysLoad` per server); no source measured the effect of splitting by itself.

### Gaps
- No primary study isolates "split into multiple servers" vs "one consolidated server"; no source found.
- MCP-Bench's per-model accuracy numbers and LongFuncEval's exact catalog sizes were not extracted from the papers.
- No published threshold specific to Claude 5.x models; the 30–50 figure is undated guidance on the current docs page.

## Q5. Evaluating and iterating on tools

### Takeaway
Build realistic, multi-step tasks with verifiable answers, run them in a simple agent loop via the API, track accuracy plus runtime, tool-call count, tokens and tool errors, read transcripts (including what the agent did not do), let Claude refactor tools from concatenated transcripts, and confirm on a held-out set.

### Cited Findings
- [REC] Generate tasks grounded in real use with realistic data; strong tasks may need dozens of calls (e.g., "Customer ID 9182 reported that they were charged three times for a single purchase attempt."); weak tasks are narrow (e.g., "Search the payment logs for `purchase_complete` and `customer_id=9182`."). Pair each prompt with a verifiable outcome (exact match or Claude-as-judge); avoid over-strict verifiers; optionally record expected tool calls without overfitting to one strategy — [Writing tools](https://www.anthropic.com/engineering/writing-tools-for-agents)
- [REC] Run programmatically with a simple `while`-loop agent per task; ask agents for reasoning/feedback blocks before tool calls; interleaved thinking shows why tools were or weren't called. Track accuracy, runtime, total tool calls, token consumption, tool errors — [Writing tools](https://www.anthropic.com/engineering/writing-tools-for-agents)
- [REC] Diagnostics: many redundant calls → adjust pagination or token limits; many invalid-parameter errors → improve descriptions or examples; what agents omit can matter more than what they include — [Writing tools](https://www.anthropic.com/engineering/writing-tools-for-agents)
- [REC] Paste concatenated eval transcripts into Claude Code to analyze and refactor tools (keeping implementations and descriptions consistent); use held-out test sets to avoid overfitting; the post reports gains beyond expert-written tools — [Writing tools](https://www.anthropic.com/engineering/writing-tools-for-agents)
- [REC] Test how the model uses tools: run many example inputs, observe mistakes, iterate — [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- [REC] "Monitor which tools Claude discovers to refine your descriptions." — [Tool search tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)
- [LOCAL] `mcp-builder` eval spec: "Create 10 human-readable questions"; questions "READ-ONLY, INDEPENDENT, NON-DESTRUCTIVE" (and idempotent); each needs multiple, potentially dozens of, tool calls; "Answers must be VERIFIABLE via direct string comparison"; answers must not change over time (use "closed" concepts or fixed time windows); questions should avoid keywords from the target content. Quality is measured by "how well these implementations… enable LLMs with no other context and access ONLY to the MCP servers to answer realistic and difficult questions" — [mcp-builder evaluation.md](https://github.com/anthropics/skills/blob/main/skills/mcp-builder/reference/evaluation.md)
- [LOCAL] astra `tool-author`: at least 3 scenarios (happy path; destructive tool with weak anti-pattern expected to be flagged P0; ambiguous `get_x` vs `search_x` sibling pair) and a no-skill baseline run for comparison — `/Users/zeans/.claude/plugins/cache/astra/astra-methodology/5.25.0/skills/tool-author/references/evals.md`
- [REC] OpenAI: "Evaluate performance with different numbers of functions"; consider fine-tuning for large function counts — [OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling)
- [DATA] Benchmark designs worth copying: RAG-MCP's needle-in-a-haystack "MCP stress test" varying candidate tool count — [arXiv](https://arxiv.org/abs/2505.03275); MCP-Bench's fuzzy instructions without tool names — [Hugging Face papers](https://huggingface.co/papers/2508.20453)

### Inferences
- A practical metric set for this repo: task success, tool calls per task, input/output tokens per task, `isError` rate by tool, wrong-tool rate (from transcripts), and tool-search miss rate (searches that returned nothing or the wrong tool).
- Fuzzy prompts that never name a tool are the right test for deferred-loading clients, since the description must win the search.

### Gaps
- No public source gives target values (e.g., acceptable error rate or calls per task); thresholds would have to be set from a local baseline.
- Anthropic's internal eval harness code was not found; `mcp-builder/scripts/evaluation.py` exists but was not read.

## Q6. Security for tool authors

### Takeaway
Treat everything crossing the tool boundary as untrusted in both directions: descriptions can be poisoned (and changed after approval), results can carry prompt injection, annotations are hints only. Server-side duties are normative: validate inputs, enforce access control, rate limit, sanitize outputs, never pass through tokens not issued to you, never treat a state handle as authentication, minimize scopes, and keep a human able to deny destructive calls.

### Cited Findings
**Tool poisoning, rug pulls, shadowing**
- [DATA/REC] Invariant Labs (2025-04-01) defines Tool Poisoning as "malicious instructions are embedded within MCP tool descriptions that are invisible to users but visible to AI models." Example: an `add` tool whose `<IMPORTANT>` block tells the model to read `~/.cursor/mcp.json` and `~/.ssh/id_rsa` and pass them in a `sidenote` parameter. "a malicious server can change the tool description after the client has already approved it" (rug pull). Shadowing: a malicious server's description redirected emails sent via a trusted `send_email` tool to an attacker. Mitigations: show descriptions in UI and distinguish AI-visible text, pin server/tool versions and verify descriptions by hash, cross-server dataflow controls — [Invariant Labs](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks)
- [DATA] MCPTox (arXiv 2508.14925): 1,312 malicious cases on 45 live MCP servers / 353 tools, 20 LLM agents; highest attack success o1-mini 72.8%; average 36.5%; refusal rates low (highest, Claude-3.7-Sonnet, under 3%). Figures come from search-result summaries of the paper; per-model numbers on secondary sites (e.g., Polygraf, CSA) conflict and were not verified against the paper's tables — [arXiv](https://arxiv.org/abs/2508.14925v1)
- [REC] CyberArk argues the attack surface spans the whole schema ("Full-Schema Poisoning"), not only the description (secondary, from search summary) — [CyberArk](https://www.cyberark.com/resources/home/poison-everywhere-no-output-from-your-mcp-server-is-safe)

**Prompt injection via tool results**
- [REC] "Tool results often carry content from sources outside your control… Treat that content as untrusted… Keep untrusted content inside `tool_result` blocks rather than `system` prompts or plain user `text` blocks" — [Handle tool calls](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)
- [MUST] Servers MUST "Sanitize tool outputs"; clients SHOULD "Validate tool results before passing to LLM" — [MCP tools](https://modelcontextprotocol.io/specification/latest/server/tools)
- [REC] Code-execution pattern can tokenize PII so real values move between tools without entering model context — [Code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp)

**Confused deputy, token passthrough, handles, scopes**
- [MUST] MCP proxy servers "**MUST** implement per-client consent" before forwarding to third-party authorization (registry of approved `client_id`s per user, consent UI naming the client/scopes/redirect URI, CSRF protection, exact `redirect_uri` match, single-use `state`) — [MCP security best practices](https://modelcontextprotocol.io/specification/2026-07-28/basic/security_best_practices)
- [MUST NOT] "MCP servers **MUST NOT** accept any tokens that were not explicitly issued for the MCP server." Token passthrough "is explicitly forbidden" — [MCP security best practices](https://modelcontextprotocol.io/specification/2026-07-28/basic/security_best_practices)
- [MUST]/[SHOULD] State handles: servers "**MUST NOT** treat possession of a state handle as authentication"; "**SHOULD** use secure, non-deterministic handles"; "**SHOULD** bind handles server-side to the authenticated user" (e.g., key state as `<user_id>:<handle>` with user ID from the verified token) — [MCP security best practices](https://modelcontextprotocol.io/specification/2026-07-28/basic/security_best_practices)
- [REC] Scope minimization: minimal initial scope (e.g., `mcp:tools-basic`), incremental elevation via `WWW-Authenticate` scope challenges; common mistakes include wildcard/omnibus scopes and publishing every scope in `scopes_supported` — [MCP security best practices](https://modelcontextprotocol.io/specification/2026-07-28/basic/security_best_practices)
- [SHOULD] Local servers "**SHOULD**" use stdio to limit access to the client, or require an auth token / IPC with restricted access on HTTP; one-click local install "**MUST**" show the exact command and require explicit approval — [MCP security best practices](https://modelcontextprotocol.io/specification/2026-07-28/basic/security_best_practices)

**Destructive actions and confirmation**
- [SHOULD] Human in the loop able to deny invocations; confirmation prompts for sensitive operations — [MCP tools](https://modelcontextprotocol.io/specification/latest/server/tools)
- [SPEC] Annotations default to `destructiveHint: true`, `openWorldHint: true`; clients must not trust them from untrusted servers — [schema.ts](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/schema/2026-07-28/schema.ts)
- [API] Claude Code honors `_meta["anthropic/requiresUserInteraction"]: true` with a prompt on every call even in `bypassPermissions`; in `dontAsk` mode the call is denied — [Claude Code MCP docs](https://code.claude.com/docs/en/mcp)
- [LOCAL] astra `tool-author`: side-effect tools must start with a mutation verb (`Create`, `Update`, `Delete`, `Send`, `Charge`, `Publish`), name the read-only sibling in a "Do NOT use" clause, document the exact state change, and for irreversible effects add a confirmation step (MCP) or `disable-model-invocation: true` — `/Users/zeans/.claude/plugins/cache/astra/astra-methodology/5.25.0/skills/tool-author/SKILL.md` §6

**Input validation and secrets**
- [MUST] Servers MUST "Validate all tool inputs", "Implement proper access controls", "Rate limit tool invocations" — [MCP tools](https://modelcontextprotocol.io/specification/latest/server/tools)
- [REC] `mcp-builder`: API keys in env vars, never in code; sanitize file paths (directory traversal); validate URLs; prevent command injection; schema-validate all inputs (Pydantic/Zod); don't expose internal errors; for local streamable HTTP enable DNS-rebinding protection, validate `Origin`, bind to `127.0.0.1` — [mcp_best_practices.md](https://github.com/anthropics/skills/blob/main/skills/mcp-builder/reference/mcp_best_practices.md)
- [LOCAL] plugin-dev `mcp-integration`: use HTTPS/WSS; tokens via environment variables, documented in README, never hardcoded or committed; "Pre-allow specific tools, not wildcards, for security." — `/Users/zeans/.claude/plugins/cache/claude-plugins-official/plugin-dev/ea10b213686c/skills/mcp-integration/SKILL.md`
- [API] Strict tool schemas are cached up to 24h outside PHI protections; keep PHI out of names, enums, consts, patterns — [Strict tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/strict-tool-use)
- [SHOULD] No sensitive values in `x-mcp-header` parameters (visible to intermediaries) — [MCP tools](https://modelcontextprotocol.io/specification/latest/server/tools)

### Inferences
- For a first-party server, the author's own descriptions are the poisoning surface that matters least; the bigger exposures are tool results that relay third-party text (web pages, SNS comments, search results) into context, and over-broad credentials held by the server.
- Marking publish/spend tools with accurate annotations plus `anthropic/requiresUserInteraction` gives Claude Code users a hard confirmation step that does not depend on the model reading the description.

### Gaps
- No vendor-neutral standard for signing or pinning tool descriptions was found in the current MCP spec.
- The MCPTox paper's full tables were not read; per-model figures for current Claude models were not found.

## Q7. Other vendors' guidance (where it adds something)

### Takeaway
OpenAI and Google largely agree with Anthropic. OpenAI adds three useful ideas Anthropic states less directly: "offload" arguments your code already knows, make invalid states unrepresentable with enums/structure (least surprise, intern test), and an "allowed tools" subset to keep caches warm; it also warns that examples can hurt reasoning models.
