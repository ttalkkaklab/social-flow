# 정적 검사는 기준을 넘고 본문 크기와 행동 평가는 뒤처진다

스킬(SKILL.md)과 MCP 툴 작성 기준 가운데 규격이 실제로 강제하는 항목은 열댓 개다. 스킬 쪽은 `name` 64자·`description` 1,024자 같은 표준 제약과 Claude Code의 동작(설명 1,536자 절단, 로드된 본문의 세션 내 잔류, 컴팩션 뒤 스킬마다 앞 5,000토큰만 재부착)이다. 툴 쪽은 `inputSchema` 유효성, 도구 오류를 `isError` 결과로 돌려주기, 주석은 신뢰할 수 없는 힌트라는 MCP 규정이다. 트리거 키워드를 앞에 둔 3인칭 설명, 본문 500줄·참조 1단계, 부작용 스킬의 자동 호출 차단, 매번 지켜야 할 규칙의 훅 이전, 소수의 워크플로형 툴, 다음 행동을 알려 주는 오류, 작성 전 eval 같은 나머지는 벤더 권고다. 이를 받치는 측정은 얇고 소스끼리 자주 부딪친다. 현장 측정이 되풀이해 보여 주는 실패는 두 가지로, 스킬은 기본 상태에서 절반 남짓만 자동 호출되고(Sonnet 4.5 실바이너리 50–55%) 툴은 수십 개를 넘기면 선택 정확도가 떨어진다. social-flow는 결정적 표면에서 이 기준을 대체로 넘어선다. `skill-lint.js` 16개 규칙은 위반 0건이고 툴 104개 전부에 `title`·`annotations`가 있으며 인자 검증 실패는 스펙 권고대로 `isError` 결과로 돌아간다. 어긋나는 곳은 크기와 층위와 측정이다. `produce` 본문 1,341줄과 2단계 이상 참조 트리, 날짜를 박은 "supersedes … below" 지시의 누적, 약 45.8만 자 툴 정의와 서버 `instructions` 부재, `disable-model-invocation`을 쓰는 스킬 0개, 플러그인 설치 환경의 툴 이름과 어긋날 수 있는 `allowed-tools` 접두, 그리고 트리거율이나 스킬 유무 차이를 재는 실행 가능한 eval이 하나도 없다는 점이다. 그래서 다음 작업은 규칙을 더 쓰는 일보다 이미 있는 규칙을 호스트가 실제로 읽는 자리(컴팩션 뒤 앞 5,000토큰, 세션 시작 때의 서버 instructions, 권한 프롬프트 플래그)로 옮기고 그 효과를 `claude plugin eval`로 재는 일이다.

## 하드 리밋은 열댓 개이고 나머지는 서로 부딪치는 권고다

이 보고서는 근거마다 꼬리표를 붙인다. [표준]은 agentskills.io 명세와 MCP 스펙(2026-07-28 개정)의 규범 문구, [플랫폼]은 Claude API·Claude Code 문서가 밝힌 동작과 한도, [측정]은 실험·스캔·벤치마크 수치, [권고]는 벤더가 데이터 없이 내놓은 지침, [일화]는 이슈 보고와 개인 관찰, [의견]은 개인 논자의 주장이다. 검색 요약으로만 확인된 수치에는 "1차 미확인"을 붙였다. 이 보고서가 저장소 수치에서 끌어낸 판단은 [추정]으로 적었다. 저장소 근거는 URL 대신 `파일:줄`로 표기한다. 로컬 플러그인 캐시 문서는 경로를 줄여 적었다. `superpowers/7.0.0/…`은 `/Users/zeans/.claude/plugins/cache/claude-plugins-official/superpowers/7.0.0/…`, `astra-methodology/5.25.0/…`은 `/Users/zeans/.claude/plugins/cache/astra/astra-methodology/5.25.0/…`이다.

스킬의 하드 리밋은 짧다. [표준] `name`은 필수이고 64자 이하의 소문자·숫자·하이픈이어야 하며 상위 디렉터리 이름과 같아야 한다. `description`도 필수이고 1,024자를 넘을 수 없다 ([Agent Skills Specification](https://agentskills.io/specification)). [플랫폼] claude.ai 업로드·Skills API·`package_skill.py`는 표준 여섯 필드(`name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools`) 밖의 키를 하드 에러로 거부하지만 Claude Code는 모르는 필드를 오류 없이 무시한다. YAML 파싱에 실패하면 Claude Code는 필드 없이 스킬을 로드한다. 같은 문서에 따르면 **`description`과 `when_to_use`는 합산 1,536자에서 잘리고**, 스킬 목록 예산은 컨텍스트 창의 1%이며 넘치면 덜 쓰는 스킬부터 설명을 뺀다. 로드된 SKILL.md는 다시 읽히지 않은 채 이후 턴에 계속 머문다. **컴팩션 뒤에는 스킬마다 앞 5,000토큰만 다시 붙는다**(합산 25,000토큰). `allowed-tools`는 그 턴의 사전 승인일 뿐 "every tool remains callable"이다 ([Claude Code: skills](https://code.claude.com/docs/en/skills)).

툴 쪽도 비슷하다. [표준] MCP 스펙은 `inputSchema`가 루트 `type: "object"`를 가진 유효한 JSON Schema여야 한다고 못 박는다(MUST). `outputSchema`를 선언했다면 결과가 그 스키마를 따라야 한다(MUST). 도구 실행 중 난 오류는 프로토콜 오류 대신 `isError: true` 결과로 돌려줘야 하며(SHOULD) 그래야 모델이 오류를 보고 스스로 고칠 수 있다. 2025-11-25 개정부터는 입력 검증 오류도 이 경로다(SEP-1303). 주석은 모두 힌트이고 기본값은 `readOnlyHint: false`, `destructiveHint: true`, `openWorldHint: true`다. 클라이언트는 신뢰할 수 없는 서버의 주석을 믿으면 안 되고(MUST) 서버는 입력 검증·접근 제어·속도 제한·출력 정화를 해야 한다(MUST) ([MCP tools](https://modelcontextprotocol.io/specification/latest/server/tools), [schema.ts](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/schema/2026-07-28/schema.ts), [2025-11-25 changelog](https://modelcontextprotocol.io/specification/2025-11-25/changelog)). [플랫폼] Claude API의 툴 이름 정규식 `^[a-zA-Z0-9_-]{1,128}$`은 MCP가 허용하는 `.`을 받지 않는다 ([Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)). Claude Code는 처음부터 로드되는 툴 설명과 서버 instructions를 **4,096자에서 자르고**(툴 검색으로 불러오는 툴은 16,384자) 검색 매칭도 짧은 쪽 접두만 본다. MCP 출력이 10,000토큰을 넘으면 경고하고 기본 25,000토큰에서 자른다. `isError` 텍스트가 약 11,000자를 넘으면 앞뒤 5,000자씩만 모델에 보인다. 툴 검색은 기본으로 켜져 있어 "Only tool names and server instructions load at session start"이다 ([Claude Code: MCP](https://code.claude.com/docs/en/mcp)).

그 밖의 거의 모든 지침은 [권고]이고 측정은 얇다. 500줄·5,000토큰 기준의 실험 근거나 description 문장 형태와 트리거율의 관계를 잰 공개 자료는 찾지 못했다. 소스끼리 정면으로 부딪치는 지점을 아래 표에 모았다. 마지막 열은 이 보고서가 저장소에 적용할 때 택한 판단이다.

## 설명문 21개는 형식을 지키지만 호출을 통제하는 장치는 비어 있다

모든 소스가 동의하는 최소 공통분모는 네 가지다. 1인칭을 쓰지 않는다. 핵심 용례와 트리거 키워드를 첫 문장에 둔다. 사용자가 실제로 쓰는 말(확장자, 오류 문구, 동의어)을 넣는다. 1,024자 안에서 짧게 쓴다 [권고] ([Platform BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), [agentskills.io](https://agentskills.io/skill-creation/optimizing-descriptions)). 이 권고가 겨냥하는 실패는 현장에서 가장 자주 잰 under-triggering이다. Vercel의 Next.js 16 eval에서 스킬은 **56%의 케이스에서 한 번도 호출되지 않았다**. 기본 스킬 통과율 53%는 스킬 없는 기준선 53%와 같았고 명시 지시를 더하자 79%, AGENTS.md 압축 색인은 100%였다 [측정, 표본·분산 비공개] ([Vercel](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)). Scott Spence가 실제 `claude -p` 바이너리와 Sonnet 4.5로 22개 프롬프트를 두 번씩 돌린 실험에서 훅 없는 호출률은 **55%/50%**, 스킬별 YES/NO 판정을 강제하는 UserPromptSubmit 훅은 100%/100%였다. 더 어려운 24개 프롬프트에서도 이 훅은 75%에 오탐 0건이었다. 문구만 주입하는 훅은 훅이 없을 때보다 나아지지 않았다 [측정, SvelteKit 단일 도메인] ([Spence 2026](https://scottspence.com/posts/measuring-claude-code-skill-activation-with-sandboxed-evals)). Anthropic은 skill-creator의 설명 최적화 루프로 공개 문서 스킬 6개 중 5개의 트리거가 나아졌다고 밝혔지만 전후 수치는 내놓지 않았다 [측정, 효과 크기 비공개] ([skill-creator blog](https://claude.com/blog/improving-skill-creator-test-measure-and-refine-agent-skills)). Claude Code 이슈 트래커에는 "BLOCKING REQUIREMENT"라고 적어도 Skill 툴을 건너뛴다는 보고가 있다 [일화] ([#19308](https://claudeissues.com/issue/19308-critical-claude-systematically-ignores-skill-tool-despite-explicit-blocking-requ)). 반대 방향의 경고도 있다. Anthropic 프롬프팅 가이드는 Opus 4.5·4.6이 "CRITICAL: You MUST use this tool when…" 같은 문구에 과잉 트리거하므로 평범한 "Use this tool when…"으로 낮추라고 적는다 [권고] ([prompting BP](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)).

social-flow의 description은 이 공통분모를 충실히 따른다. 21개 모두 3인칭 동사로 시작하는 정체 요약, `Use when`(한 개는 `Use for`) 트리거 문장, 워크플로와 경계 설명의 3단 구조다. **최대 787자(중앙값 588자)**라 1,024자 상한과 1,536자 절단선 모두 여유가 있다. 한국어 트리거 문구는 따옴표로 3–9개씩 들어가 사용자가 실제로 칠 말을 담는다. `produce`·`storyboard`·`autoproduce`는 형제 스킬과의 경계를 description에 직접 적는다(`skills/produce/SKILL.md:3-4`의 "Boundary — storyboard plans and stops for approval, produce starts after it, autoproduce runs both unattended"). 인접 기능과의 경계를 밝히라는 agentskills.io 권고와 같은 방향이다. `skill-lint.js`는 description 첫 76자가 스킬마다 달라야 한다는 규칙을 CI에서 강제한다. codex-cli 0.149.1이 description을 약 76자에서 자른다는 저장소 자체 측정이 근거다(`skills/platform-guide/references/skill-lint.js:10-15,41`). 설명이 줄어도 호스트가 매칭할 수 있게 핵심 용례를 앞에 두라는 Codex 문서 권고를 측정값으로 구체화한 사례다 ([Codex skills](https://developers.openai.com/codex/skills)).

위험은 두 군데다. 첫째, description 글자의 **약 60%가 트리거 문장 뒤의 워크플로 요약**이다(정체 요약 13%, 트리거 문장 26%). 공식 "what + when"과 충돌하지는 않지만 superpowers가 경고하는 실패, 즉 절차를 요약한 description이 지름길이 되어 에이전트가 본문을 건너뛴다는 관찰과 겹친다 [일화, 공개 데이터 없음] (`superpowers/7.0.0/skills/writing-skills/SKILL.md:154`). 저장소에는 이를 확인할 데이터가 없다. 둘째, 목록 예산이다 [추정]. 21개 description 합계는 12,234자이고 4자≈1토큰으로 환산하면 약 3,000토큰이다. 컨텍스트 20만 토큰 모델이라면 1% 예산은 약 2,000토큰이라 social-flow 하나로 이미 넘칠 수 있다. 다만 예산의 단위(토큰인지 글자인지)가 문서에 명시되지 않아 이 환산은 참고용이다. 이 세션처럼 다른 플러그인 스킬 수십 개가 함께 깔린 환경에선 덜 쓰는 스킬의 설명부터 빠진다. Claude Code 문서는 이 현상이 "removes the keywords Claude needs to match your request"라고 적는다 ([CC skills](https://code.claude.com/docs/en/skills)). 이 손실은 오류 없이 under-trigger로만 드러나므로 `/skill-doctor`로 스킬별 비용과 사용 빈도를 실측하는 일이 먼저다.

문구 드리프트도 하나 보인다. `grow-threads` description은 "Every outgoing text clears the configured review gates (zero P0) before it goes out"이라고 적는데(`skills/grow-threads/SKILL.md:9-11`) CLAUDE.md의 2026-10-16 지침은 리뷰 점수가 "belong primarily in skills as guidance, not automatic execution gates"라고 정했다(`CLAUDE.md:5-12`). 본문까지 대조하지 않아 실제 동작 차이인지 문구가 덜 갱신된 것인지는 확인하지 못했다. description은 매 턴 컨텍스트에 실리는 텍스트라 본문보다 먼저 맞출 자리다.

호출 통제 필드는 하나도 쓰지 않는다. 21개 스킬 어디에도 `when_to_use`, `disable-model-invocation`, `user-invocable`, `paths`, `context`가 없다. Claude Code 문서는 부작용이 있는 워크플로에 `disable-model-invocation: true`를 권하며 "You don't want Claude deciding to deploy because your code looks ready"라고 설명한다 [권고]. 이 필드는 description을 컨텍스트에서 빼므로 목록 예산도 아낀다 [플랫폼] ([CC skills](https://code.claude.com/docs/en/skills)). 저장소의 부작용은 즉시 공개되는 SNS 게시(`publish`, `grow-*`)와 유료 생성(`produce`, `autoproduce`)이다. 저장소는 이 필드 대신 세 가지에 기댄다. 서버 주석의 `destructiveHint`, `publish`가 게시 툴을 일부러 사전 승인에서 빼고 "the native permission prompt on every irreversible publish call has to act as a second line of defense"로 삼는 방식(`skills/publish/SKILL.md:11-13`), 그리고 `grow-*`의 growth-plan.md 상시 승인이다. 모든 스킬에 이 필드를 거는 것은 답이 아니다. 이 필드는 Claude가 스킬을 부르는 것 자체를 막으므로 `storyboard`가 `produce`로 넘기는 식의 연쇄를 끊을 수 있다. 문서상 scheduled task 실행도 막으므로 `/loop`로 도는 `grow-*`와의 상호작용은 먼저 확인해야 한다. 가장 깔끔한 후보는 사용자가 직접 부르고 비가역 결과를 내는 `publish`다. `platform-guide`처럼 "Knowledge only, nothing runs"인 스킬은 `/` 메뉴에서 숨기는 `user-invocable: false` 후보다(description은 계속 컨텍스트에 실린다).

`allowed-tools` 접두는 확인이 필요한 위험이다. 저장소 스킬은 `mcp__social-flow__project_manage` 형태로 툴을 적고(`skills/publish/SKILL.md:14`) `skill-lint.js`는 이 접두만 허용한다(`skill-lint.js:47`). 그런데 Claude Code 문서가 밝힌 플러그인 번들 MCP 툴 이름 형식은 `mcp__plugin_<plugin-name>_<server-name>__<tool-name>`이다 [플랫폼] ([CC MCP](https://code.claude.com/docs/en/mcp)). 이 세션에서도 툴은 `mcp__plugin_social-flow_social-flow__*`로 노출됐다. Claude Code가 플러그인 스킬의 `allowed-tools`를 이 형식으로 다시 매핑하는지는 문서에서도 조사 노트에서도 찾지 못했다. 매핑이 없다면 플러그인 설치본에서는 사전 승인이 하나도 맞지 않는다. 그러면 `publish`의 의도적 비승인과 `grow-*`의 의도적 승인이 같은 결과가 되어 기본 권한 모드에서 `grow-*`의 게시도 매번 프롬프트를 띄운다. 저장소는 이미 `allowed-tools`가 권고일 뿐이고 맞지 않는 이름은 "is not refused, it is ignored"라고 직접 측정해 적었다(`skill-lint.js:17-22`). 접두가 틀려도 아무 오류가 나지 않는 구조이고 접두만 보는 skill-lint 6번은 어느 쪽이든 통과한다. 플러그인 설치본에서 `grow-threads` 한 틱을 돌려 게시 툴이 프롬프트 없이 불리는지 한 번 보면 결론이 난다.

## produce 1,341줄 가운데 컴팩션 뒤 살아남는 것은 앞 5,000토큰이다

[권고] 공식 기준은 SKILL.md 본문 500줄 미만, 지시 5,000토큰 미만, 상세 자료는 별도 파일, 참조는 SKILL.md에서 한 단계, 100줄 넘는 참조 파일에는 목차다. 한 단계 규칙의 근거는 중첩 참조를 만나면 Claude가 `head -100`으로 일부만 미리 볼 수 있다는 관찰이다 ([Platform BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)). 시간 조건이 붙은 지시("If you're doing this before August 2025, use the old API")는 안티패턴이다. 처방은 현재 방법만 본문에 두고 옛 방식은 "Old patterns" 아래 `<details>`로 접는 것이다. 이 기준들의 실험 근거는 공개되지 않았다. 간접 근거로는 IFScale이 있다. 지시 500개를 동시에 줬을 때 최고 모델이 약 68%를 지켰고 claude-sonnet-4는 지시 수에 따라 선형으로 떨어졌으며 모델들은 앞쪽 지시를 선호했다 [측정, 키워드 포함 과제, 1차 미확인 요약] ([IFScale](https://arxiv.org/html/2507.11538v1)). Claude Code 문서도 "If you emphasize many lines, none of them stands out"이라고 적는다 [권고] ([CC best practices](https://code.claude.com/docs/en/best-practices)).

대부분의 스킬은 이 기준 안에 있다. 본문 중앙값은 192줄이다. 문제는 500줄을 넘는 네 개(`produce` 1,341, `grow-threads` 653, `grow-youtube` 515, `publish` 508)가 **전체 본문 6,045줄의 약 절반**을 차지한다는 점이다. `produce`는 16,758단어로 단순 환산하면 2만 토큰 안팎이고 [추정] 공식 5,000토큰의 네 배쯤이다. `skill-lint.js`의 상한 1,350줄은 사실상 `produce`에 맞춘 값이라 지금 여유가 10줄이 채 안 된다. 저장소의 반론도 적혀 있다. lint 주석은 "most of what they carry runs on every episode — moving that to a reference costs an extra read and saves nothing"이라며 공통 경로를 일부러 인라인에 뒀다고 설명한다(`skill-lint.js:49-56`).

그 논리는 컴팩션과 부딪친다 [추정]. 영상 한 편을 만드는 세션은 길어서 컴팩션이 일어날 가능성이 높다. 그때 Claude Code는 스킬마다 앞 5,000토큰만 다시 붙이므로 줄당 평균 단어 수로 환산하면 `produce`는 대략 앞 300줄만 돌아온다. 번호 붙은 "Absolute rules"(67–192행)는 그 안에 들지만 그 규칙을 "absolute rule 13" 식으로 다시 부르는 후반부 절차(300·337·459·680·700·1160행)는 빠진다(`skills/produce/SKILL.md`). "매 에피소드 쓰는 내용이라 인라인"이라는 이유가 긴 세션에서는 오히려 그 내용을 잃게 만든다. Claude Code 문서가 제시하는 대응도 "put the most important instructions near the top of `SKILL.md`"다 ([CC skills](https://code.claude.com/docs/en/skills)).

앞 5,000토큰이 가장 귀한 자리인데 그 자리를 날짜 지시가 채운다. `produce`는 H1보다 앞에 19줄짜리 서문을 둔다. 서문은 거의 매 줄 다른 문서를 링크한다(`skills/produce/SKILL.md:8-26`). 그 바로 뒤에 "Owner directive (2026-10-17): every delivered video is subtitle-free … This supersedes older burned-subtitle exceptions and rendering recipes below"가 온다(`skills/produce/SKILL.md:28-30`). `produce` 본문에는 ISO 날짜가 27개 있다. "supersede" 문구는 SKILL.md 18개에 나온다. 공식 문서가 안티패턴으로 꼽은 형태 그대로다. 새 지시는 위에 얹히고 대체된 옛 지시는 아래에 그대로 있어서 모델은 매번 두 층을 맞춰 읽어야 하고 옛 지시도 토큰을 차지한다. 참조 트리에서도 같은 일이 보인다. 가장 큰 참조 문서 다섯 개 가운데 세 개가 `legacy-*`(`storyboard/references/legacy-reviewer.md` 1,601줄, `storyboard/references/legacy-authoring.md` 1,350줄, `autoproduce/references/legacy-unattended.md` 1,029줄)다. 저장소의 CLAUDE.md도 312줄로 Claude Code가 권하는 200줄을 넘고 ([CC best practices](https://code.claude.com/docs/en/best-practices)) 섹션마다 날짜와 "supersedes"·"replaces"가 붙는다.

지시를 SKILL.md에 둔 위치 자체는 맞다. 플러그인 루트의 CLAUDE.md는 플러그인 사용자에게 컨텍스트로 로드되지 않으므로 사용자에게 닿아야 할 지시는 스킬에 있어야 한다 [플랫폼] ([CC plugins reference](https://code.claude.com/docs/en/plugins-reference)). 저장소는 SKILL.md 20개가 `_shared/automation-guidance.md`를 링크하고 서문에 소유자 지시를 옮겨 적는 방식으로 이를 지킨다. 고칠 것은 형태다. 날짜별 덧씌우기를 현재 계약 한 벌로 접고 옛 계약은 `legacy-*` 파일이나 Old patterns 블록으로 내리면 같은 정보로 앞 5,000토큰을 비울 수 있다. 대문자 MUST/NEVER/ALWAYS가 SKILL.md에 한 번도 없다는 점은 Opus 4.5·4.6의 과잉 반응 경고와 맞는다. 다만 `produce`의 번호 규칙 16개와 그 앞 단락 7개, 소문자 `never` 32회·`do not` 46회는 "많은 줄을 강조하면 어느 것도 두드러지지 않는다"는 같은 문제를 섹션 제목으로 재현한다 [추정].

참조 깊이는 공식 권고와 가장 멀다. `produce`는 서로 다른 .md 링크 54개 가운데 **27개가 다른 스킬의 문서**다. 행동 전에 먼저 읽으라는 문서도 5개다(`automation-guidance.md`, `character-scenarios.md`, `production-mode.md`, `model-settings.md`, `cinematic-edit.md`). 링크된 자기 참조 가운데 `produce`는 19개 중 11개, `storyboard`는 18개 중 11개가 다시 다른 .md를 링크해 트리가 2단계 이상이다. `storyboard`의 참조 .md 49개 중 21개는 SKILL.md에 이름조차 없다. 저장소 lint의 고아 검사(12번)는 basename이 어디서든 언급되면 통과하고 ASTRA 5번은 `](references/` 문자열만 보므로 둘 다 깊이를 잡지 못한다. 반면 100줄 넘는 참조의 `## Contents` 존재는 skill-lint 10번이 공식 기준(100줄) 그대로 강제한다.

디렉터리 배치는 우선순위가 낮다. 코드 파일 142개는 전부 `references/` 안에 있고 `scripts/` 디렉터리는 0개이며 7.8MB짜리 폰트 같은 비문서 파일도 `references/`에 섞여 있다. 표준은 `scripts/`(실행 코드), `references/`(필요할 때 읽는 문서), `assets/`(템플릿·데이터)를 선택 디렉터리로 정의한다 ([Spec](https://agentskills.io/specification)). 실익은 폴더 이름보다 호출 방식에 있다. 스크립트는 실행하면 출력만 컨텍스트를 쓰고 코드 자체는 로드되지 않는다 [플랫폼] ([Platform overview](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)). 그래서 SKILL.md가 각 파일을 "Run `x.py`"(실행)로 부르는지 "See `x.py`"(참조)로 부르는지 문장으로 구분하는 쪽이 효과가 크다 [권고] ([Platform BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)).

## 툴 104개는 위생 테스트를 통과하지만 45만 자 정의를 이름만 보고 고르게 한다

[권고] Anthropic의 툴 설계 지침은 다섯 가지로 요약된다. 엔드포인트를 감싼 툴보다 고영향 워크플로를 겨냥한 소수의 툴, 서비스·리소스 접두로 묶은 이름, UUID보다 의미 있는 필드를 돌려주는 응답과 `response_format` 손잡이, 기본값과 안내가 붙은 페이지·필터·절단, 그리고 다음에 할 일을 알려 주는 오류다 ([Writing tools](https://www.anthropic.com/engineering/writing-tools-for-agents)). Claude API 문서는 상세한 description을 "by far the most important factor in tool performance"라고 부르고 툴마다 최소 3–4문장을 권하며 관련 동작은 `action` 파라미터로 묶으라고 한다 ([Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)). 측정도 몇 개 있다. Slack 예시에서 간결 응답은 72토큰으로 상세 응답 206토큰의 약 3분의 1이었다 [측정] ([Writing tools](https://www.anthropic.com/engineering/writing-tools-for-agents)). 사용 예시를 붙이자 복잡한 파라미터 처리 정확도가 72%에서 90%로 올랐다 [측정, 내부 테스트] ([Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)).

툴 수는 선택 정확도와 직결된다. Claude 문서는 "Claude's ability to pick the right tool degrades once you exceed 30–50 available tools"라고 적는다. 툴 검색은 Anthropic 내부 MCP eval에서 **Opus 4를 49%에서 74%로, Opus 4.5를 79.5%에서 88.1%로** 올리면서 사전 정의 토큰을 약 77K에서 8.7K로 줄였다 [측정, Anthropic 내부] ([Tool search](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool), [Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)). 외부 측정도 같은 방향이다. RAG-MCP는 관련 툴 설명만 골라 넣자 선택 정확도가 13.62%에서 43.13%로 세 배 넘게 올랐다고 보고했다 [측정] ([RAG-MCP](https://arxiv.org/abs/2505.03275)). Microsoft Research의 MCP 서버 1,470개 조사에선 **툴 775개가 이름 충돌**을 일으켰고("search"는 32개 서버) 오류 플래그 없는 결과 5,983개 중 3,536개가 실제로는 오류 내용이었다 [측정] ([Microsoft Research](https://www.microsoft.com/en-us/research/blog/tool-space-interference-in-the-mcp-era-designing-for-agent-compatibility-at-scale)). Anthropic이 꼽은 툴 검색의 주된 실패도 이름이 비슷한 툴 사이의 혼동이었다 ([Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)).

이 서버는 툴 위생에서 권고를 대부분 지킨다. 104개 전부에 `title`과 `annotations`가 있고 힌트 조합은 프리셋 6종으로 관리된다(`server/src/tools.ts:583-595`). 즉시 공개되는 게시 툴 6개는 `destructiveHint: true`다. 저장소는 그 이유를 "the description prose reaches only the model, never the approval UI"라고 주석에 적어 두었다(`server/src/tools.ts:165-169`). description 문구는 모델에게만 닿고 주석은 승인 UI에 닿는다는 정확한 이해다. 인자 검증 실패는 zod 이슈를 `path: message`로 잇고 알 수 없는 키를 허용 키 목록과 함께 거부한 뒤 `isError` 결과로 돌려준다(`server/src/handlers.ts:171-189`). 알 수 없는 툴만 -32602 프로토콜 오류로 보낸다(`server/src/index.ts:47-49`). SEP-1303 이후 스펙이 그은 선과 같다. 페이지 인자 이름은 서버 전체에서 통일하도록 테스트가 강제한다(`server/test/contract.test.mjs:215`). data.go.kr 응답은 12,000자에서 자르면서 "lower limit, or use page"로 다음 행동을 안내한다(`server/src/datago-client.ts:446,491`). `storyboard_read`의 `level=outline|full`은 `response_format`과 같은 역할을 한다. `action`·`operation` 같은 enum으로 동작을 고르는 다중 동작 툴도 11개다. description 길이 중앙값 966자는 3–4문장 기준을 넘고 최대 3,743자(`astra_audio2video`)도 4,096자 절단선 안이다. ASTRA `tool-author`의 5줄 상한으로 보면 대부분이 걸리지만 그 상한은 내부 교훈이 출처인 로컬 규칙이라 공식 기준보다 앞설 이유가 없다. 과금을 스킬 대신 서버 한 곳에서 성공·실패 모두 원장에 기록하는 구조(`server/src/index.ts:66-103`)와 자격 증명이 없는 플랫폼의 게시·인사이트 툴을 ListTools에서 숨기는 게이트(`server/src/index.ts:24-42`)도 표면을 줄이는 좋은 장치다.

어긋나는 곳은 표면의 크기와 첫인상이다. 툴 정의 JSON은 합계 **458,145자**로 4자≈1토큰 단순 환산이면 약 11.5만 토큰이다 [추정, 한글 섞인 JSON이라 실제 토크나이저 값과 다를 수 있음]. Anthropic이 최적화 전 내부에서 봤다는 134K 토큰에 가까운 규모다 ([Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)). Claude Code는 툴 검색이 기본이라 이 정의를 한꺼번에 싣지 않고 세션 시작 때 툴 이름과 서버 instructions만 싣는다 [플랫폼]. 그런데 이 서버는 `new Server({ name: 'social-flow', version: '0.116.0' }, { capabilities: { tools: {} } })`로 만들어져 **instructions가 없다**(`server/src/index.ts:19-22`, 이 보고서가 직접 확인). Claude Code 문서는 서버 instructions에 툴이 다루는 작업 범주, 언제 검색할지, 핵심 기능을 적으라고 권한다 [권고] ([CC MCP](https://code.claude.com/docs/en/mcp)). 지금 모델은 세션을 시작할 때 맥락 없는 이름 104개만 보고 무엇을 검색할지 정한다.

이름이 그 부담을 덜어 주지 못한다. 접두가 공급자(`veo`, `seedance`, `suno`, `astra`, `omni`, `mlx`)와 도메인(`storyboard`, `speech`, `project`)을 섞는다. 툴 하나뿐인 접두도 14종이다. 이미지에서 영상을 만드는 일 하나가 `veo_img2video`, `seedance_img2video`, `astra_img2video`, `omni_img2video`, `mlx_video_generate`로 흩어져 있어 "사람 엔지니어도 어느 툴을 쓸지 단정하지 못하면 에이전트도 못 한다"는 경고에 그대로 해당한다 [권고] ([Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). 워크트리에 있는 `video_plan`(`operation` enum) 같은 라우팅 툴은 통합 방향이지만 이 세션의 설치본 툴 목록에는 아직 보이지 않았다. 어느 스킬의 `allowed-tools`에도 없는 툴이 25개(`blender_*` 7개, `omni_*` 4개, `tts_generate_checked`, `tts_review_final`, `tts_route` 등)인데 이 중 게시 툴 일부는 의도적 제외다. 나머지는 퇴역시키거나 이미 있는 `disabled-tools.json`·`SOCIAL_FLOW_*` 게이트(`server/src/tool-gate.ts`)로 기본 비활성화할 후보다. 듣기·채점 게이트를 걷어 낸 2026-10-16 음성 지침 이후에도 `tts_generate_checked`·`tts_review_final`이 노출돼 있다는 점이 특히 눈에 띈다 [추정]. 스키마 하나가 표면의 큰 몫을 차지하기도 한다. `storyboard_apply`의 inputSchema는 68,613자로 전체 inputSchema의 약 22%다. 툴 검색으로 불려 오는 순간 이 툴 하나가 단순 환산 1.7만 토큰을 쓰고 [추정], 지연 로딩이 없는 클라이언트라면 11.5만 토큰 전체가 실린다.

오류 본문은 권고와 어긋난다. 외부 API 실패는 `fromApi`에서 `HTTP ${result.status}\n${result.body}`로 원본 본문을 그대로 돌려준다(`server/src/handlers.ts:137-139`). Anthropic은 불투명한 오류 코드나 트레이스백 대신 구체적 해결책을 담으라고 권한다 [권고] ([Writing tools](https://www.anthropic.com/engineering/writing-tools-for-agents)). mcp-builder도 "Don't expose internal implementation details"라고 적는다 [권고] ([mcp-builder](https://github.com/anthropics/skills/blob/main/skills/mcp-builder/reference/mcp_best_practices.md)). 본문이 길면 Claude Code가 앞뒤 5,000자씩만 보여 주므로 [플랫폼] 상태 코드별 다음 행동(재시도 시점, 확인할 키 이름) 한 줄을 맨 앞에 두고 원본을 뒤로 보내야 한다. 모든 외부 호출이 `fromApi`를 지나므로 수정은 함수 하나로 끝난다. 입력 스키마는 두 벌이다. `tools.ts`의 JSON Schema는 손으로 쓰고 런타임 검증은 핸들러의 zod 스키마(`parseArgs` 87회 호출)가 맡는다. 둘을 잇는 변환은 쓰지 않고 서버 전체 패리티 테스트도 없다(일부 툴만 `server/test/elevenlabs-v4-provider.test.mjs:233`처럼 대조). 모델이 보는 스키마와 서버가 받는 스키마가 어긋나면 모델은 문서대로 호출하고도 거부당한다 [추정]. 이미 일부 툴에 있는 키 대조 테스트를 104개 전체로 넓히는 것이 가장 작은 수정이다.

보안 쪽에서는 툴 결과로 들어오는 제3자 텍스트가 핵심이다. 이 서버는 SNS 댓글(`sns_comment_inbox`)과 검색 결과(`serp_*`, `naver_search`, `threads_search`)를 컨텍스트로 들여온다. 같은 세션에서 즉시 공개 게시(`threads_publish`, `sns_comment_reply`)도 할 수 있다. Simon Willison이 "lethal trifecta"라 부른 조건 가운데 신뢰할 수 없는 콘텐츠와 외부 통신 두 가지가 한 서버에 모인 셈이다 [의견] ([Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)). 공개 저장소의 악성 이슈 하나가 GitHub MCP를 거쳐 Claude 4 Opus에게 비공개 저장소 내용을 공개 PR로 옮기게 한 사례도 있다 [일화] ([Invariant Labs](https://invariantlabs.ai/blog/mcp-github-vulnerability)). MCP 스펙은 서버가 출력을 정화하라고 요구하고(MUST) Claude API 문서는 신뢰할 수 없는 내용을 `tool_result` 안에 두라고 권한다 ([MCP tools](https://modelcontextprotocol.io/specification/latest/server/tools), [Handle tool calls](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)). 이 보고서가 `server/src`를 검색한 결과 `_meta["anthropic/requiresUserInteraction"]`은 한 번도 쓰이지 않았다. 이 플래그는 `bypassPermissions`에서도 매 호출 프롬프트를 강제한다 [플랫폼] ([CC MCP](https://code.claude.com/docs/en/mcp)). 여기서 긴장이 생긴다. 플래그는 툴 단위라서 `publish`와 `grow-threads`가 같은 `threads_publish`를 쓰는 한 한쪽에만 걸 수 없다. 걸면 소유자가 growth-plan.md 상시 승인으로 택한 자동 게시 루프가 멈춘다. 걸지 않으면 게시 승인은 모델이 지시를 따르는지에 달린다. 이 선택은 소유자의 몫이다. 두 경우 모두와 양립하는 조치는 제3자 텍스트를 결과 안에서 출처가 드러나게 감싸 지시와 구분하는 일이다 [추정]. 어느 스킬도 사전 승인하지 않는 비가역 툴(`sns_comment_moderate`, `youtube_update`)에는 플래그를 따로 거는 방안도 검토할 만하다.

## CI 체커 18개가 문자열을 지키지만 실행되는 행동 eval은 없다

[권고] 공식 순서는 eval이 먼저다. Platform BP는 "Create evaluations BEFORE writing extensive documentation"이라며 스킬 없이 대표 과제를 돌려 실패를 기록하고 시나리오 3개와 기준선을 만든 뒤 최소한의 지시만 쓰라고 한다 ([Platform BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)). Claude Code 문서는 스킬이 호출되는지와 호출됐을 때 결과가 맞는지를 따로 재고 기준선은 새 세션에서 잡으라고 한다. 작성 중에 쌓인 맥락이 지시의 빈틈을 가리기 때문이다 ([CC skills](https://code.claude.com/docs/en/skills)). 플러그인에는 `claude plugin eval`이 있다 [플랫폼]. 케이스마다 플러그인을 켠 실행 3회와 끈 실행 3회를 돌려 `WITH`/`W/OUT`/`Δ`를 낸다. `tool_used: Skill` grader는 자연스러운 문장에서 스킬이 선택되는지 보고 `evals/mocks/<server>/<tool>.md`는 MCP 툴을 모킹한다. 임계값 미만이면 0이 아닌 코드로 끝나므로 CI 게이트로 쓸 수 있다. 기본 `--threshold`는 1.0이고 모든 실행이 실제 과금 호출이다 ([CC plugin evals](https://code.claude.com/docs/en/plugin-evals)). 트리거 eval의 관행 수치는 쿼리 약 20개(should 8–10, should-not 8–10), 쿼리당 3회, 60/40 분할, 최대 5회 반복이다 [권고] ([agentskills.io](https://agentskills.io/skill-creation/optimizing-descriptions)). skill-creator의 eval 형식과 `claude plugin eval` 형식은 케이스 파일이 호환되지 않으므로 하나를 골라야 한다 [플랫폼]. 모델 교체는 재측정 사유다. 앞서 본 대로 모델이 바뀌자 단순 훅의 호출률이 20%에서 50–59%로 움직였다 [측정]. Anthropic은 기본 모델이 스킬 없이 eval을 통과하면 그 스킬이 "no longer necessary"라는 신호로 읽으라고 한다 [권고] ([skill-creator blog](https://claude.com/blog/improving-skill-creator-test-measure-and-refine-agent-skills)).

저장소의 결정적 검사는 업계 권고보다 앞서 있다. `.github/workflows/check.yml`은 push와 PR마다 빌드·테스트, 커밋된 `dist`와 새 빌드의 일치(`check:dist`), `--selftest` 체커 18개를 돌린다(`check.yml:27-69`). `skill-lint.js` 16개 규칙은 name·디렉터리 일치, 1,024자, 76자 유일성, 리드인 금지, 참조 파일 실재, 목차, 변동성 참조의 신선도 줄, 고아 참조, 매니페스트 버전, MCP 설정 경로, README 툴 수까지 보고 현재 위반 0건이다. `server/test/contract.test.mjs`(1,564줄)는 툴 이름 유일성, title 60자 이하, description 40자 이상, 중첩 파라미터까지의 description, enum 위생, 주석 조합의 일관성, outputSchema 유효성, 툴과 핸들러의 1:1, 즉시 공개 툴의 승인 문구를 테스트한다(`server/test/contract.test.mjs:107-467`). 특히 `pipeline-lint.js`는 SKILL.md 산문과 `pipeline.js`의 단계 인계를 대조한다(`skills/platform-guide/references/pipeline-lint.js:1-8`). 산문과 코드가 따로 움직이는 드리프트를 결정적으로 잡는 장치로, 현장 자료가 권하는 형태 그대로다. 기계로 검사할 수 있는 규칙은 코드로 옮기라는 Claude Code 문서의 권고와도 맞는다 ([CC best practices](https://code.claude.com/docs/en/best-practices), [Steering blog](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)).

훅은 SessionStart 컨텍스트 주입 하나뿐이다(`hooks/hooks.json`, `hooks/project-context.js`). Claude Code 문서는 매번 지켜야 하는 규칙을 훅으로 옮기라고 하지만 [권고] 이 저장소에서 훅 후보는 좁다. 2026-10-16 지침이 창작 구조·문체·리뷰 점수를 실행 게이트에서 뺐다. Anthropic도 리뷰어가 찾은 지적을 전부 쫓으면 "leads to over-engineering"이라고 경고한다 ([CC best practices](https://code.claude.com/docs/en/best-practices)). 훅이나 체커로 옮길 자리는 같은 지침이 유지한 최소 실행 계약(읽을 수 있는 입력, 안정된 참조, 지원되는 어댑터 페이로드, 쓸 수 있는 미디어, 유한한 타이밍, 실제 지출 한도)으로 한정하는 편이 맞다.

빈칸은 행동 측정이다. `references/evals.md`가 있는 스킬은 4개(`produce`, `storyboard`, `autoproduce`, `inspect-content`)다. 어느 것도 시나리오 형식이 아니고 `claude plugin eval`용 `evals/` 디렉터리도 없다. 서버 테스트 파일 125개 가운데 SKILL.md를 읽는 것은 `seedance-routing.test.mjs` 하나다. 그래서 description을 고치거나 모델이 바뀌어도 트리거율과 스킬 유무 차이가 어떻게 움직였는지 알 길이 없다. 앞 절의 위험(목록 예산 초과, 접두 불일치, 컴팩션 뒤 손실)은 모두 오류 없이 under-trigger나 엉뚱한 툴 선택으로만 드러나는 종류라 이 빈칸이 더 크게 작용한다. 이 eval은 개발 시점의 회귀 측정이고 2026-10-16 지침이 걷어 낸 런타임 품질 게이트와는 다르다. 비용과 노이즈를 생각하면 처음에는 `--threshold`를 기본 1.0보다 낮춰 정보용으로 돌리는 편이 현실적이다 [추정].

문서 동기화는 툴 쪽만 기계로 지켜진다. README는 서버 툴 104개를 하나도 빠짐없이 언급하고 "104 tools" 주장 3곳(`README.md:601,604,671`)은 서버와 일치하며 skill-lint 16번이 이를 강제한다. 스킬 수에는 검사 규칙이 없어 `AGENTS.md:3`의 "18 skills"와 `README.md:437`의 "the 18 skills load"가 실제 21개와 어긋난다(437행은 "measured on codex 0.147.0"이 붙어 과거 기록일 여지가 있다). skill-lint 16번이 이미 쓰는 "N tools" 패턴을 "N skills"로 넓히면 된다. 단일 출처 주장도 둘이다. CLAUDE.md는 README를 툴 목록의 출처로 지정하지만(`CLAUDE.md:21`) `server/src/tools.ts:169`는 주석 판정표의 출처를 `docs/api-reference/mcp-tools.html §7`로 적는다.

ASTRA `skill-lint` 13항목으로 이 저장소를 채점하면 왜곡이 생긴다. 이 체크리스트는 Anthropic 공식 자료와 별개인 로컬 방법론이다(공식 체크리스트는 Core quality 10, Code and scripts 8, Testing 4 항목). 문서 안에서도 언어 정책(§12.1과 §14), 500줄 초과의 심각도(WARN 기준과 FAIL 예시), 체크리스트 출처 절(§13과 §14)이 서로 맞지 않는다(`astra-methodology/5.25.0/commands/skill-lint.md:9,37,65,84`, `astra-methodology/5.25.0/docs/development/skill-best-practices.md:184-193,237-240`). 8번(`allowed-tools` 필수)은 Claude Code 동작과 반대라 `platform-guide`의 FAIL은 공식 기준 위반이 아니다. 9번의 부작용 키워드(`git push`, `deploy`, `merge` 등)는 개발 워크플로 기준이라 SNS 게시와 유료 생성은 놓치고 "through produce" 같은 오탐 3건만 낸다. 5번은 `](references/` 문자열만 봐서 실제 2단계 중첩을 통과시킨다. 이 저장소에는 ASTRA 점수보다 공식 문서와 저장소 자체 lint의 확장이 더 맞는 잣대다.

## 결론

이 조사로 바뀐 그림은 이렇다. social-flow의 약점은 규칙이 모자란 데 있지 않고 규칙이 놓인 층에 있다. 호스트가 압박 속에서 실제로 읽는 자리, 즉 세션 시작 때의 서버 instructions, 1% 예산 안의 description, 컴팩션 뒤 앞 5,000토큰, 권한 프롬프트를 띄우는 툴 플래그는 비어 있거나 날짜별 덧씌우기로 붐빈다. 정보의 대부분은 호스트가 잘라 낼 수 있는 자리에 있다. 그래서 개선의 단위는 이동이다. 같은 내용을 앞으로 당기고 옛 층을 접고 서버 instructions로 첫인상을 주는 일은 새 정책을 하나도 만들지 않는다.

두 번째 함의는 측정의 방향이다. 이 저장소는 문자열 수준의 결정적 검사(이름, 길이, 참조, 주석, 수치 동기화)를 업계 권고보다 촘촘하게 갖췄지만 같은 규율을 행동에는 적용하지 않았다. 현장 자료는 문구 효과가 모델마다 반대로 움직인다는 점을 보여 준다. 그러니 문구 논쟁은 관습으로 정리되지 않는다. 또 social-flow 스킬 대부분은 모델이 모르는 능력을 가르치는 capability-uplift형보다 소유자의 작업 순서를 엮은 encoded-preference형에 가까워 보인다 [추정]. Anthropic은 이 유형이 오래가는 대신 "only as valuable as their fidelity to the actual workflow"라고 적는다 ([skill-creator blog](https://claude.com/blog/improving-skill-creator-test-measure-and-refine-agent-skills)). 이 저장소에서 그 충실도를 가장 자주 깨는 것은 소유자의 최신 지시와 스킬 본문 사이의 간극이고 그 간극은 지금 날짜 박힌 "supersedes" 층으로 쌓이고 있다. 다음 유지 보수의 중심은 `pipeline-lint.js`가 산문과 `pipeline.js`를 대조하듯 지시와 본문의 정합을 기계와 eval로 확인하는 일이다. 아직 모르는 것도 분명하다. Opus 5.x 기준 스킬 호출률, Claude Code의 플러그인 스킬 `allowed-tools` 재매핑 여부, 실제 토크나이저 기준 툴 정의 비용은 공개 자료에도 이 저장소에도 없다.
