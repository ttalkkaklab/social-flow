# 테스트는 행동을 붙잡고 구현은 놓아준다

테스트 클래스를 쓰고 관리하는 모범 사례는 출처가 달라도 한 가지 기준으로 모인다. **테스트 하나는 공개 진입점으로 행동 하나를 실행해 그 결과만 단언하고 원인과 결과는 테스트 본문 안에서 보여야 한다.** 나머지 규칙은 이 기준에서 따라 나온다. 픽스처는 테스트마다 새로 만들고 공유가 필요하면 범위를 명시적으로 선언한다. 테스트 더블은 다른 시스템이 관찰하는 경계에만 두고 리팩터링에 깨지는 테스트는 고치거나 지운다. Google은 이를 "unchanging tests"로 요약한다. 요구사항이 바뀔 때만 테스트를 고쳐야 하며 그러지 않으면 테스트 유지보수가 팀 시간을 점점 더 많이 차지한다는 것이다 ([SWE at Google 12장](https://abseil.io/resources/swe-book/html/ch12.html)). 스위트 차원에서는 플래키 테스트를 자동 탐지해 격리하고 소유자에게 배정하는 방식이 2016~2025년 사이 업계 관행으로 굳었다. 커버리지와 뮤테이션 점수는 빈틈을 찾는 신호로만 쓴다. JUnit·pytest·xUnit.net은 테스트마다 테스트 클래스 인스턴스를 새로 만드는 기본값으로 격리를 강제하고 공유는 각자 정해 둔 범위 장치로 선언하게 한다. 이 원칙들은 사람 팀을 대상으로 나왔지만 작업마다 테스트를 덧붙이는 AI 코딩 에이전트에게 더 날카롭게 적용된다. 유지 비용을 정하는 것은 테스트 개수보다 테스트가 구현에 얼마나 묶여 있느냐이기 때문이다.

## 실행 한 번과 행동 하나가 개별 테스트의 단위다

### AAA·Given-When-Then·Four-Phase는 같은 구조의 세 이름이다

Bill Wake는 2001년에 Arrange-Act-Assert 패턴을 관찰하고 이름을 붙였다 ([Wake, 3A](https://xp123.com/3a-arrange-act-assert/)). Dan North와 Chris Matts는 BDD에서 "Given some initial context (the givens), When an event occurs, Then ensure some outcomes." 템플릿을 만들었다 ([North, Introducing BDD](https://dannorth.net/blog/introducing-bdd/)). Martin Fowler는 Given-When-Then을 Meszaros의 Four-Phase Test(setup, exercise, verify, teardown)를 고쳐 쓴 형태로 본다 ([Fowler, GivenWhenThen](https://martinfowler.com/bliki/GivenWhenThen.html)). 세 이름의 차이는 어휘와 teardown 단계 유무 정도이고 처방은 같다. 대상을 준비하고 **SUT를 한 번만 실행한 뒤** 그 실행의 결과를 검증한다. Meszaros는 "exercise, verify, exercise, verify"처럼 실행과 검증이 번갈아 나오면 여러 조건을 한 테스트에 몰아넣은 것이니 별도 테스트 메서드로 나누라고 적었다 ([xunitpatterns.com, Principles of Test Automation](http://xunitpatterns.com/Principles%20of%20Test%20Automation.html)).

Google의 2018년 Testing on the Toilet(TotT) 글은 이 신호를 더 구체적으로 짚는다. SUT 호출 결과를 단언한 뒤 SUT를 다시 호출한다면 시나리오가 둘 이상이라는 뜻이다. 예금·출금·초과 인출 한도를 한 테스트에서 연달아 확인하던 `WithdrawFromAccount`는 `CanWithdrawWithinBalance`, `CannotOverdraw`, `CanOverdrawUpToOverdraftLimit` 세 테스트로 나누고 공통 준비만 `DepositAndSettle(Usd(5))` 헬퍼로 뺐다. 이렇게 나누면 한 시나리오의 부수효과가 다음 시나리오의 가정을 가리지 않고 한 시나리오가 실패해도 나머지는 계속 실행된다 ([TotT, Keep Tests Focused](https://testing.googleblog.com/2018/06/testing-on-toilet-keep-tests-focused.html)). 같은 글은 통합·E2E 테스트의 시나리오가 더 길어도 된다고 허용한다. Wake도 누적 상태를 한 흐름으로 보여 주는 편이 더 명확할 때는 예외를 인정한다. 단위 테스트에 한해서는 사실상 합의된 규칙이다.

### "단언 하나" 규칙은 결함 위치 파악을 대신하는 대리 지표다

"테스트당 단언 하나"는 Roy Osherove의 2006년 글이 대표한다. Osherove는 .NET 프레임워크가 첫 번째 실패 단언에서 테스트를 멈춘다는 점과 단언이 여럿이면 사실상 여러 가지를 검증한다는 점을 근거로 들었다 ([Osherove 2006](https://osherove.com/blog/2006/10/3/avoid-multiple-asserts-in-a-single-unit-test-revisited.html)). 다른 1차 출처 대부분은 행동을 단위로 잡는다. Meszaros는 원칙을 "Verify One Condition per Test"로 정하고 단언 하나 학파를 소개하면서도 "I wouldn't be too dogmatic about insisting on a single assertion"이라고 선을 긋는다 ([xunitpatterns.com, Principles of Test Automation](http://xunitpatterns.com/Principles%20of%20Test%20Automation.html)). Mark Seemann은 2022년에 이 규칙을 Assertion Roulette의 오독으로 규정했다. 예약 취소 테스트가 `IsSuccessStatusCode`만 단언하면 아무 일도 하지 않는 `Delete` 구현도 통과한다. 그래서 같은 테스트에서 후속 GET이 `NotFound`를 돌려주는지까지 확인하는 편이 낫고 두 단언은 여전히 "Successfully cancelling a reservation"이라는 한 사례다 ([Seemann, Multiple assertions per test are fine](https://stackoverflow.blog/2022/11/03/multiple-assertions-per-test-are-fine/)).

SWE at Google 12장은 "the vast majority of unit tests require only one 'when' and one 'then' block"이라고 쓰고 **테스트 이름에 "and"가 필요하면 여러 행동을 검증하는 신호**로 본다 ([SWE at Google 12장](https://abseil.io/resources/swe-book/html/ch12.html)). Kent Beck의 Test Desiderata는 개수 규칙 대신 "Specific — if a test fails, the cause of the failure should be obvious"라는 속성을 내세운다 ([Test Desiderata](https://testdesiderata.com/)). 단언 하나 규칙은 결국 이 목적, 곧 Meszaros가 말한 Defect Localization의 대리 지표다. 정보가 풍부한 실패 메시지나 커스텀 단언으로 같은 목적을 이루면 규칙을 완화해도 된다. 첫 실패에서 멈춘다는 Osherove의 근거도 xUnit.net v3의 `Assert.Multiple`처럼 여러 검사를 실행하고 실패를 모아 보고하는 기능 앞에서 힘을 잃는다 ([xUnit.net API, Assert.Multiple](https://api.xunit.net/v3/3.0.0/v3.3.0.0-Xunit.Assert.Multiple.html)).

### 이름에는 시나리오와 기대 결과가 둘 다 들어간다

이름 형식은 출처마다 다르다. Osherove는 `[UnitOfWork_StateUnderTest_ExpectedBehavior]` 형식과 `Sum_NegativeNumberAs1stParam_ExceptionThrown` 같은 예를 제시했다 ([Osherove 2005](https://osherove.com/blog/2005/4/3/naming-standards-for-unit-tests.html)). Dan North는 "should"로 시작하는 문장을 권했다. "Should implicitly allows you to challenge the premise of the test"라서 실패가 버그인지 낡은 가정인지 따지기 쉬워진다는 이유다 ([North, Introducing BDD](https://dannorth.net/blog/introducing-bdd/)). Vladimir Khorikov는 2019년 글에서 `[MethodUnderTest]_[Scenario]_[ExpectedResult]`를 "popular, yet inferior"라고 부른다. 메서드 이름을 빼고 도메인을 아는 비프로그래머에게 설명하듯 `Delivery_with_a_past_date_is_invalid`처럼 쓰라고 하며 사실을 진술하는 문장에 "should"는 어울리지 않는다고 본다 ([Khorikov, You are naming your tests wrong!](https://enterprisecraftsmanship.com/posts/you-naming-tests-wrong/)).

형식 논쟁 아래에는 공통 규칙이 있다. Google의 Andrew Trenk는 `isUserLockedOut_invalidLogin`이 시나리오만 말하고 결과를 말하지 않는다며 `isUserLockedOut_lockOutUserAfterThreeInvalidLoginAttempts`로 고쳤다. Trenk의 결론은 "Whichever pattern you use, the same advice still applies: Make sure test names contain both the scenario being tested and the expected outcome."이다 ([TotT, Writing Descriptive Test Names](https://testing.googleblog.com/2014/10/testing-on-toilet-writing-descriptive.html)). 형식은 팀 관례로 정하면 되고 판단 기준은 이름 목록만 읽어도 클래스의 동작이 보이느냐다. 메서드 이름을 넣을지는 탐색성과 리팩터링 내성 사이의 선택이며 한 행동이 여러 메서드에 걸칠 때는 메서드 접두사가 오히려 오해를 부른다 ([TotT, Test Behaviors, Not Methods](https://testing.googleblog.com/2014/04/testing-on-toilet-test-behaviors-not.html)). 명명 형식이 이해도나 유지보수 비용에 미치는 영향을 잰 실증 연구는 이번 조사에서 나오지 않았다.

### 넓은 단언과 테스트 안 로직이 깨지기 쉬운 테스트를 만든다

단언은 좁을수록 오래 산다. Google의 2024년 TotT 글은 ACCOUNT 테이블에 CREATION_DATE 열을 추가하자 계정 객체 전체를 `EXPECT_EQ(account, kExpected)`로 비교하던 테스트가 깨진 사례를 든다. 이 테스트는 잔액만 확인하려 했지만 실제로는 "implicitly tests unrelated behaviors" 상태였다. `EXPECT_EQ(account.balance, 2000)`으로 좁히면 문제가 사라진다. 그 글은 **복잡한 객체의 완전 동등성은 공통 사례 하나에서만 확인하고 나머지는 좁은 단언을 쓰라**고 권한다 ([TotT, Prefer Narrow Assertions in Unit Tests](https://testing.googleblog.com/2024/04/prefer-narrow-assertions-in-unit-tests.html)). Meszaros는 객체를 문자열로 바꿔 기대 문자열과 비교하는 Sensitive Equality를 "just plain wrong"이라고 했다 ([xunitpatterns.com, Fragile Test](http://xunitpatterns.com/Fragile%20Test.html)). 실패 메시지는 기대값·실제값·관련 매개변수를 보여 줘야 하므로 SWE at Google은 `assertTrue(colors.contains("orange"))`보다 Truth의 `assertThat(colors).contains("orange")` 같은 풍부한 매처를 권한다 ([SWE at Google 12장](https://abseil.io/resources/swe-book/html/ch12.html)). 반복되는 검증은 의도를 드러내는 이름의 Custom Assertion으로 옮긴다 ([xunitpatterns.com, Custom Assertion](http://xunitpatterns.com/Custom%20Assertion.html)). 그런 헬퍼는 "a single conceptual fact"만 단언해야 하고 자체 테스트를 가져야 한다 ([SWE at Google 12장](https://abseil.io/resources/swe-book/html/ch12.html)).

테스트 본문은 분기·루프·계산이 없는 직선 코드여야 한다. Erik Kuefler의 2014년 예가 이유를 보여 준다. `baseUrl + "/u/0/photos"`로 기대값을 계산한 테스트는 `baseUrl` 끝의 슬래시 때문에 생긴 `//` 버그를 숨긴다. 프로덕션 코드가 같은 실수를 하면 테스트는 "(even worse) incorrectly pass" 상태가 된다. 기대값을 리터럴 `"http://plus.google.com//u/0/photos"`로 풀어 쓰면 버그가 바로 눈에 띈다 ([TotT, Don't Put Logic in Tests](https://testing.googleblog.com/2014/07/testing-on-toilet-dont-put-logic-in.html)). Meszaros도 "Test Methods must be simple enough to not need tests"라며 테스트 메서드 안의 제어 구조를 극도로 의심하라고 했다 ([xunitpatterns.com, Conditional Test Logic](http://xunitpatterns.com/Conditional%20Test%20Logic.html)). 원인과 결과도 같은 테스트 안에 있어야 한다. Ben Yu의 2017년 예에서 `assertEquals(9, tally.get("key1"))`이 맞는지는 200줄 떨어진 `@Before`를 읽어야 알 수 있었다. Yu는 판단 규칙을 "Relevant? In (don't worry about DRY). Irrelevant? Out."으로 정리했다 ([TotT, Keep Cause and Effect Clear](https://testing.googleblog.com/2017/01/testing-on-toilet-keep-cause-and-effect.html)). 외부 파일에서 픽스처를 읽어 기대값의 근거가 보이지 않는 Mystery Guest도 같은 문제다 ([xunitpatterns.com, Obscure Test](http://xunitpatterns.com/Obscure%20Test.html)).

기대값 표현에는 출처 사이에 긴장이 있다. Kuefler는 출력값을 직접 쓰라고 한다. Meszaros는 의미 없는 리터럴 대신 이름 붙은 상수나 입력에서 계산한 Derived Value를 권한다 ([xunitpatterns.com, Obscure Test](http://xunitpatterns.com/Obscure%20Test.html)). testsmells.org는 단언 속 숫자 리터럴 자체를 Magic Number Test 스멜로 잡는다 ([testsmells.org](https://testsmells.org/pages/testsmells.html)). 세 주장을 함께 만족하는 방식은 다음과 같다. 다만 한 출처가 이 셋을 모두 권한 것은 아니므로 이는 종합 판단이다. 기대값은 리터럴로 쓴다. 입력과의 관계가 자명하지 않을 때만 이름 붙은 상수나 짧은 주석으로 의미를 드러낸다. 프로덕션 알고리즘을 테스트 안에서 다시 구현하는 계산은 하지 않는다.

### FIRST와 Test Desiderata는 서로 부딪히는 트레이드오프 축이다

이 규칙들의 상위 틀로 자주 인용되는 FIRST(Fast, Isolated, Repeatable, Self-validating, Timely)는 Object Mentor 시절 Tim Ottinger와 Brett Schuchert가 다듬었고 *Clean Code* 9장에 실리며 널리 퍼졌다 ([Agile in a Flash, FIRST](https://agileinaflash.blogspot.com/2009/02/first.html)). 여기서 Isolated는 실패 원인이 분명하고 실행 순서에 의존하지 않는다는 뜻이다. Ottinger의 설명에는 "모든 의존성을 mock하라" 같은 mocking 요구가 없다. Beck의 Test Desiderata는 같은 개념을 Isolated(순서 독립)와 Specific(실패 원인이 명확함)으로 나누고 12개 속성이 서로 충돌한다고 인정한다. "Making tests more predictive of production behavior makes them slower."라는 문장이 그 예다 ([Test Desiderata](https://testdesiderata.com/)).

### 스멜 탐지기는 1차 필터일 뿐 결함 판정기가 아니다

테스트 스멜 개념은 van Deursen 외의 2001년 보고서 "Refactoring Test Code"에서 시작했다 ([CWI 저장소](https://ir.cwi.nl/pub/4324)). Meszaros의 *xUnit Test Patterns*는 이를 Obscure Test, Fragile Test, Assertion Roulette 같은 상위 스멜과 그 원인(Eager Test, Mystery Guest, Sensitive Equality)으로 체계화했다 ([xunitpatterns.com, Test Smells](http://xunitpatterns.com/Test%20Smells.html)). testsmells.org는 이를 기계 탐지 규칙으로 옮겼는데 그 규칙에서 Assertion Roulette는 "메시지 없는 단언 2개 이상"이고 Eager Test는 "여러 프로덕션 메서드 호출"이다 ([testsmells.org](https://testsmells.org/pages/testsmells.html)). 이렇게 좁히면 Seemann이 옹호한 다중 단언 테스트와 한 행동이 여러 메서드에 걸치는 정상 테스트도 스멜로 표시된다. Panichella 외(2022)는 개발자 작성 테스트와 자동 생성 테스트를 손으로 라벨링해 탐지 도구를 벤치마크했다. 그 결과 **일부 스멜은 개발자 테스트에 흔하지만 실제 의미·유지보수 결함과 거의 연관되지 않았다** ([Panichella et al., Test Smells 20 Years Later](https://research.tudelft.nl/en/publications/test-smells-20-years-later-detectability-validity-and-reliability)). 탐지기는 저비용 1차 필터로 쓰고 판정은 "독자가 이 테스트를 한눈에 이해하고 실패 원인을 바로 아는가"라는 Meszaros의 원래 기준으로 내리는 편이 맞다.

## 테스트 클래스는 프로덕션 클래스당 하나로 시작해 시작 상태나 기능 단위로 쪼갠다

### 분할 기준은 테스트들이 공유하는 시작 상태다

Meszaros는 Testcase Class per Class를 "a simple way to start off organizing our tests"로 본다. 테스트가 늘어 공통 시작 상태가 몇 개로 모이면 Testcase Class per Fixture로, 서로 다른 기능이 여럿이면 Testcase Class per Feature로 나눈다 ([xunitpatterns.com, Testcase Class per Class](http://xunitpatterns.com/Testcase%20Class%20per%20Class.html)). 두 분할은 효과가 다르다. per Feature는 큰 클래스를 테스트 메서드를 고치지 않고 나누는 체계적 방법이지만 개별 테스트를 더 읽기 쉽게 만들지는 않는다. Meszaros에 따르면 그 효과는 per Fixture에서만 나온다 ([xunitpatterns.com, Testcase Class per Feature](http://xunitpatterns.com/Testcase%20Class%20per%20Feature.html)). per Fixture 구조에서는 setUp이 픽스처를 맡고 각 테스트는 실행과 검증에 집중한다. 클래스마다 같은 메서드 목록이 생기므로 어느 시작 상태에서 어떤 연산을 빠뜨렸는지 IDE 아웃라인에서 바로 보인다. Meszaros는 이 패턴을 "a key part of the behavior-driven development style"이라 부르고 기능이 너무 많아 테스트 클래스가 비대해지면 SUT의 책임 과다를 의심해 프로덕션 쪽에 Extract Class를 적용하라고 한다 ([xunitpatterns.com, Testcase Class per Fixture](http://xunitpatterns.com/Testcase%20Class%20per%20Fixture.html)). Google은 같은 방향을 더 밀어 "rather than writing a test for each method, write a test for each behavior"라고 쓴다 ([SWE at Google 12장](https://abseil.io/resources/swe-book/html/ch12.html)). `FooTest`라는 이름은 진입점 표시일 뿐이고 그 안의 테스트가 `Foo`의 메서드를 1:1로 따라갈 필요는 없다.

중첩 그룹(JUnit `@Nested`, `describe` 블록)은 per Fixture 구조를 한 파일 안에 표현하는 수단이다. JUnit 공식 예제는 스택을 `WhenNew`와 그 안의 `AfterPushing`처럼 상태별로 중첩하고 단계마다 `@BeforeEach`가 상태 하나씩을 더한다 ([JUnit User Guide, Nested Tests](https://docs.junit.org/6.1.3/writing-tests/nested-tests.html)). Kent C. Dodds는 2019년 글에서 반대편 위험을 짚었다. 상단에 변수를 선언하고 훅에서 할당한 뒤 더 깊은 훅에서 재할당하면 독자는 값의 흐름을 파일 전체에서 추적해야 한다. Dodds는 정리용 `afterEach`나 서버 기동용 `beforeAll`은 괜찮다면서도 "I just don't recommend them as a mechanism for code reuse."라고 결론짓는다 ([Dodds, Avoid Nesting when you're Testing](https://kentcdodds.com/blog/avoid-nesting-when-youre-testing)). 두 입장은 "준비 과정이 독자에게 보이는가"라는 같은 기준을 서로 다른 지점에 적용한 결과다. 중첩 단계마다 하위 테스트 전부가 정말 필요로 하는 상태 하나를 더하고 깊이가 얕으면 중첩이 읽기를 돕는다. 훅이 상위 변수를 덮어쓰거나 일부 테스트만 쓰는 준비가 상위 단계에 올라가 있으면 읽기를 방해한다. 적정 깊이의 정량 기준을 제시한 1차 출처는 없다.

### setUp에는 결과와 무관한 준비만 둔다

기본값은 Fresh Fixture다. 테스트마다 픽스처를 새로 만들고 끝나면 정리해 모든 테스트가 "clean slate"에서 시작한다 ([xunitpatterns.com, Fresh Fixture](http://xunitpatterns.com/Fresh%20Fixture.html)). Meszaros는 Shared Fixture의 정당한 사용 이유를 느린 테스트(주로 실제 DB)와 Incremental Tests 두 가지로 한정한다. 느린 테스트라는 이유조차 "A better solution is to make the tests run faster by not interacting with the database at all."이라며 반박한다. 공유가 불가피하면 Immutable Shared Fixture로 나눈다. 모든 테스트가 읽기만 하는 참조 데이터는 공유하고 테스트가 수정할 객체는 각 테스트가 새로 만든다 ([xunitpatterns.com, Shared Fixture](http://xunitpatterns.com/Shared%20Fixture.html)). setUp(Implicit Setup)에는 SUT와 협력 객체 생성이나 연결 초기화처럼 "essential but irrelevant"한 부분만 둔다 ([xunitpatterns.com, Implicit Setup](http://xunitpatterns.com/Implicit%20Setup.html)). SWE at Google도 setup 메서드의 최선의 용도를 테스트 대상 객체와 협력자 생성으로 보며 특정 값에 의존하는 테스트는 그 값을 본문에서 직접 지정하라고 한다 ([SWE at Google 12장](https://abseil.io/resources/swe-book/html/ch12.html)).

Meszaros는 Fowler의 태도를 이렇게 전한다. 각 테스트가 필요한 픽스처를 스스로 만들다가 여러 테스트가 우연히 같은 픽스처를 쓰게 되면 그때 setUp으로 올린다. 모든 테스트가 쓰는 큰 Standard Fixture를 미리 설계하느냐는 질문에 Fowler는 "Do people actually do this?"라고 되물었다 ([xunitpatterns.com, Standard Fixture](http://xunitpatterns.com/Standard%20Fixture.html)). Google의 2019년 TotT 글은 setUp에서 만든 `self.users`를 헬퍼 `_RegisterAllUsers()`와 for 루프로 등록하던 테스트를 고쳐 사용자 생성·등록·검증을 본문에 직접 쓰고 setUp에는 `Forum()` 생성만 두었다. 근거는 "Since tests don't have tests, it should be easy for humans to manually inspect them for correctness, even at the expense of greater code duplication."이다 ([TotT, Tests Too DRY? Make Them DAMP!](https://testing.googleblog.com/2019/12/testing-on-toilet-tests-too-dry-make.html)).

### 테스트 데이터는 기본값 있는 빌더로 만들고 기본값에 기대지 않는다

Fowler가 정리한 Object Mother는 이름 붙은 표준 예시 객체를 돌려주는 팩토리다. 여러 테스트 클래스에서 재사용하기 좋지만 "there's a heavy coupling in that many tests will depend on the exact data in the mothers"라는 대가가 따른다 ([Fowler, ObjectMother](https://martinfowler.com/bliki/ObjectMother.html)). Nat Pryce는 2007년에 Object Mother가 "does not cope at all well with variation in the test data"라며 Test Data Builder를 제안했다. 빌더는 각 필드를 안전한 기본값으로 채우고 테스트가 관심 있는 필드만 체이닝으로 덮어쓴다. 테스트는 결과와 무관한 객체 구조에서 분리되고 생성자 인자가 늘어도 깨지지 않는다 ([Pryce, Test Data Builders](http://www.natpryce.com/articles/000714.html)). Google의 2018년 TotT 글은 `newCompany(2, 2, null, PUBLIC)`처럼 매개변수가 불어나거나 `newCompanyWithEmployeesAndBoardMembers`처럼 조합마다 메서드가 생기는 헬퍼 대신 빌더를 권하면서 조건 하나를 붙인다. "tests should never rely on default values that are specified by a helper method" ([TotT, Cleanly Create Test Data](https://testing.googleblog.com/2018/02/testing-on-toilet-cleanly-create-test.html)). SWE at Google은 명시하지 않은 필드의 기본값을 약간 무작위화하면 기본값에 기댄 숨은 의존을 막을 수 있다고 각주에 적었다 ([SWE at Google 12장](https://abseil.io/resources/swe-book/html/ch12.html)). 팩토리의 기본값은 어떤 값이어도 테스트가 통과해야 하는 값이어야 한다. 변형이 거의 없는 소수의 대표 예시는 이름 있는 Creation Method로 충분하며 이 방식의 단점은 "it creates another API for test automaters to learn"이다 ([xunitpatterns.com, Creation Method](http://xunitpatterns.com/Creation%20Method.html)).

### 상속보다 합성을 쓰고 파일은 생태계 관례대로 둔다

공통 준비를 추상 기반 테스트 클래스로 상속하는 방식은 Meszaros가 Testcase Superclass로 인정한 선택지다. Meszaros는 Test Helper(별도 클래스)와의 선택을 "type visibility" 문제로 보고 mixin을 "the best of both worlds"라 불렀다 ([xunitpatterns.com, Testcase Superclass](http://xunitpatterns.com/Testcase%20Superclass.html)). 실무 쪽 평가는 더 엄격하다. Jan Van Ryswyck는 기반 클래스가 있으면 테스트를 읽을 때 "we're missing an important part of the context" 상태가 되고 테스트가 기반 클래스 속성에 묶인다며 테스트 코드에도 상속보다 합성을 쓰라고 권한다 ([Van Ryswyck, Avoid Inheritance For Test Classes](https://dev.to/janvanryswyck/avoid-inheritance-for-test-classes-4dli)). 상위 클래스의 setUp은 Mystery Guest를 테스트 메서드 밖을 넘어 파일 밖으로 숨긴다. 상속이 제값을 하는 경우는 같은 인터페이스의 여러 구현(실제 구현과 fake)에 같은 테스트 묶음을 돌리는 추상 계약 테스트, 그리고 DB 연결이나 트랜잭션 롤백 같은 얕은 인프라 수명주기 정도다. 결과를 좌우하는 데이터를 상위 클래스에 두는 일은 피한다. 공유 테스트 인프라는 그 자체로 제품처럼 다뤄야 하고 "test infrastructure must always have its own tests"라는 것이 Google의 기준이다 ([SWE at Google 12장](https://abseil.io/resources/swe-book/html/ch12.html)).

파일 배치는 생태계 관례가 사실상 표준이다. Maven은 테스트를 `src/test/java`에 둔다 ([Maven, Standard Directory Layout](https://maven.apache.org/guides/introduction/introduction-to-the-standard-directory-layout.html)). Surefire는 `**/Test*.java`·`**/*Test.java`·`**/*Tests.java`·`**/*TestCase.java`를, Failsafe는 `**/IT*.java`·`**/*IT.java`·`**/*ITCase.java`를 기본으로 찾으므로 단위 테스트와 통합 테스트가 이름 패턴만으로 따로 실행된다 ([Maven Surefire Inclusions](https://maven.apache.org/surefire/maven-surefire-plugin/examples/inclusion-exclusion.html), [Maven Failsafe Inclusions](https://maven.apache.org/surefire/maven-failsafe-plugin/examples/inclusion-exclusion.html)). pytest는 애플리케이션 코드 밖의 `tests/`와 `src` 레이아웃을 권한다 ([pytest, Good Integration Practices](https://docs.pytest.org/en/stable/explanation/goodpractices.html)). Go는 같은 디렉터리의 `_test.go` 파일을 쓰며 `_test` 접미사 패키지에 두면 공개 식별자만 쓰는 black box 테스트가 된다 ([Go, package testing](https://pkg.go.dev/testing)). Rust는 단위 테스트를 같은 파일의 `#[cfg(test)] mod tests`에, 통합 테스트를 최상위 `tests/`에 두고 공용 헬퍼는 테스트로 수집되지 않게 `tests/common/mod.rs`에 둔다 ([The Rust Programming Language 11.3](https://doc.rust-lang.org/book/ch11-03-test-organization.html)). 언어를 가리지 않는 원칙은 네 가지다. 설정 없이 발견되는 이름과 위치를 쓴다. 단위 테스트는 대상과 1:1로 찾기 쉬운 곳에 둔다. 통합·E2E 테스트는 디렉터리나 접미사로 분리해 따로 실행할 수 있게 한다. 공용 헬퍼는 테스트로 수집되지 않는 위치에 둔다.

### 혼자, 어떤 순서로, 동시에 돌려도 결과가 같아야 한다

Meszaros는 Interacting Tests의 증상으로 다른 테스트를 추가·삭제하거나 이름을 바꾸거나 러너 버전을 올렸을 때 혼자서는 통과하던 테스트가 실패하는 현상을 든다. 원인은 테스트 수명보다 오래 사는 모든 것이다. Meszaros는 "static variables can be depended on to cause Interacting Tests and should therefore be avoided in both the SUT and the Test Automation Framework!"라고 썼다 ([xunitpatterns.com, Erratic Test](http://xunitpatterns.com/Erratic%20Test.html)). 프레임워크도 이 원칙을 돕는다. JUnit은 `MethodOrderer.Random`과 `ClassOrderer.Random`으로 숨은 순서 의존을 드러내게 한다 ([JUnit User Guide, Test Execution Order](https://docs.junit.org/6.1.3/writing-tests/test-execution-order.html)). JUnit의 병렬 실행은 opt-in이며 공유 자원은 `@ResourceLock`으로, 완전 격리가 필요한 클래스는 `@Isolated`로 선언한다 ([JUnit User Guide, Parallel Execution](https://docs.junit.org/6.1.3/writing-tests/parallel-execution.html)). Go 테이블 테스트에서 맵을 쓰면 반복 순서가 정해지지 않아 순서 독립성이 자연스럽게 검사된다 ([Go Wiki, TableDrivenTests](https://go.dev/wiki/TableDrivenTests)). 정리 코드는 테스트가 실패해도 실행되는 훅에 두어야 연쇄 실패가 생기지 않는다.

매개변수화는 같은 테스트 알고리즘을 데이터만 바꿔 반복할 때 쓴다 ([xunitpatterns.com, Parameterized Test](http://xunitpatterns.com/Parameterized%20Test.html)). Go Wiki는 테스트를 복사해 붙여 넣고 있다면 테이블 테스트를 고려하라고 하고 각 행에 `t.Run(name, ...)`으로 이름을 붙이게 한다. `t.Errorf`는 단언이 아니어서 오류를 기록한 뒤에도 테스트가 계속 진행된다 ([Go Wiki, TableDrivenTests](https://go.dev/wiki/TableDrivenTests)). 손으로 쓴 for 루프는 실패 위치를 흐리므로 케이스마다 이름이 붙는 프레임워크 매개변수화가 낫다. 행마다 준비나 검증 로직이 달라져 테이블에 "이 행이면 이 단언은 건너뛴다" 같은 플래그가 생기면 별도 테스트나 별도 테이블로 나눌 때다. 매개변수화는 "테스트 하나에 행동 하나" 원칙과 충돌하지 않는다. 행동은 하나이고 입력 공간의 표본만 여럿이기 때문이다.

## 실제 협력 객체가 기본이고 mock은 다른 시스템이 보는 경계에만 쓴다

### 다섯 가지 더블은 무엇을 대신하고 무엇을 검증하느냐로 구별된다

Meszaros가 분류하고 Fowler가 대중화한 정의는 다음과 같다 ([Fowler, Mocks Aren't Stubs](https://martinfowler.com/articles/mocksArentStubs.html)). 오른쪽 열의 쓰임새는 Google과 Khorikov의 권고를 합친 것이다.

| 더블 | 정의(Fowler 원문) | 쓸 때 |
|---|---|---|
| Dummy | "passed around but never actually used" | 매개변수 자리만 채울 때 |
| Stub | "provide canned answers to calls made during the test" | 특정 반환값이나 오류를 강제로 일으킬 때 |
| Spy | "stubs that also record some information based on how they were called" | 호출 기록을 사후에 확인해야 할 때 |
| Mock | "pre-programmed with expectations which form a specification of the calls they are expected to receive" | 외부에 보이는 부수효과가 곧 요구사항일 때 |
| Fake | "actually have working implementations, but usually take some shortcut" | 실제 구현이 느리거나 비결정적일 때(인메모리 DB 등) |

Google의 실무 우선순위는 실제 구현, fake, stub, 상호작용 검증 순이다. SWE at Google 13장은 "our first choice for tests is to use the real implementations of the system under test's dependencies"라고 쓴다. 실제 구현을 쓸 수 없으면 fake가 "often the ideal solution"이다. stub은 특정 반환값이나 오류를 일으킬 때 소수 함수에만 쓰고 interaction testing은 "should be avoided when possible"이며 상태를 바꾸는 함수에만 쓴다 ([SWE at Google 13장](https://abseil.io/resources/swe-book/html/ch13.html)). 같은 장은 mocking 프레임워크를 남용한 테스트가 "easy to write"였지만 유지 비용이 크고 "rarely finding bugs"였다는 경험을 적었다.

### 학파 논쟁은 고전파 쪽으로 기울었고 Khorikov의 기준이 가장 실용적이다

Fowler의 정리에 따르면 고전파(Detroit)는 "to use real objects if possible and a double if it's awkward to use the real thing"이고 목 지향파(London)는 "will always use a mock for any object with interesting behavior"이다 ([Fowler, Mocks Aren't Stubs](https://martinfowler.com/articles/mocksArentStubs.html)). Fowler 자신은 고전파다. Google도 실제 구현을 선호하는 방식을 "classical testing"이라 부르고 목 지향 방식은 "is difficult to scale"이라고 평가한다 ([SWE at Google 13장](https://abseil.io/resources/swe-book/html/ch13.html)). Khorikov는 2020년 글에서 "Both schools are wrong in their treatment of mocks, though the classical school is less so than the London school."이라고 쓰고 경계선을 프로세스 외부 의존성의 소유권으로 긋는다. 애플리케이션만 쓰는 DB처럼 완전히 통제하는 managed 의존성은 실제 인스턴스로 테스트하고 SMTP 서버나 메시지 버스처럼 다른 애플리케이션이 부수효과를 관찰하는 unmanaged 의존성만 mock으로 바꾼다. **"Intra-system communications are implementation details; inter-system communications are not."** 외부 시스템과의 통신 패턴은 하위 호환 때문에 고정되어야 하므로 mock으로 굳혀도 되지만 내부 클래스 간 통신을 mock으로 굳히면 테이블을 나누는 정도의 변경에도 테스트가 깨진다 ([Khorikov, When to Mock](https://enterprisecraftsmanship.com/posts/when-to-mock/)). Khorikov는 들어오는 데이터만 공급하는 불변 의존성은 stub으로 대체하라고도 한다.

London 학파의 원전도 대중적 인식보다 고전파에 가깝다. Freeman·Pryce·Mackinnon·Walnes의 2004년 논문 "Mock Roles, not Objects"는 "Mock Objects is misnamed. It is really a technique for identifying types in a system based on the roles that objects play."라고 쓰며 mock을 격리 수단보다 설계 발견 수단으로 본다. 같은 논문은 "mock-based tests quickly become too complicated when the system design is weak"라고 경고하고 테스트가 "over-specified to check features that are an artefact of the implementation" 상태가 되면 리팩터링이 막힌다고 적었다. 처방은 "a specification should be as precise as possible, but not more precise."이며 바로 이웃한 객체만 mock하라는 규칙도 함께 제시한다 ([Freeman et al., Mock Roles, not Objects](http://jmock.org/oopsla2004.pdf)). 흔히 인용되는 "Don't mock what you don't own"의 원전도 이 논문의 §4.1 "Only Mock Types You Own"이다. 런타임이나 외부 라이브러리처럼 바꿀 수 없는 타입을 mock하면 설계 피드백을 반영할 수 없으므로 "they should write thin wrappers to implement the application abstractions in terms of the underlying infrastructure"라고 처방한다 ([Freeman et al.](http://jmock.org/oopsla2004.pdf)). test double 사의 위키도 서드파티를 직접 더블로 바꾸는 고통을 "useless pain"이라 부르며 자기 소유 래퍼를 만들어 그것을 fake하라고 권한다 ([testdouble wiki, Don't mock what you don't own](https://github.com/testdouble/contributing-tests/wiki/Don%27t-mock-what-you-don%27t-own)). 이 규칙은 Khorikov의 기준과 충돌하지 않는다. unmanaged 외부 시스템을 mock할 때도 SDK 클래스를 감싼 자기 소유 어댑터 인터페이스를 mock하면 두 규칙을 동시에 지킨다.

과잉 mock은 신호로 드러난다. 한 테스트에 mock이 여럿이거나 mock이 mock을 반환하거나 내부 협력자 호출 순서를 검증하거나 리팩터링 커밋마다 테스트를 고쳐야 한다면 테스트 범위를 넓히거나 설계를 바꾸라는 피드백이다. Ham Vocke는 private 메서드를 따로 테스트하고 싶어지는 것 자체가 클래스 책임 과다의 신호라고 본다 ([Vocke, The Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html)). Google은 이를 의존성 주입(DI)과 묶어 설명한다. 테스트가 실제 구현을 더블로 바꿔 끼울 수 있어야 하고 테스트 가능성을 나중에 덧붙이는 비용은 크다 ([SWE at Google 13장](https://abseil.io/resources/swe-book/html/ch13.html)). 다만 Khorikov 기준을 적용하면 주입 인터페이스가 꼭 필요한 곳은 unmanaged 외부 시스템 어댑터와 시간·난수 같은 비결정적 입력이며 모든 내부 클래스에 인터페이스를 만드는 일은 mock 남용을 부르는 과잉 추상이 되기 쉽다.

### fake는 소유 팀이 만들고 계약 테스트로 정직하게 유지한다

Google은 "the team that owns the real implementation should write and maintain a fake"라고 쓰고 fake의 충실도를 실제 구현과 fake 양쪽에 같은 테스트를 돌리는 계약 테스트로 검증하라고 한다 ([SWE at Google 13장](https://abseil.io/resources/swe-book/html/ch13.html)). 소유 팀이 fake를 제공하지 않으면 실제 구현이 바뀌어도 mock 기반 테스트를 고쳐야 한다는 신호가 어디에도 생기지 않는다 ([SWE at Google 14장](https://abseil.io/resources/swe-book/html/ch14.html)). 테스트 클래스 설계로 옮기면 추상 계약 테스트 클래스 하나와 구현별 하위 클래스(실제용, fake용)가 가장 직접적인 형태다. 외부 서비스를 대신하는 더블은 Fowler의 ContractTest로 감시한다. 이 테스트는 "check that all the calls against your test doubles return the same results as a call to the external service would"를 확인하며 외부 서비스의 변경 주기에 맞춰 보통 하루 한 번 돌린다. 실패해도 일반 테스트처럼 빌드를 깨지 않고 더블을 갱신하거나 서비스 소유자와 대화하는 계기로 쓴다 ([Fowler, ContractTest](https://martinfowler.com/bliki/ContractTest.html)). 서비스 사이에서는 소비자 테스트가 pact 파일을 만들고 제공자가 그것으로 API를 검증하는 소비자 주도 계약(CDC)이 쓰인다 ([Vocke, The Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html)).

### 피라미드·트로피·허니콤 논쟁은 "단위"의 정의 차이다

피라미드는 "Write tests with different granularity"와 "The more high-level you get the fewer tests you should have" 두 규칙으로 요약된다 ([Vocke](https://martinfowler.com/articles/practical-test-pyramid.html)). Kent C. Dodds의 테스팅 트로피는 JS 프런트엔드 맥락에서 "Write tests. Not too many. Mostly integration."을 내세운다 ([Dodds, The Testing Trophy](https://kentcdodds.com/blog/the-testing-trophy-and-testing-classifications)). Spotify의 허니콤은 마이크로서비스에서 전통적 피라미드가 "can be actively harmful"하다며 통합 테스트를 중심에 둔다 ([Spotify Engineering, Testing of Microservices](https://engineering.atspotify.com/2018/01/testing-of-microservices)). Fowler는 2021년에 이 논쟁 대부분이 단위 테스트 정의의 차이라고 정리했다. 허니콤 쪽의 "integration test"는 Fowler의 sociable 단위 테스트(실제 협력 객체와 함께 도는 테스트)와 비슷하므로 "This makes the pyramid versus honeycomb discussion moot."이다. Fowler는 Justin Searls의 말을 빌려 비율 논쟁 대신 "expressive tests that establish clear boundaries, run quickly & reliably, and only fail for useful reasons"에 집중하라고 결론짓는다 ([Fowler, On the Diverse And Fantastical Shapes of Testing](https://martinfowler.com/articles/2021-test-shapes.html)). Fowler는 무엇을 단위로 볼지도 "the team decides what makes sense to be a unit"라고 본다 ([Fowler, UnitTest](https://martinfowler.com/bliki/UnitTest.html)).

세 모양 모두 E2E 테스트는 최소로 두고 구현 세부에 묶인 테스트도 최소로 두라는 데 동의한다. 범위 선택 규칙으로는 Vocke의 두 문장이 가장 실용적이다. "If a higher-level test spots an error and there's no lower-level test failing, you need to write a lower-level test." 그리고 "Push your tests as far down the test pyramid as you can." 하위 테스트와 겹치며 추가 가치가 없는 상위 테스트는 지운다 ([Vocke](https://martinfowler.com/articles/practical-test-pyramid.html)).

### 통제하는 의존성은 진짜를 띄워서 테스트한다

애플리케이션 전용 DB는 mock 대신 실제 인스턴스로 테스트하라는 것이 Khorikov와 Spotify의 공통 입장이다. Spotify는 "We spin up a database, populate it, start the service, and query the actual API in the tests."라고 쓰고 저장 계층을 바꾸더라도 테스트 setup만 고치면 된다고 쓴다. 대가는 스위트가 "from milliseconds to a few seconds"로 느려지는 것과 실패 시 단언보다 스택 트레이스를 따라가야 하는 피드백 정확도 손실이다 ([Spotify Engineering](https://engineering.atspotify.com/2018/01/testing-of-microservices)). Vocke는 인메모리 DB를 "risky business"라 부르고 ([Vocke](https://martinfowler.com/articles/practical-test-pyramid.html)) Testcontainers는 H2에서는 되지만 Postgres에서 실패하는 SQL을 예로 들며 "In-memory services may not have all the features of your production service."라고 지적한다 ([Testcontainers, Introducing Testcontainers](https://testcontainers.com/guides/introducing-testcontainers/)). Google은 이 선택을 충실도(fidelity)와 밀폐성(hermeticity)의 긴장으로 설명한다. 실제에 가까울수록 시스템의 진짜 동작을 반영하지만 동시성과 인프라 불안정에 더 노출된다 ([SWE at Google 14장](https://abseil.io/resources/swe-book/html/ch14.html)). 다른 팀이나 타사가 소유한 서비스는 자기 소유 어댑터를 mock이나 fake로 대체하고 어댑터 자체는 좁은 통합 테스트와 계약 테스트로 검증하는 조합이 위 출처들과 모두 맞는다.

## 스위트는 운영 대상이다: 플래키는 격리하고 커버리지는 신호로 읽으며 낡은 테스트는 지운다

### 플래키 테스트는 크기에 비례해 늘고 대부분 태어날 때부터 불안정하다

Google의 2016년 글은 **전체 테스트 실행의 약 1.5%가** 플래키 결과를 냈고 **테스트의 약 16%가** 어느 정도 플래키했으며 post-submit CI에서 관찰한 통과→실패 전이의 약 84%에 플래키 테스트가 관여했다고 보고했다 ([Google Testing Blog, Flaky Tests at Google](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html)). 세 숫자는 분모가 다르다. 1.5%는 실행 기준, 16%는 테스트 목록 기준, 84%는 전이 기준이며 "실패의 84%가 플래키"라는 뜻이 아니다. 2017년 분석은 크기와의 관계를 보여 준다. 플래키 비율은 small 테스트 0.5%, medium 1.6%, large 14%였고 바이너리 크기와의 상관(r²)은 0.82였다. 결론은 "binary size accounts for larger deviations in flakiness than the tool you use"였다 ([Google Testing Blog, Where do our flaky tests come from?](https://testing.googleblog.com/2017/04/where-do-our-flaky-tests-come-from.html)). SWE at Google은 플래키 비율이 1%에 가까워지면 테스트가 가치를 잃기 시작한다고 쓴다 ([SWE at Google 11장](https://abseil.io/resources/swe-book/html/ch11.html)).

원인 연구로는 Luo 외(FSE 2014)가 기준점이다. 51개 Apache 프로젝트의 플래키 수정 커밋 가운데 분류 가능한 161개에서 **비동기 대기 45%, 동시성 약 20%, 테스트 순서 의존 약 12%로** 상위 세 원인이 77%를 차지했다. 플래키 테스트의 78%는 처음 작성될 때부터 플래키했다. 수정의 24%는 테스트 대상 코드 쪽을 고쳤고 그중 94%가 실제 버그였다. 그래서 저자들은 "Flaky tests should not simply be removed or disabled because they can help uncover bugs in the CUT."라고 결론짓는다 ([Luo et al., An Empirical Analysis of Flaky Tests](https://huang.isis.vanderbilt.edu/cs8395/paper/flakytest.pdf)). Microsoft의 2020년 연구도 비동기 호출을 주원인으로 확인했고 개발자가 고쳤다고 주장한 일부 수정이 실험에서는 플래키 빈도를 줄이지 못했다고 보고했다 ([Microsoft Research, A Study on the Lifecycle of Flaky Tests](https://www.microsoft.com/en-us/research/?p=671544)). 수정 후에는 반복 실행으로 효과를 확인해야 한다. Fowler는 2011년에 처방을 정리했다. 맨 sleep 대신 콜백이나 짧은 간격의 폴링과 넉넉한 타임아웃을 쓰고 시스템 시계는 감싸서 주입하며 원격 서비스는 테스트 더블과 주기적 계약 테스트로 대체한다 ([Fowler, Eradicating Non-Determinism in Tests](https://martinfowler.com/articles/nonDeterminism.html)).

### 업계는 탐지·격리·배정·복귀로 수렴했다

Fowler는 비결정적 테스트를 "a virulent infection that can completely ruin your entire test suite"라고 불렀다. 사람들이 실패를 조사하지 않게 되면 건강한 테스트의 실패까지 무시되기 때문이다. Fowler는 격리(quarantine)를 권하면서 상한을 두라고 했다. 예를 들어 8개 이하, 또는 한 주 이내다 ([Fowler 2011](https://martinfowler.com/articles/nonDeterminism.html)). 이후 업계 사례는 같은 구조로 수렴했다. 아래 표의 지표는 조직마다 분모가 다르므로 서로 직접 비교하면 안 된다.

| 조직(연도) | 지표와 분모 | 변화 | 핵심 장치 |
|---|---|---|---|
| GitHub (2020) | 플래키로 빨간 빌드가 난 커밋 비율 | 약 11개 중 1개 → 200개 중 1개 미만(18배) | 재시도 통과 시 자동 초록, 영향 점수, `git blame`과 CODEOWNERS로 이슈 자동 배정 |
| Slack (2022) | 테스트 잡 실패율 / main 안정성 | 56.76% → 3.85% / 19.82% → 96% | main에서만 실행 억제, 소유 팀 Jira 티켓, 주간 요약 |
| Spotify (2019) | 플래키 비율 | 6% → 4%(두 달) | 테스트별 속도·플래키 표 공개 |
| Atlassian (2025) | 플래키가 원인인 master 빌드 실패 비율 | 도입 전 Jira 프런트엔드 약 21%, 백엔드 약 15%. 최근 분기에 빌드 2만 2천여 건 복구 | 재실행 탐지와 베이즈 이력 점수, 건강해지면 자동 복귀 |

실패 사례도 교훈을 준다. Slack의 첫 버전은 플래키 *결과*를 걸러 잡을 통과시켰는데 진짜 실패가 main으로 새어 들어가고 실패 시작 시점이 가려져 되돌렸다. 두 번째 버전은 *실행*을 억제하고 소유 팀에 티켓을 배정했다. 그러나 억제한 테스트를 다시 켜기가 어려웠다는 응답이 26%였고 다음 단계로 자동 재활성화를 추가했다 ([Slack Engineering](https://slack.engineering/handling-flaky-tests-at-scale-auto-detection-suppression/)). Atlassian은 격리한 테스트도 브랜치·예약·격리 전용 파이프라인에서 계속 돌려 신호를 유지하고 정해진 기간 건강하거나 티켓이 해결되면 복귀시킨다 ([Atlassian Engineering](https://www.atlassian.com/blog/atlassian-engineering/taming-test-flakiness-how-we-built-a-scalable-tool-to-detect-and-manage-flaky-tests)). 이 사례들이 공유하는 절차는 다섯 단계다. 같은 코드 재실행과 이력 점수로 자동 탐지하고 병합 차단 경로 밖으로 격리하되 어딘가에서는 계속 실행한다. CODEOWNERS나 `git blame`으로 소유자와 기한이 있는 티켓을 배정한다. 건강해지면 자동 복귀시키고 격리 목록의 크기와 나이에 상한을 둔다. 추적 없이 "초록이 될 때까지 재시도"하는 방식은 Google 2016년 글, Slack의 첫 버전, Luo의 결과가 모두 버그를 숨긴다고 지적한다. 플래키의 78%가 태어날 때부터 불안정하므로 새 테스트나 바뀐 테스트를 병합 전에 여러 번 돌려 보는 것이 가장 싼 예방이다.

### 커버리지 60/75/90은 안내선이고 100%는 의심 신호다

Google은 2020년에 "at Google we offer the general guidelines of 60% as 'acceptable', 75% as 'commendable' and 90% as 'exemplary.'"라고 공개했다. 커밋 단위(diff) 커버리지는 99%가 합리적이고 90%가 좋은 하한이다. 같은 글은 "Focusing on getting the number as close as possible to 100% leads to a false sense of security"라고 경고하고 커버리지 데이터의 가치는 무엇이 덮였는지보다 무엇이 덮이지 않았는지를 보여 주는 데 있다고 쓴다 ([Google Testing Blog, Code Coverage Best Practices](https://testing.googleblog.com/2020/08/code-coverage-best-practices.html)). SWE at Google은 80% 같은 강제 기준이 더 올라가지 않는 천장이 되기 쉽다고 지적하고 대형 테스트가 수치를 부풀리므로 small 테스트로만 재라고 권한다 ([SWE at Google 11장](https://abseil.io/resources/swe-book/html/ch11.html)). Fowler는 좋은 테스트라면 "upper 80s or 90s"를 기대하되 100%에 가까우면 의심하고 절반 아래면 문제 신호로 본다. Brian Marick의 말도 인용한다. "I expect a high level of coverage. Sometimes managers require one. There's a subtle difference." 목표 수치를 정하면 사람들은 잘 깨지지 않는 코드에까지 테스트를 써서 숫자를 맞춘다. Fowler가 제시하는 더 나은 기준은 프로덕션으로 새는 버그가 드물고 버그가 무서워 코드 수정을 망설이는 일이 드문 상태다 ([Fowler, TestCoverage](https://martinfowler.com/bliki/TestCoverage.html)). 리뷰 화면에 커버리지를 보여 준 것만으로 커버리지가 약 10% 올랐다는 Google의 2014년 관찰은 수치를 가시화 도구로만 써도 효과가 있다는 증거다 ([Google Testing Blog, Measuring Coverage at Google](https://testing.googleblog.com/2014/07/measuring-coverage-at-google.html)).

### 뮤테이션 테스트는 변경분에만 돌릴 때 확장된다

Google 2020년 글은 커버된 줄이 제대로 검증되는지 보려면 뮤테이션 테스트가 더 나은 기법이라고 쓴다. Petrović 외(2021)는 2만 4천 명이 넘는 개발자와 1,000개가 넘는 프로젝트에서 이를 운영한 결과를 보고했다. 뮤턴트는 코드 리뷰에서 바뀐 줄에만, 커버된 줄당 하나씩, 변경 파일 수의 7배까지만 만든다. 흥미 없는 뮤턴트를 걸러 내는 "arid node" 규칙을 더해 변경당 뮤턴트 중앙값을 820개에서 7개로 줄였다. 리뷰 코멘트로 노출되어 피드백을 받은 뮤턴트 가운데 **전체 기간 평균 82%가 유용하다는 평가를 받았고 억제 규칙을 다듬기 전후로는 그 비율이 80%에서 89%로 올랐다.** 논문은 저장소 전체의 뮤테이션 점수를 일부러 보고하지 않는다. 계산 비용이 너무 크고 점수는 "neither concrete nor actionable"이기 때문이다 ([Petrović et al., Practical Mutation Testing at Scale](https://arxiv.org/abs/2102.11378)). 후속 연구는 뮤테이션 테스트에 노출된 개발자가 테스트를 더 많이 쓰고 살아남은 뮤턴트를 줄이도록 스위트를 개선했다고 보고했다 ([Petrović et al., ICSE 2021](https://arxiv.org/abs/2103.07189)). 기성 도구도 같은 방식을 흉내 낼 수 있다. StrykerJS의 기본 임계값 `{ high: 80, low: 60, break: null }`은 보고용 색 구간이며 `break`를 지정하지 않으면 빌드를 깨지 않는다 ([Stryker configuration](https://stryker-mutator.io/docs/stryker-js/configuration/)). `--incremental` 모드는 이전 결과를 재사용한다. 공식 예시에서는 3,965개 중 3,731개를 재사용했지만 의존성이나 환경 변수 변화는 감지하지 못하므로 주기적으로 `--force`를 돌려야 한다 ([Stryker incremental](https://stryker-mutator.io/docs/stryker-js/incremental/)).

### 크기 분류와 계층 실행이 피드백 속도를 지킨다

Google은 테스트를 범위(scope)와 별개로 크기(size)로 분류한다. small은 한 프로세스 안에서 돌며 sleep·I/O·블로킹을 금지하고 medium은 localhost까지만 허용하며 large는 여러 머신에 걸친다. 권장 구성은 대략 단위 80%, 통합 15%, E2E 5%이고 E2E가 많고 단위가 적은 "ice cream cone"과 통합이 비는 "hourglass"를 안티패턴으로 든다. 밀폐성의 기준은 "A test should contain all of the information necessary to set up, execute, and tear down its environment"이다 ([SWE at Google 11장](https://abseil.io/resources/swe-book/html/ch11.html)). Bazel은 크기를 기본 타임아웃(small 60초, medium 300초, large 900초, enormous 3600초)과 자원 예약에 연결해 크기 라벨을 실행 예산으로 만든다 ([Bazel, Test encyclopedia](https://bazel.build/reference/test-encyclopedia)). 2017년의 플래키 비율(small 0.5% 대 large 14%)을 함께 보면 대형 테스트를 병합 차단 경로에서 빼거나 더 엄격한 플래키 관리를 적용할 근거가 된다.

빠른 피드백의 다른 축은 선택 실행이다. Meta의 예측 테스트 선택은 변경과 테스트의 특징으로 학습한 모델로 테스트를 고른다. 변경된 코드에 전이적으로 의존하는 테스트의 약 3분의 1만 돌리면서도 결함 있는 변경의 99.9% 이상을 잡고 테스트 인프라 비용을 절반으로 줄였다 ([Machalica et al.](https://arxiv.org/abs/1810.05286), [Meta Engineering](https://engineering.fb.com/developer-tools/predictive-test-selection/)). 이런 확률적 선택은 작은 누락률을 비용과 맞바꾸므로 post-submit 전체 실행 같은 안전망이 필요하다. 순서 독립성과 밀폐성은 샤딩, 캐싱, 무작위 순서 병렬 실행, 테스트별 뮤테이션 분석의 전제 조건이다. Stryker의 `perTest` 분석도 테스트가 독립적으로, 무작위 순서로 돌 수 있어야 동작한다 ([Stryker configuration](https://stryker-mutator.io/docs/stryker-js/configuration/)).

### 리팩터링에 깨지는 테스트는 음의 가치를 가진다

SWE at Google 12장의 유지보수 원칙은 명확하다. 테스트는 "after it's written, it never needs to change unless the requirements of the system under test change"여야 한다. 순수 리팩터링이면 테스트가 바뀌지 않아야 하고 새 기능은 새 테스트만 필요하다. "Bug fixes typically shouldn't require updates to existing tests"이며 기존 테스트를 고쳐야 하는 정당한 경우는 행동 변경뿐이다. 이 원칙이 없으면 "test maintenance will inevitably consume a larger and larger proportion of the team's time" ([SWE at Google 12장](https://abseil.io/resources/swe-book/html/ch12.html)). Alex Eagle의 2015년 TotT 글은 mock 호출 순서를 검증하듯 코드를 그대로 옮겨 적은 change-detector 테스트가 "provide negative value"라고 판정한다. 결함은 못 잡고 유지 비용만 늘리기 때문이며 처방은 "These tests should be re-written or deleted."이다 ([TotT, Change-Detector Tests Considered Harmful](https://testing.googleblog.com/2015/01/testing-on-toilet-change-detector-tests.html)). André Arko는 2025년 글에서 "Confidence is the point of writing tests"라며 신뢰를 떨어뜨리는 테스트를 지우라고 주장한다. 대상은 플래키 테스트, 느려서 건너뛰는 테스트, 한 줄 변경에 150개를 고쳐야 하는 깨지기 쉬운 테스트, 바뀐 요구사항의 낡은 테스트다 ([Arko, You should delete tests](https://andre.arko.net/2025/06/30/you-should-delete-tests/)). Fowler도 테스트가 개발을 느리게 만든다면 너무 많이 테스트하고 있다는 신호로 본다 ([Fowler, TestCoverage](https://martinfowler.com/bliki/TestCoverage.html)).

삭제에는 반대 무게도 있다. Luo의 결과처럼 플래키 수정의 4분의 1이 실제 버그를 고쳤으므로 플래키 테스트는 소유자가 원인을 조사한 뒤에 지워야 한다. 이 출처들을 합치면 삭제·재작성 판단 규칙이 나온다. 순수 리팩터링에 깨지는 테스트, 다른 곳에서 이미 고정한 행동을 중복 검증하며 스위트를 느리게 하는 테스트, 폐기된 요구사항을 검증하는 테스트, 조사를 마쳤는데도 계속 플래키한 테스트가 대상이다. 가능하면 단순 삭제보다 더 작은 크기·범위의 테스트로 대체한다. 스위트 건강은 분모를 명시한 소수의 비율로 추적한다. 병합 차단 스위트의 실행 시간(p50/p95), 실행당 플래키 비율과 플래키로 인한 빨간 빌드 비율, 격리 목록의 크기와 나이, 팀별 미해결 플래키 티켓, 병합된 변경의 diff 커버리지 정도면 출발점으로 충분하다. 스위트 실행 시간의 목표치를 제시한 1차 출처는 이번 조사에서 찾지 못했다.

### JUnit은 package-private 클래스와 확장 모델이 관용형이다

JUnit 사용자 가이드는 "It is generally recommended to omit the `public` modifier for test classes, test methods, and lifecycle methods"라고 권하며 `private`만 금지한다 ([JUnit, Test Classes and Methods](https://docs.junit.org/6.1.3/writing-tests/test-classes-and-methods.html)). 기본 PER_METHOD 수명주기는 "unexpected side effects due to mutable test instance state"를 피하려고 존재한다. 그래서 인스턴스 필드에 픽스처를 두고 `@BeforeEach`로 채우는 방식이 안전한 기본형이다. PER_CLASS를 전역 기본값으로 바꾸는 설정을 두고 문서는 일관되게 적용하지 않으면 "can lead to unpredictable results and fragile builds"라고 경고한다 ([JUnit, Test Instance Lifecycle](https://docs.junit.org/6.1.3/writing-tests/test-instance-lifecycle.html)). `@Nested`는 non-static 내부 클래스로 만들며 바깥 `@BeforeEach`가 안쪽 테스트보다 먼저 실행되므로 안쪽 테스트 하나만 단독 실행해도 준비 과정이 보장된다 ([JUnit, Nested Tests](https://docs.junit.org/6.1.3/writing-tests/nested-tests.html)). `@DisplayNameGeneration`의 `ReplaceUnderscores`나 `IndicativeSentences` 생성기는 Khorikov식 문장형 이름을 보고서에 그대로 보여 준다 ([JUnit, Display Names](https://docs.junit.org/6.1.3/writing-tests/display-names.html)). 공통 동작은 추상 기반 클래스보다 `@ExtendWith`와 `@RegisterExtension` 확장으로 붙이는 편이 Jupiter의 설계 방향과 맞는다. 확장은 클래스 계층과 무관하게 조합되며 `static` 필드에 등록하면 `BeforeAllCallback` 같은 클래스 수준 API도 구현할 수 있다 ([JUnit, Registering Extensions](https://docs.junit.org/6.1.3/extensions/registering-extensions.html)). Maven에서 통합 테스트는 `mvn verify`로 돌린다. Failsafe는 `integration-test` 단계에서 빌드를 실패시키지 않아 `post-integration-test`의 환경 정리가 실행되도록 설계되어 있다 ([Maven Failsafe Plugin](https://maven.apache.org/surefire/maven-failsafe-plugin/)).

JUnit 5에서 6으로 올릴 때 깨지기 쉬운 지점도 문서에 나와 있다. Java 17 미만 런타임, JUnit 4용 `JUnitPlatform` 러너, `MethodOrderer.Alphanumeric`, Surefire/Failsafe 3.0.0 미만 지원이 사라졌다. `@TestMethodOrder`가 이제 `@Nested` 클래스로 상속되고 `@CsvSource` 파서가 FastCSV로 바뀌었으며 매개변수화 테스트 표시 이름이 `name = value` 형식에 텍스트 인자를 따옴표로 감싸게 됐다 ([JUnit 6.0.0 Release Notes](https://docs.junit.org/6.0.0/release-notes/)). 표시 이름을 비교하는 리포트 도구가 있다면 업그레이드 때 확인해야 한다.

### pytest는 함수와 픽스처가 기본이고 클래스는 묶음 용도로만 쓴다

pytest 문서가 드는 클래스의 이점은 묶음, 그 클래스 안에서만 쓰는 픽스처 공유, 마커 일괄 적용 세 가지다. 각 테스트는 클래스의 고유 인스턴스를 받는다. "Having each test share the same class instance would be very detrimental to test isolation." 다만 클래스 수준에 둔 속성은 클래스 속성이므로 테스트 사이에 공유된다 ([pytest, Get Started](https://docs.pytest.org/en/stable/getting-started.html)). 상태는 function scope 픽스처에 둔다. 정리는 `yield` 픽스처로 하고 정리는 설정의 역순으로 실행된다. 공식 문서의 "Safe teardowns" 지침은 **픽스처 하나에 상태 변경 하나와 그 정리만 묶으라**는 것이다. 여러 동작을 한 픽스처에 넣으면 중간에 실패했을 때 상태가 정리되지 않는다. 한 테스트에서 여러 객체를 만들어야 하면 데이터 대신 함수를 돌려주고 `yield` 뒤에서 만든 것을 지우는 "Factories as fixtures" 패턴을 쓴다 ([pytest, How to use fixtures](https://docs.pytest.org/en/stable/how-to/fixtures.html)). `conftest.py`에 둔 픽스처는 그 디렉터리와 하위 전체에서 쓸 수 있고 하위 레벨에서 같은 이름으로 재정의할 수 있으므로 JUnit의 확장이나 xUnit의 컬렉션 픽스처가 맡는 역할을 디렉터리 단위로 처리한다.

`parametrize` 값은 복사되지 않고 참조로 전달되므로 테스트가 list나 dict 인자를 바꾸면 다음 케이스에 영향을 준다 ([pytest, How to parametrize](https://docs.pytest.org/en/stable/how-to/parametrize.html)). 미등록 마커는 기본적으로 경고에 그치고 `strict_markers` 설정이나 `--strict-markers`를 켜야 오류가 된다 ([pytest, How to mark](https://docs.pytest.org/en/stable/how-to/mark.html)). 새 프로젝트의 무난한 조합은 `src/` 레이아웃, 최상위 `tests/`, `importlib` import 모드, `strict_markers`다. 기본 `prepend` 모드는 테스트 파일을 최상위 모듈로 import하므로 서로 다른 디렉터리에 있어도 파일 이름이 겹치면 안 된다. `__init__.py`로 우회하면 저장소 루트가 `sys.path`에 들어가 다른 도구와 충돌할 수 있다 ([pytest, Good Integration Practices](https://docs.pytest.org/en/stable/explanation/goodpractices.html)).

### Jest·Vitest·node:test는 목 초기화 기본값이 서로 다르다

세 러너는 `describe`/`it` 블록과 블록 범위 훅을 공유한다. Jest 문서는 최상위 훅이 파일 전체에, `describe` 안의 훅이 그 블록에만 적용된다고 설명하며 모든 `describe` 본문을 먼저 실행해 테스트를 수집한 뒤 테스트를 돌리므로 준비·정리 코드는 `before*`/`after*` 훅에 두라고 권한다. 테스트가 `test.only`로 혼자 돌 때는 통과하고 묶음에서 실패하면 공유 상태 간섭을 의심하라는 조언도 같은 페이지에 있다 ([Jest, Setup and Teardown](https://jestjs.io/docs/setup-teardown)). Vitest와 node:test도 같은 블록 API를 쓰지만 수집 단계 동작은 Jest 문서에서만 확인했다.

2026년 기준 가장 주의할 차이는 목 초기화 기본값이다. Jest 30은 `clearMocks`, `resetMocks`, `restoreMocks`가 모두 기본 false다. `clearMocks`는 호출 기록만 지우고 "This does not remove any mock implementation"이며 `restoreMocks`는 원래 구현까지 복원한다 ([Jest, Configuration](https://jestjs.io/docs/configuration)). **Vitest 5는 `clearMocks` 기본값을 true로 바꿨다** ([Vitest, Migration Guide](https://vitest.dev/guide/migration)). Jest에서 Vitest 5로 옮기면 호출 횟수 단언 결과가 달라질 수 있으므로 두 러너를 쓰는 팀은 설정 파일에 이 값들을 명시해 두는 편이 안전하다. Vitest는 concurrent 테스트에서 `restoreMocks`나 `mockReset`을 켜면 한 테스트의 종료가 진행 중인 다른 테스트의 목을 복원하거나 지울 수 있다고 경고한다 ([Vitest, restoreMocks](https://vitest.dev/config/restoremocks), [Vitest, mockReset](https://vitest.dev/config/mockreset)). `vi.setSystemTime`, `vi.stubGlobal`, `import.meta.env`는 자동으로 원복되지 않는다 ([Vitest, Mocking](https://vitest.dev/guide/mocking)). Vitest 5에서는 `vi.mock`을 함수나 `describe` 콜백 안에 두면 경고에 그치지 않고 오류가 난다. node:test의 `t.mock`은 그 테스트가 끝나면 자동 복원되고 전역 `mock`은 `mock.restoreAll()`로 직접 처리한다 ([Node.js, Test runner](https://nodejs.org/api/test.html)).

스냅샷은 Jest 공식 지침이 기준이다. "Commit snapshots and review them as part of your regular code review process."이고 스냅샷은 작고 집중적이어야 하며 플랫폼별 데이터나 비결정적 데이터를 담지 않아야 한다. ID나 날짜 같은 생성 값은 `expect.any(Date)` 같은 property matcher로 처리한다. 실패할 때마다 원인을 보지 않고 `-u`로 재생성하는 습관을 경계하라고 하며 "The aim of snapshot testing is not to replace existing unit tests"라고 못 박는다 ([Jest, Snapshot Testing](https://jestjs.io/docs/snapshot-testing)). Testing Library의 원칙 "The more your tests resemble the way your software is used, the more confidence they can give you."는 컴포넌트 인스턴스 대신 DOM 노드를 다루라는 구체적 지침으로 이어진다 ([Testing Library, Guiding Principles](https://testing-library.com/docs/guiding-principles)).

### xUnit.net은 공유를 타입으로 선언하게 한다

xUnit.net은 "creates a new instance of the test class for every test that is run"이므로 `[SetUp]` 대신 생성자를, `[TearDown]` 대신 `IDisposable`을 쓴다. 생성자는 async일 수 없어 비동기 준비는 `IAsyncLifetime`으로 하고 v3에서는 비동기 정리만 필요하면 `IAsyncDisposable`만 구현해도 된다. 공유는 범위별 타입으로 선언한다. `IClassFixture<T>`는 한 클래스의 모든 테스트가 인스턴스 하나를 공유하고 `ICollectionFixture<T>`는 `[CollectionDefinition]`으로 묶은 여러 클래스가 공유한다. v3의 `[assembly: AssemblyFixture(typeof(T))]`는 어셈블리 전체가 공유하며 컬렉션 픽스처와 달리 병렬화를 바꾸지 않아 동시에 사용될 수 있으므로 스레드 안전해야 한다 ([xUnit.net, Shared Context](https://xunit.net/docs/shared-context)). v3는 `MatrixTheoryData`로 데이터 세트의 모든 조합을 만들고 `TestContext.Current.CancellationToken`을 전달하지 않은 호출을 분석기 xUnit1051로 표시한다 ([xUnit.net v3, What's New](https://xunit.net/docs/getting-started/v3/whats-new)). NUnit은 반대로 기본이 단일 인스턴스 공유이며 3.13부터 `[FixtureLifeCycle(LifeCycle.InstancePerTestCase)]`로 테스트마다 새 인스턴스를 만들 수 있다. 이 모드에서는 `Parallelizable`과 함께 써도 인스턴스 필드가 병렬 테스트 사이에 공유되지 않는다 ([NUnit, FixtureLifeCycle](https://docs.nunit.org/articles/nunit/writing-tests/attributes/fixturelifecycle.html)). 병렬 실행을 켜는 NUnit 프로젝트라면 이 설정을 어셈블리 수준에 두는 것이 xUnit식 격리에 가깝다.

어느 프레임워크든 인스턴스를 매번 새로 만들어도 static 필드, 클래스 속성, 모듈 전역, 전역 목·타이머·환경 변수는 보호되지 않는다. 언어를 가리지 않고 가장 흔한 누수 경로가 이쪽이다. 병렬 실행을 켜는 순간 공유 픽스처의 스레드 안전성이라는 조건이 하나 더 붙는다.

## AI 에이전트가 더하는 테스트는 바뀐 행동의 양만큼만 늘어야 한다

조사한 출처 가운데 AI 코딩 에이전트를 직접 연구한 것은 없다. 아래 규칙은 사람 팀을 대상으로 나온 지침을 작업마다 테스트를 덧붙이는 에이전트에 옮긴 것이다. 위험의 구조는 단순하다. 작업 하나가 끝날 때마다 테스트가 더해지고 아무도 지우지 않으면 스위트는 행동의 변화와 상관없이 작업 횟수에 비례해 자란다. SWE at Google의 "unchanging tests" 기준을 적용하면 이 성장은 비정상이다. 리팩터링은 테스트를 바꾸지 않고 새 기능은 새 테스트를, 버그 수정은 기존 테스트를 고치지 않는 회귀 테스트 하나를 요구할 뿐이다 ([SWE at Google 12장](https://abseil.io/resources/swe-book/html/ch12.html)). 아래 표는 에이전트에게 줄 지시와 리뷰 기준이다.

| 규칙 | 근거 | 리뷰에서 확인할 것 |
|---|---|---|
| 모듈당 테스트 파일 하나에서 시작한다 | 프로덕션 클래스당 테스트 클래스 하나가 출발점이고 공유 시작 상태가 뚜렷할 때만 쪼갠다 ([Meszaros](http://xunitpatterns.com/Testcase%20Class%20per%20Class.html)). 발견 규칙은 생태계 관례를 따른다 ([pytest](https://docs.pytest.org/en/stable/explanation/goodpractices.html)) | 작업 번호나 이슈 이름을 딴 새 테스트 파일이 생기지 않았는가 |
| 바뀐 행동에만 테스트를 더한다 | unchanging tests ([SWE 12장](https://abseil.io/resources/swe-book/html/ch12.html)). 하위 테스트가 이미 잡는 오류를 상위 테스트로 중복 검증하지 않는다 ([Vocke](https://martinfowler.com/articles/practical-test-pyramid.html)) | 리팩터링 커밋에 테스트 변경이 없는가, 버그 수정에 회귀 테스트 하나만 붙었는가 |
| 제거한 행동의 테스트는 같은 변경에서 지운다 | change-detector는 "re-written or deleted" ([TotT 2015](https://testing.googleblog.com/2015/01/testing-on-toilet-change-detector-tests.html)), 낡은 요구사항 테스트는 삭제 ([Arko 2025](https://andre.arko.net/2025/06/30/you-should-delete-tests/)) | 삭제된 공개 API나 폐기된 요구사항을 가리키는 테스트가 그대로 있지 않은가 |
| DAMP를 DRY보다 앞에 둔다 | "lean more heavily toward DAMP" ([TotT 2019](https://testing.googleblog.com/2019/12/testing-on-toilet-tests-too-dry-make.html)). DAMP는 DRY를 보완한다 ([SWE 12장](https://abseil.io/resources/swe-book/html/ch12.html)) | 기대값의 원인이 본문에 보이는가, 새 헬퍼에 자체 테스트가 있는가 |
| 구조를 단언하고 문구는 비교하지 않는다 | 좁은 단언 ([TotT 2024](https://testing.googleblog.com/2024/04/prefer-narrow-assertions-in-unit-tests.html)), Sensitive Equality ([Meszaros](http://xunitpatterns.com/Fragile%20Test.html)), 작고 결정적인 스냅샷 ([Jest](https://jestjs.io/docs/snapshot-testing)) | 오류 메시지 전문·`toString`·큰 스냅샷 대신 필드·타입·상태 코드를 확인하는가 |
| 커버리지와 뮤테이션은 신호로 쓴다 | 60/75/90 안내선과 100% 경고 ([Google 2020](https://testing.googleblog.com/2020/08/code-coverage-best-practices.html)), 목표가 된 수치의 부작용 ([Fowler](https://martinfowler.com/bliki/TestCoverage.html)), 저장소 점수 대신 diff 뮤턴트 ([Petrović](https://arxiv.org/abs/2102.11378)) | 수치를 맞추려고 더한 테스트가 없는가, 살아남은 뮤턴트가 실제 빈틈을 가리키는가 |

몇 가지는 설명을 덧붙일 만하다. "모듈당 파일 하나"는 탐색 비용의 문제다. 같은 모듈의 테스트가 작업별 파일로 흩어지면 어느 행동이 이미 고정되어 있는지 찾기 어려워지고 그 결과 같은 행동을 다시 검증하는 테스트가 생긴다. 파일을 나누는 정당한 이유는 Meszaros가 말한 공유 시작 상태나 기능 단위이지 작업 단위가 아니다. "구조를 단언한다"는 규칙은 Sensitive Equality의 현대판을 겨냥한다. 자연어 오류 메시지 전문, 로그 문장, 렌더링된 HTML 전체를 그대로 비교하는 테스트는 문구 하나만 다듬어도 깨지고 행동은 아무것도 보장하지 않는다. 예외 타입, 오류 코드, 반환 객체의 필드처럼 요구사항이 정한 구조만 단언하면 Beck의 "Structure-insensitive"와 Google의 좁은 단언을 함께 만족한다. "커버리지는 신호"는 Marick의 구분이 그대로 적용된다. 커버리지 수치를 목표로 받은 쪽은 사람이든 에이전트든 잘 깨지지 않는 코드에까지 테스트를 써서 숫자를 맞춘다. diff 커버리지의 빈 줄과 살아남은 뮤턴트는 무엇을 더 테스트할지 알려 주고 저장소 전체 비율은 그러지 못한다.

플래키 예방도 에이전트 작업 흐름에 넣을 수 있다. 플래키 테스트의 78%가 처음부터 불안정했다는 Luo의 결과는 새로 쓴 테스트를 병합 전에 여러 번, 가능하면 무작위 순서로 돌려 보는 단계 하나로 대부분을 걸러 낼 수 있음을 뜻한다 ([Luo et al.](https://huang.isis.vanderbilt.edu/cs8395/paper/flakytest.pdf)). 플래키를 고쳤다고 주장할 때도 Microsoft 연구가 보여 주듯 반복 실행으로 효과를 확인해야 한다 ([Microsoft Research](https://www.microsoft.com/en-us/research/?p=671544)). 이 규칙들의 공통 전제는 삭제를 추가와 같은 등급의 정상 작업으로 다루는 것이다. 에이전트에게 테스트 추가를 지시하는 문서가 있다면 같은 자리에 삭제와 재작성 조건도 적어 두어야 한다.

## 결론

출처를 가로질러 보면 테스트의 비용은 개수보다 결합에서 나온다. 행동에 묶인 테스트는 요구사항이 바뀔 때만 움직이므로 수가 늘어도 유지 비용이 크게 늘지 않는다. 구현 구조나 사람이 읽는 문구에 묶인 테스트는 리팩터링마다 비용을 청구하고 버그는 거의 잡지 못한다. 그래서 스위트 관리의 핵심 질문은 "테스트가 충분한가"보다 "이 테스트는 사용자나 외부 시스템이 알아챌 변경에서만 실패하는가"이다. 이 질문에 답하지 못하는 테스트를 지우는 일은 정상적인 유지보수다. 작업 단위로 테스트를 생산하는 AI 에이전트 시대에는 이 관점이 스위트가 끝없이 커지지 않게 막는 필수 제동 장치다.

증거의 질도 고르지 않다는 점을 기억해야 한다. 플래키 테스트, 커버리지, 뮤테이션, 테스트 선택에는 대규모 정량 데이터가 있지만 이름 형식, DRY와 DAMP의 균형, 중첩 깊이, 테스트 클래스 상속은 경험과 의견에 기댄 지침이며 이를 잰 실증 연구는 이번 조사에서 나오지 않았다. Panichella 외의 결과처럼 스멜 카탈로그와 탐지기조차 실제 결함과 잘 맞지 않는다. 따라서 이 규칙들은 기본값으로 삼고 판정은 Searls의 기준, 즉 경계가 분명하고 빠르고 안정적이며 쓸모 있는 이유로만 실패하는가로 내리는 편이 맞다. 프레임워크 기본값도 Vitest 5의 `clearMocks`나 JUnit 6의 `@Nested` 순서 상속처럼 버전마다 바뀌므로 격리에 영향을 주는 설정은 저장소의 설정 파일에 명시해 두는 것이 업그레이드 비용을 줄이는 가장 값싼 방법이다.
