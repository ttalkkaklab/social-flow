ELEVENLABS

ElevenLabs TTS — the third speech lane

Plain REST behind an xi-api-key header: one POST returns audio bytes, the /with-timestamps twin returns base64 audio plus per-character timing, and /v1/text-to-dialogue voices a whole multi-speaker scene in one request. Paid and account-specific, so it is opt-in per channel — the two things it does that the other lanes can't are inline acting with audio tags on eleven_v3 and dialogue with up to 10 voices.

1. Models

The Models page lists five TTS-capable ids; this server exposes the four below plus the deprecated Turbo (still served, kept so an existing profile keeps working). Per-request caps come from the page's "Character limits" table.

model_idCharacterCap / requestAPI rateNotes
eleven_multilingual_v2Stable, lifelike — the vendor's convert default and this server's10,000$0.10 / 1KIgnores language_code (detects from text)
eleven_v3Most expressive; inline audio tags; the only dialogue model5,000$0.10 / 1KSlow by design (not realtime). Rejects previous_text/next_text (measured 400)
eleven_v3_conversationalv3 family tuned for realtime5,000 (applied — not in the vendor table)$0.05 / 1KAccepted by convert and with-timestamps (measured); dialogue rejects it with invalid_argument
eleven_flash_v2_5Fastest (~75 ms)40,000$0.05 / 1KHonors language_code; reads digits raw unless normalization is on
eleven_turbo_v2_5Deprecated → flash_v2_5 (spec marks it deprecated: true)40,000$0.05 / 1KFunctionally equivalent, higher latency

Not exposed: eleven_flash_v2 (English only — it answers Korean with a 200, which is the trap), the removed v1 models (zero occurrences in the live OpenAPI spec). Text-to-dialogue accepts eleven_v3 only — model_does_not_support_dialogue on multilingual_v2, invalid_argument on v3 conversational, both measured.

Why the default is multilingual_v2 and not v3. The vendor's own convert default is v2, with-timestamps on it is measured, the price is the same as v3, and v3 adds failure modes (Creative mode hallucinations, no neighbor-text context). v3 is routed by need: audio tags and dialogue. Same reasoning as the Supertonic lane matching the upstream CLI default — the same request should not sound different here.

Body fields and ranges: voice_settings.stability 0–1 (default 0.5; on v3 a 3-way mode — 0.0 Creative · 0.5 Natural · 1.0 Robust, other values are snapped), similarity_boost 0–1 (0.75), style 0–1 (0), use_speaker_boost (true), speed 0.7–1.2 (1.0); seed 0–4294967295; language_code ISO 639-1, honored by flash/turbo v2.5 and v3, ignored by multilingual_v2; pronunciation_dictionary_locators up to 3 (not exposed here yet). The tool names mirror these in camelCase.

3. Output formats and tier gates

The enum on the non-streaming endpoints has 28 values (29 on the live API — m4a_aac_44100_128 is accepted but absent from the spec): mp3 × 8, pcm × 7, wav × 7, opus × 5, ulaw, alaw. The streaming twins drop wav_* entirely. This server exposes the production-relevant subset.

FormatContent-Type (measured)PlanHere
wav_24000audio/wav — real RIFF, correct size fields, mono 16-bit, a LIST/INFO chunk before dataevery plandefault — the Gemini lane's spec, builder-ready
wav_16000 · wav_22050 · wav_48000audio/wavevery planexposed
wav_44100 · pcm_44100—Pro and above (403 output_format_not_allowed below, measured)wav_44100 exposed (matches Supertonic's 44.1 kHz on a Pro account)
mp3_44100_64/128/192audio/mpeg192 kbps is Creator and aboveexposed for non-pipeline use
pcm_* · opus_* · m4a · ulaw · alawaudio/pcm (container-less) · audio/opus (Ogg "OggS") · audio/mp4—not exposed — no place in the video pipeline
Why WAV, and why mp3 is not narration input. build-reel.sh sniffs the first four bytes of every narration file: RIFF is opened as a container, anything else is read as raw s16le 24 kHz PCM. An mp3 narration file therefore becomes noise on the timeline. The tool refuses a filename whose extension disagrees with the format for the same reason.

4. Timestamps and dialogue

with-timestamps

{
  "audio_base64": "UklGR…",                       // the audio in the requested format (RIFF when wav_*)
  "alignment":            { "characters": ["안","녕",…], "character_start_times_seconds": […], "character_end_times_seconds": […] },
  "normalized_alignment": { "characters": [" ","a","n","n","y","e","o",…], … },   // the vendor's normalized text
  "voice_segments": [ { "voice_id", "start_time_seconds", "end_time_seconds", "character_start_index", "character_end_index", "dialogue_input_index" } ]  // dialogue only
}
normalized_alignment romanizes Korean. 14 Hangul characters came back as 33 Latin ones ("annyeo…"), so it cannot index the source string. The sidecar <audio basename>.alignment.json keeps both objects verbatim; every summary the server prints reads alignment. On v3 the audio-tag characters ([whispers] ) are in the alignment too, with their own (near-zero) timings.

text-to-dialogue

Body: inputs: [{ text, voice_id }] (both required, nothing else per line), model_id (default and only eleven_v3), settings: { stability } — the spec's ModelSettingsResponseModel has that one property; use_speaker_boost and friends are ignored (measured 200 with a bogus field). Limits: at most 10 distinct voice_ids per request (the capability page's "no limit on speakers" is stale — build to 10), and the vendor asks for ≤ 2,000 characters in total for reliable generation; the hard cap is v3's 5,000. The measured voice_segments show a legacy voice id (Rachel 21m00…) mapped to a current id (eLDc7xhWxG2FElT3kUTj) — legacy ids still work but are rewritten.

5. Voices, keys, errors, limits

Voices are account-specific — GET /v2/voices (20 query params; this server uses page_size ≤ 100, search, category ∈ premade · cloned · generated · professional, include_total_count) returns voices[] with voice_id, name, category, labels {gender, age, accent, language, use_case, descriptive}, description, preview_url, verified_languages[], plus has_more/next_page_token. The legacy premade set (Rachel, George, …) retires 2026-12-31, and the help center adds an account-age gate: default voices are only available for accounts created before March 2026 — a new account sees the replacement set (Darian, Talia, Elara, … names only in the docs), so the 21 commonly circulated legacy ids that all answered 200 on 2026-08-23 did so on an older account. Listing with category: premade shows whichever set the account has. Voice Library voices are not usable via API on the Free plan. Korean quality tracks the voice, not the model — pin a voice_id in profile.md and never a display name.

Keys are permission-scoped (49 permission names in the spec): synthesis needs text_to_speech, the listing voices_read, the plan line user_read, GET /v1/models needs models_read. A restricted key fails with 401 missing_permissions that names the permission — the Mac mini key used for the measurements had text_to_speech only.

Response headers worth reading: character-cost (the vendor's metered quantity — below the raw count on every measured call: Korean 18 → 10, English 28 → 15), request-id, tts-latency-ms. The server reports all three.

6. Pricing and license

API usage is billed in dollars per 1,000 characters, the same on every plan (pricing/api, read 2026-08-23): $0.10 for multilingual_v2 and eleven_v3, $0.05 for flash/turbo and v3 conversational. Each plan includes a monthly character allowance on that meter (Free 10,000 · Starter $6 → 60,000 · Creator $22 → 220,000 · Pro $99 → 990,000 for the $0.10 models; double for the $0.05 ones). The "credits" tables on the main pricing page are the web-UI meter, not the API's. For the ledger: key tts.elevenlabs (v2·v3) or tts.elevenlabs-flash (flash·v3 conversational), quantity = character-cost ÷ 1000.

The Free plan has no commercial license ("cannot be used for any commercial purpose") and requires attribution — "elevenlabs.io" or "11.ai" in the title. Every paid plan includes a commercial license; Starter ($6) is the floor for a monetized channel. Voice Library voices, IVC and 192 kbps start at Starter/Creator; 44.1 kHz PCM/WAV at Pro.
