1. 베이스 URL과 버전

플랫폼베이스토큰 파일토큰 수명
Threadshttps://graph.threads.net/v1.0threads_token60일 (갱신형)

Graph API 최신 버전은 v25.0(2026-02)이다. 이 서버가 v23.0에 고정된 것은 결함이 아니다 — Meta 버전은 릴리스 후 약 2년간 유효하고 v23.0(2025-05)은 2027년까지 살아 있으며, 버전 고정은 상위 버전에서 파괴적 변경이 들어와도 게시가 조용히 깨지지 않게 하는 장치다. 다만 갱신 시점 판단을 위해 버전을 상수 한 곳에서만 관리해야 한다.

2. 컨테이너-후-게시 2단계

Threads와 Instagram은 미디어를 즉시 게시하지 않는다. 컨테이너를 만들고, 처리가 끝나기를 기다린 뒤, 별도 호출로 게시한다.

POST /{user-id}/threads      또는  /{ig-id}/media        → { id: creationId }
GET  /{creationId}?fields=status | status_code           → FINISHED 까지 폴링
POST /{user-id}/threads_publish 또는 /{ig-id}/media_publish?creation_id=…
플랫폼상태 필드값
ThreadsstatusIN_PROGRESS · FINISHED · PUBLISHED · ERROR · EXPIRED
Instagramstatus_code동일 5종. EXPIRED = 24시간 안에 게시하지 않음

이 서버는 2초 간격 최대 60회(2분) 폴링하고, ERROR/EXPIRED는 즉시 실패로 갈라 낸다 — 실패가 확정된 컨테이너를 2분간 기다리는 것은 낭비다.

게시 API는 비멱등이다. media_publish가 성공한 뒤 permalink 조회가 실패했다고 해서 전체를 재시도하면 같은 글이 두 번 게시된다. 이 서버는 permalink 조회 실패를 permalink: null로 낮춰 보고하고 게시 자체는 성공으로 반환한다.

3. Threads

항목플랫폼 계약이 서버
media_typeTEXT · IMAGE · VIDEO · CAROUSEL(2–20)TEXT · IMAGE만
본문 길이500자. 이모지는 UTF-8 바이트로 계산된다500자 (JS 문자 길이 기준)
이미지JPEG/PNG, 8MB 이하, 가로 320–1440px, 비율 최대 10:1공개 URL 1장 (플랫폼이 크롤)
영상MOV/MP4, H264/HEVC, 0–300초, 1GB 이하미지원
링크 카드link_attachment — media_type=TEXT 전용. 게시물당 링크 5개까지, 본문 URL과 같으면 1개로 계산linkUrl로 노출 (imageUrl과 배타 — 같이 오면 400)
답글reply_to_id를 단 새 게시물이 곧 답글 — 깊이 제한 없음replyToId로 노출
게시 쿼터24시간당 250건 (캐러셀은 1건)—
Threads 영상 미지원은 플랫폼 제약이 아니라 이 서버의 선택이다. 플랫폼은 VIDEO·CAROUSEL을 지원한다. 이 파이프라인은 쇼트폼 영상을 YouTube/IG 릴스로 내보내고, Threads에는 반말 구어체 본문 + 영상 링크 한 건으로 유입을 만드는 전략을 쓴다. 툴 설명이 이를 플랫폼 한계처럼 적으면 안 된다.

본문 링크 규칙(2026-08-15 개정): 영상 회차는 링크 없는 구어체 본문을 먼저 게시하고, IG 릴스 permalink 를 자기 답글로 단다 — 2026-08-14 의 "본문에 링크 1개" 방식을 철회한 것이다. 커버 이미지도 붙이지 않는다. 근거는 실측이다 — 본문 링크 글 2건이 조회 9·21 로 같은 날 링크 없는 글의 1/10 이었고, 답글 링크 글 2건은 257·623 이었다. 2024년의 본문 링크 페널티를 Mosseri 가 공개 철회했지만 우리 도달 분포는 반대로 나왔으므로 실측을 따른다. 링크는 YouTube 가 아니라 IG 릴스가 기본이다(같은 Meta 생태계라 이탈 손실이 가장 작다) — 게시 순서도 IG 먼저, permalink 를 받아 Threads 다. linkUrl(플랫폼 파라미터 link_attachment)은 API 능력 자체는 그대로여서, media_type=TEXT 전용이라 imageUrl과 배타이며 서버가 400으로 먼저 막는다. 해시태그는 랭킹 가중치가 0이라 1개 이하를 권한다.

항목플랫폼 계약
media_typeIMAGE · VIDEO · REELS · CAROUSEL · STORIES
캡션2,200자. 첫 125자가 접히기 전 훅. 캡션 내 링크는 클릭 불가
이미지JPEG만 — MPO·JPS 등 확장 포맷 거부
캐러셀최대 10개(이미지·영상 혼합 가능). 첫 항목 비율로 나머지를 강제 크롭(기본 1:1)
게시 쿼터24시간 이동 구간당 100건 (캐러셀은 1건)
게시 후 수정캡션만 가능 — 이미지 교체 불가

캐러셀 흐름

for 각 이미지:
  POST /{ig-id}/media?image_url=…&is_carousel_item=true   → childId
for 각 childId:
  GET /{childId}?fields=status_code                        → FINISHED 대기
POST /{ig-id}/media?media_type=CAROUSEL&children={id,id,…}&caption=…
POST /{ig-id}/media_publish?creation_id=…

자식 컨테이너를 전부 FINISHED로 만든 뒤 묶어야 한다. 하나라도 처리 중이면 CAROUSEL 생성이 실패한다.

릴스는 media_type=REELS + video_url 한 번이면 되고, imageUrls와는 배타다.

5. Facebook 페이지

형태엔드포인트비고
텍스트 (+링크)POST /{page-id}/feed message link—
이미지 ≤10장POST /{page-id}/photos (published=false) → /feed + attached_media[N]미게시 사진을 만들고 피드에 묶는다
영상POST /{page-id}/videos file_url description일반 영상 — 릴스가 아니다. 타임아웃 120초. 응답의 id가 곧 video_id
자막POST /{video-id}/captions captions_file default_localeSRT 파일 첨부(multipart/form-data) · 200K 상한
댓글POST /{post-id}/comments messagescope pages_manage_engagement

본문 길이는 사실상 넉넉하지만 이 서버는 5,000자로 제한한다. 댓글은 8,000자.

원문 링크는 본문이 아니라 첫 댓글로. 페이스북은 외부 링크가 붙은 게시물의 도달을 낮춘다. facebook_publish 성공 직후 응답의 postId를 facebook_comment에 넘겨 첫 댓글로 링크를 단다 — FB 댓글의 링크는 클릭 가능하고 프리뷰도 렌더된다. linkUrl은 미디어가 없는 텍스트 게시의 예외 경로로만 남겼다.
댓글만 실패했을 때 본문을 재게시하면 안 된다. facebook_comment만 재시도한다. 게시 API가 비멱등이라 본문 재시도는 중복 게시가 된다. 자막(captionWarning)도 같다.

자막은 영상과 따로 올린다

Meta 4종 중 Facebook만 자막 파일을 받는다. 영상 게시 응답의 id가 그대로 video_id라 곧바로 자막 엣지에 넘길 수 있다.

POST /{video-id}/captions
Content-Type: multipart/form-data

access_token=…
default_locale=ko_KR
captions_file=@caption.ko_KR.srt   ← 파일명이 계약이다
파일명이 로케일을 결정한다. <이름>.<locale>.srt 형식이 아니면 error 386으로 거부된다(ko_KR·en_US 꼴). 이 서버는 captionLocale을 정규식으로 검증하고 파일명을 직접 조립해 이 함정을 없앴다. 200K를 넘는 파일도 호출 전에 막는다.

FB는 file_url 영상을 비동기로 처리한다. 게시 직후 자막 호출이 처리 중 상태에 걸리면 실패할 수 있는데, 그때도 게시는 유효하므로 경고로만 보고하고 자막만 다시 올린다.

Instagram·Threads에는 자막 파일 경로가 없다. IG Content Publishing 컨테이너에 자막 파라미터가 없어서, IG 릴스는 화면에 자막을 태운 영상(video-sub.mp4)을 올리는 것이 유일한 방법이다. 그래서 이 파이프라인은 영상을 두 벌 만든다 — 클린 마스터는 YouTube·Facebook으로, 번인본은 Instagram으로.

받은 댓글 관리(sns_comment_*)가 흡수해야 하는 플랫폼 차이다. Meta 3종은 2026-07-26 토큰 실측, YouTube는 2026-08-11 편입 기준.

YouTube의 판정만 시각 기준인 이유. 다른 셋은 댓글마다 "우리 것인가"를 알려주는 필드가 있지만 YouTube에는 없다. 스레드 단위로 뭉뚱그리면 우리 답글 뒤에 붙은 새 댓글을 놓치고, 댓글 단위로만 보면 이미 답한 스레드에 또 답한다. 그래서 우리 마지막 답글보다 나중에 달린 것만 미응대로 잡는다. replies part가 5건만 주므로 잘렸으면 comments.list로 전체를 다시 받고, 그래도 불완전하면(100건 초과·조회 실패) 판정 근거가 없으니 응대됨으로 처리해 목록에서 뺀다 — 놓친 댓글은 다음 조회에 잡히지만 반대로 틀리면 중복 답글이 공개로 나간다.
YouTube는 2026-08부터 인박스·답글에 편입됐다(commentThreads.list + comments.insert). 다만 youtube.force-ssl 스코프가 있어야 하고, 게시용으로 발급한 토큰에는 없다 — 이때 인박스는 조용히 빼지 않고 skipped에 재발급 안내와 함께 실어 보고한다. "YouTube 댓글이 0건"과 "YouTube를 조회하지 못함"은 다른 사실이다.

숨김·좋아요는 여전히 YouTube를 지원하지 않는다. API가 주는 것은 의미가 다른 검토 보류/거부(setModerationStatus)뿐이라 "되돌릴 수 있는 숨김"으로 매핑할 수 없다 — 잘못 매핑하느니 명시적으로 거부한다.

인박스 설계

  • 기본값은 우리가 아직 답하지 않은 남의 댓글만이다. "이미 답했는가"를 추측이 아니라 플랫폼 필드로 판정하므로 중복 답글이 나가지 않는다.
  • 목록은 최신순으로 가져온다(reverse=true · order=reverse_chronological) — limit로 잘릴 때 남겨야 하는 건 오래된 댓글이 아니라 골든아워 댓글이다.
  • 각 댓글에 ageMinutes를, 요약에 withinGoldenHour(첫 60분 안 미응대 수)를 계산해 싣는다. 답글 속도가 확산을 좌우하므로 이 값이 우선순위 판단의 1순위 신호다.
  • Threads 목록에서 is_reply인 항목은 우리 자기 답글이라 인박스 루트에서 제외한다.
  • 플랫폼 하나가 실패해도 나머지는 그대로 반환하고 사유를 skipped에 싣는다 — 부분 실패가 전체를 막지 않는다.

모더레이션에 삭제가 없는 이유

숨김은 되돌릴 수 있고 작성자 본인에게는 계속 보여 마찰이 적은 반면 삭제는 비가역이다. 스팸·어뷰징 대응에는 숨김이 브랜드 리스크가 낮다. 정당한 비판·불만은 숨기지 않는다 — 숨김은 스팸·광고·혐오·개인정보 노출에만 쓴다.

7. 토큰과 계정 결정

게시 계정을 설정으로 받지 않는다. 토큰의 /me를 조회해 결정한다 — 계정 ID를 설정으로 받으면 토큰·계정 불일치(잘못된 계정으로 게시)의 여지가 생기는데, /me는 그 불일치가 구조적으로 불가능하다.

채널(브랜드) 2계층

<SNS_TOKEN_DIR>/<채널 slug>/threads_token   ← channel 인자 지정 시
<SNS_TOKEN_DIR>/threads_token                ← 미지정 시 (단일 채널·레거시)
채널 지정 시 기본 토큰으로 폴백하지 않는다. 폴백하면 채널 토큰이 없을 때 다른 브랜드 계정으로 조용히 게시되는 사고가 난다. 대신 사용 가능한 채널 목록을 담은 명시적 에러를 반환한다.

토큰 값은 환경변수로 받지 않는다. Meta의 60일 갱신 절차가 파일을 덮어쓰는 구조라 파일 기반이어야 갱신이 가능하고, 커밋 대상인 .mcp.json에 시크릿이 실리는 것도 막는다.

ListTools 시점에 자격증명 파일이 존재하는 플랫폼의 게시 툴만 노출된다. 요청 시점 평가라 토큰 파일 추가가 서버 재시작 없이 반영된다. 핸들러는 전부 유지되므로 숨은 툴을 직접 호출하면 명시적 토큰 부재 에러가 돌아온다.

플랫폼 자격증명은 전부 선택이다. Meta 3종의 토큰이 여는 것은 threads_publish·threads_insights·threads_search·instagram_publish·instagram_insights·facebook_publish·facebook_comment 일곱이고, 여기에 youtube_publish·youtube_insights를 더한 아홉이 게이트 대상이다(토큰이 하나도 없으면 tools/list 는 50 대신 41을 보여 준다). 토큰을 건너뛰면 제작까지는 그대로 돌아가고 — produce 가 완성 영상과 플랫폼별 문안을 data/<채널>/episodes/<주제>/output/ 에 쓰고 사람이 직접 올린다 — 게시·성장 절반만 못 쓴다. 플랫폼 단위라 YouTube 만 연결해 두는 구성도 된다.

9. Threads 성장 조회 (인사이트·키워드 검색)

grow-threads 스킬 전용 읽기 엔드포인트 2종 — threads_insights·threads_search 툴의 백엔드다. 2026-08-11 공식 문서(Insights · Keyword Search) 기준.

항목인사이트키워드 검색
엔드포인트계정 GET /{user-id}/threads_insights
게시물 GET /{media-id}/insights		GET /keyword_search (uid 불필요)
필요 스코프threads_manage_insightsthreads_keyword_search
주요 파라미터metric · since/until(unix 초)q · search_type=TOP|RECENT · search_mode=KEYWORD|TAG · since/until · limit(기본 25 최대 100)
쿼터일반 Graph 한도계정당 24시간 롤링 2,200회 — 결과 없는 쿼리는 미포함

계정 지표의 두 가지 응답 형태

  • views는 일 단위 시계열(values[]), likes·replies·reposts·quotes는 구간 합계(total_value)로 온다 — 서버가 { total, daily[] } / 스칼라로 정규화한다.
  • followers_count·follower_demographics는 since/until 미지원 — 서버는 followers_count 를 별도 호출로 분리한다(같은 요청에 섞으면 실패). demographics 는 팔로워 100명 미만이면 안 나오므로 미노출.
  • since/until 은 2024-04-13 이전으로 내려가지 않는다(플랫폼 제약).
  • 게시물 지표 views·shares는 문서상 "개발 중" — 오차 전제로 추이 판단에만 쓴다.

키워드 검색 실측 주의

  • 응답 필드: id,text,media_type,permalink,timestamp,username,has_replies,is_quote_post,is_reply — owner 필드는 없다.
  • 앱이 고급 접근 승인 전이면 인증된 자기 계정 게시물만 반환된다 — 검색이 "빈 결과"인 것과 "권한 부족"은 다른 사실이므로 grow-threads init 의 스코프 검증에서 걸러야 한다.
  • 민감·유해 키워드는 에러가 아니라 빈 배열로 온다 — 정상 동작이다.
  • 검색 결과 postId 에 reply_to_id 게시(= threads_publish 의 replyToId)로 남의 공개 글에 답글 참여가 가능하다 — 상대 계정의 답글 제한 설정에 막히면 게시 단계에서 플랫폼 에러가 돌아온다.
스코프는 재발급으로만 늘어난다. 게시용으로 발급한 기존 토큰에는 이 두 스코프가 없다 — refresh_access_token 갱신은 스코프를 바꾸지 못하므로, 동의 플로우에서 체크박스를 켜고 토큰을 새로 발급해야 한다. 서버는 스코프 부족 에러에 이 안내(token-setup.md)를 얹어 반환한다.

10. Instagram 성장 조회 (인사이트)

grow-instagram 스킬 전용 읽기 엔드포인트 — instagram_insights 툴의 백엔드다. 계정 구간 지표와 최근 미디어별 지표를 한 번의 툴 호출로 받아 정규화한다. 스코프는 instagram_business_manage_insights 하나다.

대상엔드포인트요청 지표
계정GET /{ig-user-id}/insightsreach · views · profile_views · accounts_engaged · total_interactions · likes · comments · shares · saves · profile_links_taps
미디어 공통GET /{media-id}/insightsviews · reach · likes · comments · shares · saved · total_interactions
릴스 전용같은 엔드포인트ig_reels_avg_watch_time · ig_reels_video_view_total_time · reels_skip_rate
피드 전용같은 엔드포인트follows · profile_visits

실호출로 확인한 함정 넷

  • metric_type=total_value 를 빼면 지표가 조용히 사라진다. views 처럼 시계열을 지원하지 않는 지표가 에러 없이 응답에서 빠진다 — 그래서 계정 지표는 전부 구간 합계로 요청한다.
  • 팔로워 수는 인사이트가 아니라 프로필 필드다. 인사이트의 follower_count 는 팔로워 100명 미만 계정에서 빈 배열을 돌려주므로 갓 만든 채널에서는 쓸모가 없다. 서버는 /me 의 followers_count 를 읽는다.
  • 계정은 saves, 미디어는 saved. 같은 뜻인데 단·복수가 다르다.
  • 릴스 지표와 피드 지표를 섞으면 응답 전체가 400 이다. 릴스에 follows·profile_visits 를 요청하면 does not support ... metric 으로 실패하고, 반대로 피드(이미지·캐러셀)에 릴스 3종을 요청해도 같다. 서버는 media_product_type 으로 갈라 붙인다.
reels_skip_rate 는 이 플랫폼에만 있다. 3초 미만 시청 확률을 랭킹 모델이 직접 예측하는데, 그 이탈률을 API 로 돌려주는 곳이 여기뿐이다. YouTube Analytics 에는 대응 메트릭이 없어 쇼츠 훅은 averageViewPercentage 로 우회한다(YouTube Data API 참조).
