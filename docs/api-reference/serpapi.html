SerpApi — 검색 결과 조회

Google 웹·뉴스·이미지와 Naver를 하나의 엔드포인트에서 engine 파라미터로 갈라 쓴다. 엔진마다 파라미터 이름과 정렬 값 체계가 다르다 — 같은 "최신순"이 엔진에 따라 1이기도 하고 dd이기도 하다.

1. 공통 계약

GET https://serpapi.com/search?engine={엔진}&api_key={키}&output=json&…
키가 URL 쿼리로만 전달된다. 타임아웃·도달 불가 같은 실패 경로는 URL을 에러 본문에 싣기 때문에, 마스킹하지 않으면 API 키가 그대로 LLM 컨텍스트에 들어간다. 이 서버는 밖으로 나가는 모든 텍스트에 api_key=[^&\s"']+ → api_key=*** 치환을 건다.

2. engine=google — 웹 검색

툴 serp_web_search

파라미터의미구현 노출
q검색어. site:·inurl:·intitle:·filetype: 연산자 지원○ — 툴 인자는 query
gl국가 코드 2자 (kr·us·vn)○
hl인터페이스 언어 코드○
location도시 단위 검색 기준지. uule·lat·lon과 병용 불가○
start결과 오프셋 — 페이지 번호가 아니다. 0부터 세며 10 단위로 페이지를 끊는다△ — page로 받아 (page-1)×10으로 환산
num이 엔진에서 무효 — SerpApi가 구글로 넘기지 않는다(아래)미전송. 툴 인자 limit(1–10)은 서버 슬라이스
tbs기간 필터 등 고급 필터△ — recency로 받아 qdr:h|d|w|m|y로 환산
google_domain·tbm·device·safe·no_cache·async도메인·검색유형·기기·세이프서치·캐시·비동기미노출
num은 이 엔진에서 무효다. SerpApi가 구글로 넘기지 않는다 — 실측(2026-08-11)으로 세 가지가 함께 확인된다.
  • 응답의 search_parameters에 num이 없다 (engine·q·google_domain·hl·gl·start·device만).
  • search_metadata.google_url에도 실리지 않는다.
  • serpapi_pagination.current가 start 0/10/20을 각각 1/2/3페이지로 센다 — 페이지 경계는 10 단위다(실제 organic_results는 광고·비디오 블록에 밀려 5~10건으로 흔들린다).
그래서 오프셋 단위를 limit에 연동하면 안 된다. limit=20을 20 배수로 잡으면 page=2가 구글 3페이지를 가리켜 2페이지(11~20번)가 통째로 사라진다. 오프셋은 항상 10 단위이고, limit 상한도 실제 페이지 크기인 10으로 맞췄다 — 지킬 수 없는 20을 약속하지 않는다.

결과의 position은 (page-1)×10을 더한 전역 순번으로 바꿔 싣는다. 원본은 페이지마다 1부터 다시 시작해서, 그대로 두면 2페이지의 1번이 1페이지의 1번과 같은 순위로 읽힌다. 전역 순번이면 구글이 페이지 경계에서 같은 링크를 재배치해도 모델이 알아본다.

슬리밍 대상 필드

원본 응답은 검색 1회에 20~60KB다. 근거로 쓸 수 있는 것만 남겨 2~4KB로 줄인다.

필드남기는 하위 키
search_information.total_results—
answer_boxtype title answer snippet link
knowledge_graphtitle type description source website
organic_resultsposition title link snippet date source
related_questionsquestion snippet link (상위 4개)

버려지는 것: 광고, 인라인 이미지·비디오, 페이지네이션 메타, serpapi_* 내부 링크, 썸네일 URL. 전부 사실검증에 기여하지 않으면서 응답의 대부분을 차지한다.

3. engine=google_news — 뉴스

툴 serp_news_search

파라미터의미구현 노출
q · gl · hl검색어 · 국가 · 언어○
so정렬 — 0=관련도(기본) · 1=날짜. q와 병용 불가미노출 (아래 경고)
topic_token·publication_token·story_token·section_token토큰 기반 탐색미노출
num · start없음 — 이 엔진은 오프셋 페이지네이션을 지원하지 않는다—
num이 없으므로 결과 수 제한은 서버 측 슬라이스다. limit은 요청 크기를 줄이지 않고 반환만 줄인다 — 과금은 동일하게 검색 1회다. 잘라낸 만큼은 응답 note로 알린다.
news_results의 첫 항목은 기사가 아니라 stories[]를 단 묶음일 수 있다. 실측(2026-08-11): {"position":1,"title":"주요 뉴스","stories":[4건]}. link가 없다고 버리면 그 안의 4건이 함께 사라지는데, 그것들이 응답에서 가장 최신이다 — 시효성 검증이 이 툴의 존재 이유인데 최상위 랭크의 최신 기사가 없어진다. 헤더는 벗기되 안의 기사는 평탄화해 살린다.

4. engine=naver — Naver

툴 serp_naver_search

파라미터값툴 인자
query검색어. NOT·OR·site: 지원query

page · start페이지 번호 · 오프셋page
sort_bywhere 에 따라 값 체계가 다르다 (아래)sort
period기간 필터 — 1h·1d·1w·1m·3m·6m·1yperiod — 오값은 400
num이미지 검색 전용, 기본 50(미전송해도 적용된다)num=10을 명시해 보폭과 같게 맞춘다 — 미전송하면 48건이 와서 보폭 10과 어긋나 38건이 중복됐다(실측)
page 보폭where마다 다르다 — 실측 web 15 · news 10 · video 48(네이버 자체 pagination이 start=49를 제시) · image 10SerpApi의 page 인자를 버리고 start를 직접 계산한다 (web 공식이 page=2를 무동작으로 만든다)
페이지네이션의 불변식은 "한 번에 오는 건수 = 보폭"이다. 어긋나면 조용히 겹치거나(청크 > 보폭) 빠진다(청크 < 보폭). image는 num으로 청크를 보폭에 맞추고, num이 안 먹는 where는 limit을 보폭으로 클램프한다(줄인 사실은 note에 싣는다).

where=video만은 보폭을 맞춰도 page 경계에서 10건 안팎이 겹친다 — 네이버가 페이지마다 결과를 재배치하기 때문이다(페이지 내부는 고유 48/48이고 경계도 이어지므로 보폭 계산 문제가 아니다). stateless 서버가 직전 페이지를 기억할 수 없으니 없애지 못하고, 응답 note로 "링크로 중복을 걸러내라"고 알린다.

sort_by는 where에 따라 값이 다르다.
where관련도최신오래된순
news0 (기본)12
그 외 (web 등)r (기본)dd—
where=news에 dd를 보내면 정렬이 적용되지 않는다. 에러가 아니라 조용히 무시되므로, 최신순으로 정렬됐다고 믿고 시효성 값을 뽑으면 오래된 기사를 최신으로 인용하게 된다.

결과 배열의 키 이름 — 문서와 실제가 다르다

SerpApi 문서는 where=web이 web_results를 준다고 적지만, 실제로 오는 것은 organic_results다(실측).
where문서실제 응답 키
webweb_resultsorganic_results (position title link displayed_link snippet related_results)
newsnews_resultsnews_results ✓
nexearch여러 배열web_results · ads_results · inline_images_results
imageinline_images_resultsimages_results (title original thumbnail width height source where link)
videoinline_videos_resultsvideo_results (position title link duration origin channel publish_date views thumbnail)
이 서버는 키 후보를 모두 확인한다. web_results만 읽던 구현은 기본 경로(where=web)에서 매번 "결과 없음"을 반환했고, 그 응답이 진짜로 결과가 없는 경우와 구분되지 않아 모델이 검색을 포기했다 — 에러도 예외도 없이 조용히 틀리는 부류의 결함이다. image·video도 같은 함정을 반복하지 않도록 실측 키를 먼저 보고 문서상 키로 폴백한다.
where=news는 날짜와 언론사를 news_info 하위에 중첩해 준다. 최상위 date·source만 보면 뉴스 결과에서 둘 다 사라진다 — 이 툴을 뉴스로 쓰는 이유가 시효성 검증이고 period·sort=latest를 붙이는 이유도 그건데, 정작 응답으로 정렬이 걸렸는지 확인할 수 없게 된다. 실제 구조(실측): news_info.news_date "2시간 전" · news_info.press_name "이데일리". 배열 키만 실측하고 항목 필드를 안 보면 이 함정을 반복한다.
스크린리더 라벨이 본문에 섞여 온다. where=video의 title·origin·channel 끝에 새 창 열림이 붙는다("너만몰라TV새 창 열림"). 스크래핑 원본의 접근성 텍스트인데, 남겨두면 모델이 채널명의 일부로 읽어 인용문에 그대로 복사한다. 서버가 제거한다.

5. engine=google_images — 이미지

툴 serp_image_search

레퍼런스 구도 조사, 실물 확인(제품·장소가 실제로 어떻게 생겼는지), 생성 프롬프트의 시각 근거 수집에 쓴다. 직접 만들 화면은 이 툴로 찾지 않고 생성한다 — 기본 경로는 무료·온디바이스인 image_local_generate이고, 글자가 들어가는 프레임이나 고품질이 필요한 자리는 gpt_image_text2img다. 생성물에는 권리 문제가 없다.

필터는 tbs로 조립하지 않는다. SerpApi가 전용 파라미터를 따로 받으며, 공식 문서상 이들이 tbs의 대응 성분(itp·ic·sur)을 덮어쓴다. 둘을 함께 보내면 어느 쪽이 이겼는지 응답만 봐서는 알 수 없다. 특히 종횡비는 예전 tbs=iar이 구글에서 중단돼 imgar로 바뀌었다.
라이선스를 지정하지 않은 결과는 권리 확인이 안 된 이미지다. 조사·확인 용도면 무지정으로 충분하지만, 게시물에 실을 소재를 찾는 중이라면 license를 반드시 건다 — commercial(상업 이용) 이상, 편집까지 하면 modify_commercial. 필터를 걸면 응답에 license_details_url이 실려 근거를 남길 수 있다.

슬리밍 대상

images_results에서 position title original(→imageUrl) thumbnail original_width/height source link license_details_url만 남기고, suggested_searches는 이름만 6개까지 싣는다. 버려지는 것: related_content_id·serpapi_related_content_link 같은 내부 링크, source_logo, 쇼핑 결과.

6. engine=google_trends_trending_now — 급상승 검색어

툴 serp_trending_now · sns_issue_scout(includeTrending)

"지금 이 나라에서 뭐가 뜨나"를 검색량·증가율과 함께 받는다. 검색어(q)가 없는 엔진이라 geo 로 나라를 고르고 hours 로 창을 정한다. 2026-08-18 실측(KR·24시간)으로 159건이 왔고 대부분 연예·사건 검색어였다 — 채널 주제와 겹치는 것만 시의성 소재로 본다.

슬리밍 대상

trending_searches[]에서 query search_volume(→searchVolume) increase_percentage(→increasePct) active start_timestamp(→startedAt ISO) categories[].name trend_breakdown(상위 8) 만 싣는다. 버려지는 것: news_page_token·serpapi_google_trends_link·serpapi_news_link·end_timestamp.

검색량·증가율은 구간 어림값이다. 2,000,000 · 1000% 처럼 구글이 반올림한 값이라 순위 비교로만 쓴다. Google Trends 의 것이므로 구글 검색 기준이지 SNS 참여 기준이 아니다.

sns_issue_scout — 같은 클라이언트를 조합한 스카우트

새 엔진이 아니라 engine=google 검색에 site:threads.com / site:x.com / site:instagram.com 을 붙여 플랫폼 × 시드마다 돌리고, 게시물 URL 을 정규화해 중복을 걷어낸 뒤 여러 글·여러 플랫폼에 같이 나오는 주제어를 세는 툴이다(구현 server/src/sns-issue-scout.ts). 급상승 검색어는 위 엔진으로 한 번 더 부른다. 크레딧 = 플랫폼 수 × 시드 수 × 페이지 수 + 1. 타임아웃·5xx 는 한 번 재시도하는데 같은 검색은 SerpApi 캐시가 받아 과금이 없다.

참여량이 없는 경로다. 좋아요·답글·조회는 구글 결과에 실려 오지 않고 순서도 관련도순이다. 그래서 결과는 "무엇이 터졌나"가 아니라 "이 주제로 지금 무엇이 오가나"의 언급 목록이며, youtube_topic_scout 의 채널 중앙값 배수와 같은 표에 섞으면 언급 수 12 가 배수 12 로 읽힌다. 스니펫이 본문과 다를 수 있다 — 스레드는 페이지의 자동 생성 주제 요약문이 스니펫으로 오기도 한다(실측 1건).

7. 에러와 쿼터

상황응답서버의 대응 지시
키 무효HTTP 401"키를 교정하기 전 재시도 금지 (401/400은 재시도해도 같은 결과)"
쿼터 소진HTTP 429"이번 세션에서는 추가 검색을 중단하고, 이미 확보한 근거 안에서만 저작하거나 미검증 주장을 본문에서 제외할 것"
결과 없음HTTP 200 + error 문자열툴 에러가 아니라 "빈 결과"로 취급. 결과 없는 검색은 과금되지 않는다
결과 없음이 200으로 온다는 게 함정이다. res.ok만 보고 파싱하면 빈 결과를 정상 응답으로 오해한다. 본문의 error 필드를 먼저 검사하고, 그 안에서도 "hasn't returned any results" 계열만 빈 결과로, 나머지는 진짜 에러로 갈라야 한다.

무료 플랜은 월 250회다. 검색 1회 = 크레딧 1건이므로 같은 검색을 반복하지 않는 것이 실질 쿼터를 좌우한다. 한국어 소재 리서치는 쿼터가 큰 Naver Open API(일 25,000회)를 먼저 쓴다.
