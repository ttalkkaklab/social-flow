Naver 검색 Open API

한국어 소재 리서치의 1차 도구. 일 25,000회 무료라 SerpApi(월 250회)보다 쿼터가 두 자릿수 크고, 국내 뉴스·블로그 후기·카페 여론은 Google 인덱스보다 이쪽이 정확하다.

1. 엔드포인트 8종

GET https://openapi.naver.com/v1/search/{엔드포인트}
X-Naver-Client-Id:     {클라이언트 ID}
X-Naver-Client-Secret: {클라이언트 시크릿}
type엔드포인트쓰임sortlimit 상한
news 기본news.json국내 뉴스 — 시효성 값(가격·시행일) 교차 검증sim·date30
blogblog.json블로그 후기 — 실사용 경험·체감sim·date30
webwebkr.json웹문서 — 공식 페이지·자료미지원30
cafecafearticle.json카페글 — 커뮤니티 여론·불만sim·date30
kinkin.json지식iN — 사람들이 실제로 모르는 것. 훅 문장의 재료sim·date30
imageimage.json이미지 — 국내 소재 레퍼런스sim·date30
encycencyc.json백과사전 — 자막에 쓸 용어 정의미지원30
locallocal.json지역 업체 — 주소·좌표·전화·카테고리random·comment5
공식 문서에 있는데 실제로는 죽은 API가 5개 있다. 네이버 공식 swagger(naver/naver-openapi-guide)는 book·book_adv·doc(전문자료)·shop(쇼핑)·movie(영화)를 여전히 싣고 있지만, 실호출은 전부 404 SE05 "존재하지 않는 검색 api"다(실측 2026-08-11). 문서만 보고 툴을 추가하면 죽은 툴이 된다 — 살아 있음을 확인한 8종만 노출한다.
타입마다 파라미터 표면이 다르고, 위반은 조용히 무시되거나 400이다.
  • web·encyc는 공식 문서상 sort 비적용 대상이다. 실호출은 400이 아니라 200을 주지만(실측), 그건 지원한다는 뜻이 아니라 조용히 무시한다는 뜻이다.
  • local은 sim/date가 아니라 random/comment 체계다. display를 10으로 올려도 5건만 오고, start를 넘겨도 같은 결과가 온다(페이징 없음).
  • filter(이미지 크기)는 image 전용이다.
잘못된 값이 에러 없이 무시되는 게 가장 위험하다 — 모델이 "최신순으로 정렬됐다"고 믿고 오래된 자료를 최신으로 인용한다. 그래서 서버가 호출 전에 거절한다.

자격증명은 헤더로만 전달된다. SerpApi와 달리 URL에 키가 실리지 않아, 에러 본문에 URL이 에코돼도 키가 새지 않는다.

동영상 검색은 이 API에 없다. 필요하면 serp_naver_search(where: "video")를 쓴다.

2. 파라미터

툴 인자API 파라미터·범위기본구현
queryquery필수1–300자
limitdisplay 1–100101–30으로 축소 (local은 5)
pagestart 1–1000 — 페이지가 아니라 항목 오프셋1(page-1)×limit+1로 환산. 상한 초과·local은 거절
sortsort — 타입별 값 체계 상이API 기본값타입이 지원하지 않으면 거절
imageSizefilter — all·large·medium·small—image 전용 — 다른 타입이면 거절

start 상한이 1000이라 한 검색어로 수집 가능한 최대 결과는 약 1,099건이다.

네이버 start는 페이지 번호가 아니다. 1부터 세는 항목 위치라서 page를 그대로 넘기면 page=2가 2번째 항목부터를 뜻해 결과가 겹친다(limit=3이면 3건 중 2건이 직전 페이지와 같다). 서버가 (page-1)×limit+1로 환산하므로 툴 사용자는 page를 페이지로만 생각하면 된다 — 이름이 같으면 뜻도 같아야 통일에 의미가 있다.
툴 인자 이름은 검색 툴 전체가 공유한다 — query·limit·page. 백엔드가 q·display·num·start 중 무엇을 쓰든 환산은 서버가 맡는다. 이름이 툴마다 흔들리면 모델이 툴을 갈아탈 때마다 인자를 다시 배우고, 그 비용은 잘못된 인자명 호출 → -32602 왕복으로 돌아온다. 계약 테스트가 이 규약을 강제한다.
display를 30으로 좁힌 것은 결함이 아니라 설계다. API 상한 100건을 그대로 받으면 응답이 LLM 컨텍스트를 크게 잠식하는데, 소재 리서치에서 31번째 결과가 판단을 바꾸는 일은 사실상 없다. 더 필요하면 start로 다음 페이지를 짚는 것이 옳다.

3. 응답과 정제

{
  "total": 12345,
  "start": 1,
  "display": 10,
  "items": [
    {
      "title": "<b>검색어</b>가 포함된 제목",
      "originallink": "https://…",
      "link": "https://n.news.naver.com/…",
      "description": "…<b>하이라이트</b>…",
      "pubDate": "Tue, 29 Jul 2026 09:00:00 +0900"
    }
  ]
}
원본 필드정제 후처리
titletitle<b> 태그 제거 + HTML 엔티티 복원
originallink / linklinkoriginallink 우선 — 네이버 뉴스 미러가 아니라 언론사 원문이 출처 표기에 맞다
descriptiondescription동일 정제
bloggername / cafenamesource타입에 따라 있는 쪽
pubDate / postdatedate타입에 따라 있는 쪽
sizewidth / sizeheightwidth / heightimage 전용 — link는 imageUrl로 개명(원본 이미지 URL임을 분명히)
mapx / mapycoordslocal 전용 — 107로 나눠 경위도 환산
total—local에서는 제거 (아래 경고)
address / roadAddress / telephone / category동명local 전용 — 그대로 보존
local의 total은 전체 업체 수가 아니다. 요청한 건수를 그대로 되돌려주는 값이다(실측: limit=2 → total:2, limit=3 → total:3). 그대로 실으면 모델이 "강남에 카페가 2곳"으로 읽으므로 아예 뺀다. 대신 상한·페이징 부재를 note로 항상 실어, 적은 결과를 검색 실패로 오해하지 않게 한다.
local의 좌표를 원본 그대로 흘리면 안 된다. mapx: "1269719531"은 소수점이 빠진 정수 문자열이다. 107로 나눠야 경도 126.9719531이 된다. 원본을 그대로 두면 모델이 이를 좌표로 오인해 엉뚱한 지점을 인용한다. 환산 결과가 한반도 범위를 벗어나면 좌표계 가정이 깨진 것이므로 추측값을 흘리지 않고 필드를 생략한다.

타입마다 응답 필드가 다르다 — image는 description이 아예 없고 thumbnail·크기가 오며, local은 주소·좌표·전화가 온다. 공통 슬리밍으로 뭉개면 지역 검색의 좌표가 통째로 사라지므로 타입별로 분기한다.

<b> 하이라이트를 남겨두면 모델이 이를 강조로 오해하거나 그대로 인용문에 복사한다. &quot;·&amp;·&lt;·&gt;·&apos;도 함께 복원한다.

4. 에러와 쿼터

상황응답서버의 대응 지시
키 무효 / 검색 API 미신청401 · 403"키를 교정하기 전 재시도 금지" + 앱 설정 링크
쿼터 소진429"일일 쿼터(25,000회) 소진 — 이번 세션에서는 WebSearch/serp_*로 대체할 것"
결과 없음200 + 빈 items"검색어를 바꿔 1회만 재시도하거나, 확인 실패한 주장은 본문에서 제외할 것"
403은 키가 틀린 게 아니라 "검색 API 사용 신청"이 안 된 앱일 수 있다. Naver Developers에서 앱을 만들어도 API별 사용 신청이 별도다. 에러 메시지가 이 둘을 함께 제시해야 모델이 엉뚱한 방향(키 재발급)으로 가지 않는다.
