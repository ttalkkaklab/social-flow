SerpApi — reading search results

Google web, news, and images plus Naver all come from one endpoint, split by the engine parameter. Parameter names and sort value schemes differ per engine — the same "newest first" is 1 on one engine and dd on another.

1. Shared contract

GET https://serpapi.com/search?engine={engine}&api_key={key}&output=json&…
The key only travels as a URL query param. Failure paths like timeouts and unreachable hosts put the URL in the error body, so without masking the API key lands straight in the LLM context. This server applies api_key=[^&\s"']+ → api_key=*** to every piece of text going out.

num is a no-op on this engine. SerpApi doesn't forward it to Google — measured 2026-08-11, and three things confirm it together.
  • The response's search_parameters has no num (only engine·q·google_domain·hl·gl·start·device).
  • It doesn't show up in search_metadata.google_url either.
  • serpapi_pagination.current counts start 0/10/20 as pages 1/2/3 — page boundaries fall every 10 (the actual organic_results wobbles between 5 and 10 items as ad and video blocks push things out).
So don't tie the offset unit to limit. Set the offset in multiples of 20 for limit=20 and page=2 points at Google's page 3, wiping out page 2 (items 11–20) entirely. The offset is always in units of 10, and the limit cap matches the real page size of 10 — no promising what can't be delivered.

Each result's position is rewritten as a global rank by adding (page-1)×10. The original restarts at 1 on every page, so left alone, page 2's #1 reads as the same rank as page 1's #1. With a global rank the model notices when Google reshuffles the same link across a page boundary.

What the slimming keeps

The raw response is 20–60KB per search. Keeping only what can be cited as evidence cuts it to 2–4KB.

FieldSub-keys kept
search_information.total_results—
answer_boxtype title answer snippet link
knowledge_graphtitle type description source website
organic_resultsposition title link snippet date source
related_questionsquestion snippet link (top 4)

Thrown away: ads, inline images and videos, pagination metadata, serpapi_* internal links, thumbnail URLs. None of it helps fact-checking, and all of it is most of the response.

3. engine=google_news — news

Tool serp_news_search

ParameterMeaningExposed as
q · gl · hlQuery · country · language○
soSort — 0=relevance (default) · 1=date. Can't be used with qNot exposed (warning below)
topic_token·publication_token·story_token·section_tokenToken-based browsingNot exposed
num · startAbsent — this engine has no offset pagination—
With no num, limiting the result count is a server-side slice. limit doesn't shrink the request, only what comes back — billing is one search either way. Whatever gets cut is disclosed in the response's note.
The first item in news_results may not be an article but a bundle carrying stories[]. Measured 2026-08-11: {"position":1,"title":"주요 뉴스","stories":[4 items]} (the title means "top news"). Drop it because it has no link and the 4 articles inside vanish with it — and those are the freshest items in the response. Recency checking is this tool's reason to exist, and the newest top-ranked articles were the ones disappearing. Peel off the header, flatten the articles inside, keep them.

page strideDiffers per where — measured: web 15 · news 10 · video 48 (Naver's own pagination proposes start=49) · image 10We ignore SerpApi's page argument and compute start ourselves (the documented web formula makes page=2 a no-op)
Pagination's invariant is "items per call = stride". When they diverge, pages silently overlap (chunk > stride) or skip (chunk < stride). For image we match the chunk to the stride with num; where num has no effect we clamp limit to the stride (and say so in note).

where=video alone still overlaps by about 10 items at page boundaries even with the stride matched — Naver reshuffles results per page (within a page it's a unique 48 of 48 and the boundaries do connect, so it isn't our stride math). A stateless server can't remember the previous page, so we can't remove it; the response's note says to dedupe by link.

sort_by takes different values depending on where.
whereRelevanceNewestOldest
news0 (default)12
everything else (web …)r (default)dd—
Send dd with where=news and the sort simply doesn't apply. It's silently ignored, not an error — so if you trust that results came back newest-first and pull recency facts from them, you end up citing old articles as new.

Result array key names — the docs and reality disagree

SerpApi's docs say where=web returns web_results, but what actually arrives is organic_results (measured).
whereDocsActual response key
webweb_resultsorganic_results (position title link displayed_link snippet related_results)
newsnews_resultsnews_results ✓
nexearchSeveral arraysweb_results · ads_results · inline_images_results
imageinline_images_resultsimages_results (title original thumbnail width height source where link)
videoinline_videos_resultsvideo_results (position title link duration origin channel publish_date views thumbnail)
This server checks every candidate key. An implementation that read only web_results returned "no results" every single time on the default path (where=web), and that response was indistinguishable from genuinely having no results, so the model gave up searching — the kind of defect that goes wrong quietly, with no error and no exception. To keep image and video out of the same trap, we read the measured key first and fall back to the documented one.
where=news nests the date and the outlet under news_info. Read only the top-level date and source and both disappear from news results — recency checking is the reason to use this tool as a news source, it's the reason to attach period and sort=latest, and yet the response gives you no way to confirm the sort applied. The real structure (measured): news_info.news_date "2시간 전" ("2 hours ago") · news_info.press_name "이데일리" (the outlet's name). Measure the array key but skip the item fields, and you walk into this one.
Screen-reader labels come mixed into the text. On where=video, title, origin, and channel end with 새 창 열림 ("opens in a new window") — as in "너만몰라TV새 창 열림". It's accessibility text from the scraped page, and left in, the model reads it as part of the channel name and copies it into citations. The server strips it.

5. engine=google_images — images

Tool serp_image_search

Use it to study reference compositions, check what something really looks like (a product, a place), and gather visual evidence for generation prompts. Frames you're going to make yourself aren't found with this tool, they're generated — the default path is the free on-device image_local_generate, and frames with text on them or anything needing high quality go to gpt_image_text2img. Generated output carries no rights problem.

Don't assemble these filters into tbs. SerpApi takes dedicated parameters for them, and the official docs say those override the matching tbs components (itp, ic, sur). Send both and the response won't tell you which one won. Aspect ratio especially: the old tbs=iar was discontinued by Google and became imgar.
Results with no license filter are images whose rights you haven't checked. For research or verification, no filter is fine — but if you're looking for material to put in a post, always set license: commercial or above, and modify_commercial if you'll edit it. With the filter on, the response carries license_details_url so you have the evidence on file.

What the slimming keeps

From images_results we keep position title original (→imageUrl) thumbnail original_width/height source link license_details_url, plus up to 6 suggested_searches names. Thrown away: internal links like related_content_id and serpapi_related_content_link, source_logo, shopping results.

6. engine=google_trends_trending_now — trending searches

Tools serp_trending_now · sns_issue_scout (includeTrending)

Answers "what's rising in this country right now", with search volume and rate of increase. The engine has no query (q), so you pick a country with geo and a window with hours. Measured 2026-08-18 (KR, 24 hours): 159 items, mostly celebrity and incident queries — only the ones overlapping your channel's subject count as timely material.

What the slimming keeps

From trending_searches[] we carry query search_volume (→searchVolume) increase_percentage (→increasePct) active start_timestamp (→startedAt, ISO) categories[].name trend_breakdown (top 8). Thrown away: news_page_token, serpapi_google_trends_link, serpapi_news_link, end_timestamp.

Search volume and increase are bucketed estimates. Values like 2,000,000 and 1000% are Google's own rounding, so use them for ranking comparisons only. And since they come from Google Trends, they're a Google-search measure, not an SNS engagement one.

sns_issue_scout — a scout built on the same client

Not a new engine. It runs engine=google searches with site:threads.com / site:x.com / site:instagram.com appended, once per platform × seed, normalizes post URLs to drop duplicates, then counts the topic words that show up across several posts and several platforms (implementation: server/src/sns-issue-scout.ts). Trending searches come from one extra call to the engine above. Credits = platforms × seeds × pages + 1. Timeouts and 5xx get one retry, and since it's the same search, SerpApi's cache serves it with no extra billing.

This path carries no engagement numbers. Likes, replies, and views don't come through Google results, and the ordering is by relevance. So the output isn't "what blew up" but a list of mentions — "what people are saying about this right now" — and putting it in the same table as youtube_topic_scout's channel-median multiples makes 12 mentions read as a 12× multiple. Snippets can also differ from the post body: on Threads, the page's auto-generated topic summary sometimes comes through as the snippet (measured once).

7. Errors and quota

SituationResponseWhat the server tells the model
Invalid keyHTTP 401"Do not retry before fixing the key (401/400 return the same thing on retry)"
Quota exhaustedHTTP 429"Stop searching for this session; write from the evidence already gathered, or drop unverified claims from the copy"
No resultsHTTP 200 + an error stringTreated as an empty result, not a tool error. Searches with no results are not billed
The trap is that "no results" arrives as a 200. Parse on res.ok alone and an empty result looks like a normal response. Check the body's error field first, and inside that, split off only the "hasn't returned any results" family as an empty result — everything else is a real error.

The free plan allows 250 searches a month. One search = one credit, so not repeating the same search is what really governs your effective quota. For Korean-language research, start with Naver Open API (25,000/day), which has far more room.
