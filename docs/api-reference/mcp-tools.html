1. Tool 정의 필드

MCP의 tools/list 응답에 실리는 Tool 객체의 필드다. SDK 1.30.0의 ToolSchema가 정본이다.

필드필수용도social-flow
name필수고유 식별자. 모델이 호출할 때 쓰는 이름사용
title선택사람에게 보여줄 표시 이름. 클라이언트 UI가 툴 목록·승인 창에 띄운다사용
description선택모델이 읽는 사용 설명. 사실상 프롬프트다사용
inputSchema필수인자 JSON Schema. type: "object" 고정사용
outputSchema선택구조화 결과의 JSON Schema. 선언하면 서버는 MUST 이에 맞는 structuredContent를 반환해야 한다SNS·성장 툴 17종에 사용
annotations선택동작 힌트 4종 + 표시용 title (아래 §2)전 툴 사용

_meta · icons선택구현별 확장 메타 · 아이콘미사용
outputSchema는 선언하면 계약이 된다. 스펙은 "Servers MUST provide structured results that conform to this schema"라고 못박는다. 실패 경로에서 structuredContent를 못 채울 가능성이 있으면 선언하지 않는 편이 낫다. 이 저장소는 성공 경로에서 항상 채워지는 필드만 required로 잡고, 실패는 isError: true + 텍스트로만 반환해 이 계약을 지킨다.

2. 동작 힌트(annotations)

클라이언트가 "이 호출에 사용자 확인을 받아야 하나"를 판단하는 근거다. 스펙은 이들을 힌트로 규정하고, 클라이언트는 신뢰할 수 없는 서버의 힌트를 믿어서는 안 된다고 경고한다 — 그러나 신뢰되는 서버가 이 필드를 비워두면 클라이언트는 위험한 툴과 안전한 툴을 구분할 수단을 잃는다.

힌트기본값의미
readOnlyHintfalse환경을 수정하지 않는다
destructiveHinttrue파괴적·되돌리기 어려운 갱신을 할 수 있다. readOnlyHint: false일 때만 의미가 있다
idempotentHintfalse같은 인자로 반복 호출해도 추가 효과가 없다. readOnlyHint: false일 때만 의미가 있다
openWorldHinttrue외부(인터넷 등) 열린 세계와 상호작용한다
title—표시 이름 (Tool 최상위 title의 구버전 위치)
이 서버에는 게시 전 검토 게이트가 없다 — 호출이 곧 공개다. threads_publish·instagram_publish·facebook_publish·facebook_comment·youtube_publish·youtube_update·sns_comment_reply·sns_comment_moderate 8종은 호출 즉시 외부에 반영되고, 그중 게시 API는 비멱등이라 재시도가 중복 게시를 만든다. 이 사실은 원래 각 툴의 description 산문으로만 적혀 있었다 — 즉 모델은 읽지만 클라이언트는 읽지 못하는 형태였다. 이제 destructiveHint: true + idempotentHint: false로 기계가 읽을 수 있게 선언한다.

3. CallToolResult 계약

비구조화 결과는 content[]에, 구조화 결과는 structuredContent에 담는다. 둘은 배타가 아니라 병행이다 — 스펙은 구조화 결과를 내는 툴도 하위호환을 위해 직렬화 JSON을 텍스트 블록으로 함께 실으라고 권한다(SHOULD).

콘텐츠 블록 종류

  • text — { type, text }
  • image — { type, data(base64), mimeType }
  • audio — { type, data(base64), mimeType }
  • resource_link — { type, uri, name, description?, mimeType? }
  • resource — 임베드된 리소스
생성 미디어를 base64로 돌려줄지, 경로만 돌려줄지. 이미지(gpt_image_*)는 image 블록으로 함께 반환한다 — 모델이 결과를 눈으로 보고 재생성 여부를 판단해야 하기 때문이다. 반면 영상·음성·음악은 경로만 반환한다: 수 MB짜리 base64는 컨텍스트를 태우는데 모델은 오디오·비디오를 어차피 직접 평가하지 못한다.

4. 에러 보고 2계층

계층형태쓰는 경우이 서버
프로토콜 에러JSON-RPC error알 수 없는 툴, 잘못된 인자, 서버 내부 오류SDK가 전송 계층에서 처리
툴 실행 에러result.isError: true + 텍스트API 실패, 입력 데이터 오류, 비즈니스 로직 실패index.ts가 모든 예외를 여기로 변환

실행 에러를 isError로 돌려주는 이유는 모델이 그걸 읽고 스스로 교정할 수 있어야 하기 때문이다. 프로토콜 에러로 던지면 모델은 실패 사실만 알고 원인을 못 본다. 이 서버는 zod 검증 실패도 필드 경로와 함께 실행 에러로 변환한다.

Invalid arguments — durationSeconds: 1080p resolution is only supported at 8s duration (requested: 4s).

5. 툴 작성 원칙 7가지

Anthropic의 Writing tools for agents에서 정리한 원칙과, 이 저장소가 각각을 어떻게 지키는지.

① 워크플로 단위로 통합하라

API 엔드포인트를 1:1로 감싸지 말고, 실제 작업 단위로 묶는다. list_users+list_events+create_event 대신 schedule_event 하나.

적용: instagram_publish 한 번이 /me 조회 → 자식 컨테이너 N개 생성 → 전부 FINISHED 폴링 → 캐러셀 묶기 → media_publish → permalink 조회까지 6단계를 처리한다. 모델은 캡션과 이미지 URL만 넘긴다.

② 네임스페이싱

서비스·리소스별 공통 접두어로 묶어 모델이 유사 툴을 구분하게 한다.

적용: serp_·naver_·datago_·gpt_image_·veo_·tts_·music_·sns_. 게시 툴만 플랫폼 이름을 앞에 둔다(threads_publish) — 게시는 플랫폼 선택이 곧 의사결정이라 접두어가 플랫폼이어야 모델이 헷갈리지 않는다.

③ 고신호 컨텍스트만 반환

기술적 식별자(UUID·MIME)보다 의미 있는 언어로. 유연성보다 관련성 우선.

적용: SERP 원본 JSON은 검색 1회에 20~60KB다. organic_results·answer_box·knowledge_graph·related_questions만 추려 2~4KB로 줄인다. sns_comment_inbox는 플랫폼별 필드명 차이를 흡수하고 ageMinutes·withinGoldenHour처럼 판단에 바로 쓰이는 파생값을 계산해 싣는다.

④ 토큰 효율 — 페이지네이션·필터·절단

기본값을 합리적으로 잡고, 잘렸으면 잘렸다고 실행 가능한 안내와 함께 알린다.

적용: datago_file_fetch는 12,000자에서 자르며 …(잘림 — limit 을 줄이거나 필요한 행만 page 로 짚어 조회할 것)을 덧붙인다. tts_*는 16,000자 대본을 그대로 반향하지 않고 길이만 돌려준다 — 이미 호출자가 보낸 문자열이라 정보가 0인데 컨텍스트만 태우기 때문이다.

⑤ 실행 가능한 에러 메시지

에러 코드가 아니라 "무엇을 어떻게 고치면 되는지"를 말한다.

적용: odcloud -4를 그대로 흘리지 않고 "이 API에 등록되지 않은 인증키 — 포털에서 활용신청(자동승인)을 먼저 해야 한다. 활용신청 전에는 datago_file_download(무인증)로 원본을 받는 것이 빠르다"로 번역한다. SerpApi 401/429는 "키를 교정하기 전 재시도 금지"·"이번 세션에서는 추가 검색을 중단"처럼 재시도 정책까지 지시한다.

⑥ 설명은 신입 온보딩처럼

암묵적 맥락을 명시하고, 파라미터 이름을 모호하지 않게(user가 아니라 user_id) 짓는다.

적용: 생성 툴 설명은 Use when… / Do NOT use… / Returns: 3부 구조를 고정한다. 이건 "무엇을 하는가"만 적은 설명이 유발하는 오선택을 막는다 — 모델이 veo_img2video를 써야 할 때 veo_text2video를 고르는 실패는 기능 설명이 아니라 경계 설명이 없어서 생긴다.

⑦ 체계적 평가

실제 워크플로 기반의 다단계 태스크로 평가하고, 정확도 외에 실행시간·호출 수·토큰·에러를 함께 본다.

적용(부분): 이 저장소는 server/test/contract.test.mjs로 정적 계약(스키마 유효성·라우팅 정합·힌트 일관성)을 자동 검증한다. 실제 모델을 돌리는 행동 평가(behavioral eval)는 아직 없다 — 게시 툴이 실호출로 공개 게시를 만들기 때문에 안전한 평가 하네스에는 드라이런 계층이 먼저 필요하다.

6. 평가 루브릭

이 저장소의 툴 품질 점수는 아래 5축 100점으로 계산한다. 감사 리포트가 이 루브릭으로 채점한 결과다.

P0(호출을 실패시키거나 사고를 만드는 결함)은 해당 축 점수를 0으로 내리고, P1은 항목당 감점, P2는 총평에만 반영한다.

7. 이 저장소의 적용 규칙

애매한 경계를 미리 못박아 툴이 추가될 때 판단이 흔들리지 않게 한다.

단일 출처 상수

목록형 값(TTS 음성 30종, 조성 13종, 생성 모드 3종)은 클라이언트 모듈의 상수 하나를 정본으로 두고 tools.ts의 JSON Schema enum과 zod enum을 파생시킨다. 목록을 스키마에 복사해두면 값이 추가될 때 한쪽만 고쳐지는 사고가 반드시 난다.

// tts-client.ts — 정본
export const TTS_VOICES = { Zephyr: 'Bright', /* …30종… */ } as const;
export const TTS_VOICE_NAMES = Object.keys(TTS_VOICES) as [VoiceName, ...VoiceName[]];

// tools.ts — 파생
enum: [...TTS_VOICE_NAMES]
// tts-client.ts — 파생
const voiceSchema = z.enum(TTS_VOICE_NAMES);
