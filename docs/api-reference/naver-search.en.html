NAVER OPEN API

Naver Search Open API

Naver is Korea's dominant search portal, and this is its official search API — the first tool for Korean-language research. The free tier allows 25,000 calls a day, two orders of magnitude above SerpApi's 250 a month, and for Korean news, blog reviews, and community opinion it beats Google's index. Responses come back in Korean, field names included.

Five APIs are in the official docs but dead in practice. Naver's official swagger (naver/naver-openapi-guide) still lists book, book_adv, doc (specialist documents), shop (shopping), and movie, but every real call returns 404 SE05 "존재하지 않는 검색 api" ("no such search api") — measured 2026-08-11. Add a tool from the docs alone and you ship a dead tool, so we expose only the 8 confirmed alive.
The parameter surface differs per type, and violations are either silently ignored or a 400.
  • web and encyc are documented as not taking sort. A real call answers 200 rather than 400 (measured), but that doesn't mean it's supported — it means it's silently ignored.
  • local doesn't use sim/date — it has its own random/comment scheme. Raise display to 10 and you still get 5, and passing start returns the same results (no paging).
  • filter (image size) is image-only.
The dangerous part is the wrong value being ignored without an error — the model believes results are sorted newest-first and cites old material as current. So the server rejects it before the call.

Credentials travel in headers only. Unlike SerpApi, the key never rides in the URL, so even when an error body echoes the URL nothing leaks.

This API has no video search. Use serp_naver_search(where: "video") when you need it.

With start capped at 1000, a single query can yield at most about 1,099 results.

Naver's start is not a page number. It's a 1-based item position, so passing page through directly makes page=2 mean "from the 2nd item" and the results overlap (at limit=3, two of the three repeat the previous page). The server converts with (page-1)×limit+1, so a tool user can just think of page as a page — the point of a shared name is that it means the same thing everywhere.
Every search tool shares the same argument names — query, limit, page. Whether the backend calls them q, display, num, or start, the server does the conversion. Let the names wobble per tool and the model re-learns the arguments every time it switches tools, and that cost comes back as wrong-argument calls and -32602 round trips. A contract test enforces the convention.
Narrowing display to 30 is a design decision, not a defect. Taking the API's full 100 eats a large slice of the LLM context, and in research the 31st result essentially never changes the conclusion. If you do need more, stepping through with start is the right move.

The sample values are Korean: the title reads "a title containing <b>the query</b>" and the description holds a <b>highlight</b>. Field names are English, but the content is not.

local's total is not the number of businesses. It echoes back however many you asked for (measured: limit=2 → total:2, limit=3 → total:3). Passed through, the model reads it as "there are 2 cafés in Gangnam", so we drop it entirely. Instead the response always carries a note about the cap and the missing paging, so a short result isn't mistaken for a failed search.
Don't let local's coordinates through raw. mapx: "1269719531" is an integer string with the decimal point removed; divide by 107 and it becomes longitude 126.9719531. Left raw, the model mistakes it for a coordinate and cites the wrong place. If the converted value falls outside the Korean peninsula, the coordinate-system assumption has broken, so we omit the field rather than emit a guess.

Response fields differ per type — image has no description at all and brings thumbnail plus dimensions, while local brings address, coordinates, and phone. One common slimming path would erase local search's coordinates, so we branch per type.

Leave the <b> highlights in and the model reads them as emphasis or copies them straight into a citation. &quot;, &amp;, &lt;, &gt;, and &apos; are restored along with them.

4. Errors and quota

SituationResponseWhat the server tells the model
Invalid key / search API not applied for401 · 403"Do not retry before fixing the key" + a link to the app settings
Quota exhausted429"Daily quota (25,000) exhausted — fall back to WebSearch/serp_* for this session"
No results200 + empty items"Retry once with a different query, or drop claims you could not verify from the copy"
A 403 may not mean a bad key — it may be an app that never applied for the search API. Creating an app on Naver Developers isn't enough; each API needs its own usage application. The error message has to offer both possibilities, or the model heads off in the wrong direction and reissues the key.
