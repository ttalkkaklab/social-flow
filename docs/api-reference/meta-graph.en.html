Meta Graph — Threads · Instagram · Facebook

The three platforms share Graph syntax, but their publish flows, length limits, and comment capabilities are all different. Comment capability in particular is badly asymmetric, and a cross-platform tool has to absorb that difference.

The latest Graph API version is v25.0 (2026-02). This server pinning v23.0 isn't a defect — Meta versions stay valid for about two years after release, so v23.0 (2025-05) lives until 2027, and pinning is what keeps publishing from quietly breaking when a newer version lands a breaking change. What it does require is keeping the version in one constant so the upgrade decision has a single place to happen.

2. Container, then publish

Threads and Instagram don't publish media immediately. You create a container, wait for processing to finish, then publish with a separate call.

POST /{user-id}/threads      or  /{ig-id}/media        → { id: creationId }
GET  /{creationId}?fields=status | status_code         → poll until FINISHED
POST /{user-id}/threads_publish or /{ig-id}/media_publish?creation_id=…
PlatformStatus fieldValues
ThreadsstatusIN_PROGRESS · FINISHED · PUBLISHED · ERROR · EXPIRED
Instagramstatus_codeThe same five. EXPIRED = not published within 24 hours

This server polls every 2 seconds up to 60 times (2 minutes) and splits ERROR/EXPIRED off as immediate failures — waiting two minutes on a container that's already doomed is wasted time.

The publish API is not idempotent. Retrying the whole thing because the permalink lookup failed after media_publish succeeded posts the same thing twice. This server downgrades a failed permalink lookup to permalink: null and reports the publish itself as a success.

No video on Threads is this server's choice, not a platform limit. The platform supports VIDEO and CAROUSEL. This pipeline sends short-form video out to YouTube and IG Reels, and uses Threads for a casual-register body post plus one link to the video to drive traffic. Tool descriptions must not write that up as a platform limitation.

Body-link rule (revised 2026-08-15): a video episode publishes a link-free casual-register body post first, then attaches the IG reel permalink as a self-reply — a retraction of the 2026-08-14 "one link in the body" approach. No cover image either. The grounds are field data: the two link-in-body posts drew 9 and 21 views, a tenth of the link-free posts from the same day, while the two reply-link posts drew 257 and 623. Mosseri publicly walked back the 2024 link penalty, but our measured reach distribution says otherwise, so we follow the measurements. The link defaults to the IG reel rather than YouTube (same Meta ecosystem, smallest exit penalty), which also fixes the publishing order: IG first, then take the permalink to Threads. linkUrl (platform parameter link_attachment) remains available as an API capability, still media_type=TEXT-only and mutually exclusive with imageUrl, blocked by the server with a 400. Hashtags carry zero ranking weight, so we recommend at most one.

  GET /{childId}?fields=status_code                        → wait for FINISHED

Body length is effectively generous, but this server caps it at 5,000 characters. Comments cap at 8,000.

The source link goes in the first comment, not the body. Facebook suppresses reach on posts carrying an external link. Right after facebook_publish succeeds, pass the response's postId to facebook_comment and put the link in the first comment — links in FB comments are clickable and still render a preview. linkUrl stays only as the exception path for text posts with no media.
When only the comment failed, don't republish the post. Retry facebook_comment alone. The publish API isn't idempotent, so retrying the post duplicates it. The same goes for captions (captionWarning).

Captions upload separately from the video

Of the four Meta surfaces, only Facebook accepts a caption file. The id in the video publish response is the video_id, so it goes straight to the captions edge.

POST /{video-id}/captions
Content-Type: multipart/form-data

access_token=…
default_locale=ko_KR
captions_file=@caption.ko_KR.srt   ← the filename is the contract
The filename decides the locale. Anything that isn't <name>.<locale>.srt is rejected with error 386 (locales look like ko_KR, en_US). This server validates captionLocale with a regex and assembles the filename itself, which removes the trap. Files over 200K are blocked before the call too.

FB processes file_url videos asynchronously. A caption call right after publishing can hit the still-processing state and fail — the post is valid regardless, so we report a warning and re-upload only the captions.

Instagram and Threads have no caption-file path at all. The IG Content Publishing container has no caption parameter, so for IG reels the only way is uploading a video with the subtitles burned into the picture (video-sub.mp4). That's why this pipeline builds two copies of every video — the clean master goes to YouTube and Facebook, the burned-in copy to Instagram.

6. Comment capability asymmetry

These are the platform differences that received-comment management (sns_comment_*) has to absorb. The three Meta surfaces were measured against live tokens on 2026-07-26; YouTube joined on 2026-08-11.

Why only YouTube's verdict is time-based. The other three give you a per-comment field saying whether it's ours; YouTube has none. Lump it together per thread and you miss new comments that landed after our reply; go strictly per comment and you answer a thread you already answered. So only comments newer than our last reply count as unanswered. The replies part only returns 5, so when it's truncated we re-fetch the whole thread with comments.list; if it's still incomplete (over 100, or the lookup failed) there's no basis for a verdict, so we treat it as answered and drop it from the list — a missed comment shows up on the next pass, whereas the opposite error posts a duplicate reply in public.
YouTube joined the inbox and replies in 2026-08 (commentThreads.list + comments.insert). It needs the youtube.force-ssl scope, which a token issued for publishing doesn't have — in that case the inbox isn't silently skipped; it's reported under skipped with reissue instructions. "YouTube has 0 comments" and "we couldn't read YouTube" are different facts.

Hiding and liking still aren't supported on YouTube. What the API offers is held-for-review / rejected moderation (setModerationStatus), which means something different and can't be mapped onto "a reversible hide" — better an explicit refusal than a wrong mapping.

How the inbox is designed

  • The default is other people's comments we haven't answered yet. "Have we answered?" comes from a platform field rather than a guess, so no duplicate replies go out.
  • Listing is newest first (reverse=true · order=reverse_chronological) — when limit truncates, what has to survive is the golden-hour comments, not the old ones.
  • Each comment carries ageMinutes, and the summary carries withinGoldenHour (unanswered comments inside the first 60 minutes). Reply speed drives distribution, so that number is the first signal for prioritizing.
  • Items marked is_reply in a Threads listing are our own replies, so they're excluded from the inbox roots.
  • If one platform fails the rest still come back, with the reason in skipped — a partial failure doesn't block everything.

Why moderation has no delete

Hiding is reversible and stays visible to the author, so it creates little friction; deleting can't be undone. For spam and abuse, hiding carries less brand risk. Legitimate criticism and complaints don't get hidden — hiding is for spam, ads, hate, and exposed personal data only.

7. Tokens and account resolution

The publishing account isn't configured. We resolve it by calling the token's /me — configuring an account ID leaves room for token/account mismatch (publishing to the wrong account), and /me makes that mismatch structurally impossible.

Two layers for channels (brands)

<SNS_TOKEN_DIR>/<channel slug>/threads_token   ← when the channel argument is given
<SNS_TOKEN_DIR>/threads_token                   ← when it isn't (single-channel / legacy)
With a channel specified there is no fallback to the flat token. Fall back, and a missing channel token quietly publishes to a different brand's account. Instead we return an explicit error listing the channels that are available.

Token values don't come from environment variables. Meta's 60-day renewal overwrites the file, so it has to be file-based for renewal to work, and it also keeps secrets out of the committed .mcp.json.

At ListTools time, only platforms with a credential file present get their publish tools exposed. It's evaluated per request, so adding a token file takes effect without restarting the server. All handlers stay registered, so calling a hidden tool directly returns an explicit missing-token error.

Platform credentials are entirely optional. The three Meta tokens unlock seven tools — threads_publish, threads_insights, threads_search, instagram_publish, instagram_insights, facebook_publish, facebook_comment — and with youtube_publish and youtube_insights that's the nine gated tools (with no tokens at all, tools/list shows 37 instead of 46). Skip them and everything through production still works: produce writes the finished video plus per-platform text into data/<channel>/episodes/<topic>/output/ and you upload by hand. Only the publish and growth half is unavailable. It's per platform, so a YouTube-only setup is a valid configuration.

9. Threads growth reads (insights · keyword search)

Two read endpoints used only by the grow-threads skill — the backends of the threads_insights and threads_search tools. Based on the official docs as of 2026-08-11 (Insights · Keyword Search).

ItemInsightsKeyword search
EndpointAccount GET /{user-id}/threads_insights
Post GET /{media-id}/insights		GET /keyword_search (no uid needed)
Scope requiredthreads_manage_insightsthreads_keyword_search
Main parametersmetric · since/until (unix seconds)q · search_type=TOP|RECENT · search_mode=KEYWORD|TAG · since/until · limit (default 25, max 100)
QuotaNormal Graph limits2,200 per rolling 24 hours per account — queries with no results don't count

Account metrics come in two response shapes

  • views arrives as a daily time series (values[]), while likes, replies, reposts, and quotes arrive as period totals (total_value) — the server normalizes them into { total, daily[] } and scalars.
  • followers_count and follower_demographics don't take since/until — the server splits followers_count into its own call (mixed into the same request, it fails). Demographics don't appear below 100 followers, so they aren't exposed.
  • since/until can't reach further back than 2024-04-13 (platform limit).
  • The post metrics views and shares are documented as "in development" — assume error and use them for trends only.

Keyword search, measured

  • Response fields: id,text,media_type,permalink,timestamp,username,has_replies,is_quote_post,is_reply — there is no owner field.
  • Before the app has advanced access, only the authenticated account's own posts come back — "empty results" and "insufficient permission" are different facts, so grow-threads init has to catch it in its scope check.
  • Sensitive or harmful keywords return an empty array rather than an error — that's normal behavior.
  • A postId from search results can be replied to by publishing with reply_to_id (threads_publish's replyToId), which is how you join someone else's public conversation — if their reply restrictions block it, the platform error comes back at the publish step.
Scopes only grow by reissuing. A token issued for publishing doesn't carry these two — refresh_access_token renewal can't change scopes, so you have to tick the boxes in the consent flow and issue a new token. The server attaches that guidance (token-setup.md) to insufficient-scope errors.

10. Instagram growth reads (insights)

The read endpoint used only by the grow-instagram skill — the backend of the instagram_insights tool. It fetches account-period metrics and per-media metrics for recent posts in one tool call and normalizes them. The scope is a single one, instagram_business_manage_insights.

TargetEndpointMetrics requested
AccountGET /{ig-user-id}/insightsreach · views · profile_views · accounts_engaged · total_interactions · likes · comments · shares · saves · profile_links_taps
Media (common)GET /{media-id}/insightsviews · reach · likes · comments · shares · saved · total_interactions
Reels onlySame endpointig_reels_avg_watch_time · ig_reels_video_view_total_time · reels_skip_rate
Feed onlySame endpointfollows · profile_visits

Four traps found by calling it for real

  • Leave out metric_type=total_value and metrics vanish silently. Metrics like views that don't support a time series drop out of the response with no error — so account metrics are all requested as period totals.
  • Follower count is a profile field, not an insight. The insights follower_count returns an empty array on accounts under 100 followers, which makes it useless on a fresh channel. The server reads followers_count from /me instead.
  • Accounts say saves, media say saved. Same meaning, different number.
  • Mix reels metrics with feed metrics and the whole response is a 400. Ask a reel for follows/profile_visits and it fails with does not support ... metric; ask a feed post (image or carousel) for the three reels metrics and it's the same. The server splits them by media_product_type.
reels_skip_rate exists only on this platform. The ranking model directly predicts the probability of a sub-3-second view, and this is the only API that hands that drop-off rate back. YouTube Analytics has no equivalent metric, so Shorts hooks are judged through averageViewPercentage instead (see YouTube Data API).
