Seedance 인물·자산 정책

Dreamina Seedance 2.x 는 얼굴이 든 입력 이미지를 거부한다. 다만 막다른 길이 아니라 다른 문으로 가라는 뜻이다 — 신뢰 출력물 재사용, 프리셋 디지털 캐릭터, 권리 확보 실인물 자산 셋이 열려 있다. 이 문서는 그 셋의 조건과 절차, 그리고 참조 이미지를 콘티처럼 쓰면 왜 깨지는지를 정리한다.

1. 실측 — 무엇이 막히고 무엇이 통하나

dreamina-seedance-2-0-260128 으로 세 번 찔러 경계를 확인했다(2026-08-15). 거부는 태스크 생성 단계에서 떨어지므로 과금이 없다 — 경계를 재는 실험은 공짜다.

막는 건 사람이 아니라 얼굴이다. 실사 인물이 찍혀 있어도 얼굴이 안 보이면 들어간다. 그리고 AI 가 만든 얼굴에도 같은 필터가 걸린다 — 위 1행의 이미지는 실존 인물이 아니라 이 모델이 방금 생성한 얼굴이었다.
모델 출력물이라고 아무렇게나 다시 넣을 수는 없다. 위 1행이 거부된 이유가 여기 있다 — ffmpeg 로 프레임을 뽑아 다시 인코딩한 순간 “원본 출력물”이 아니게 된다. 신뢰 경로의 조건은 §2 에서 다룬다.

2. 우회로 셋

공식 문서가 제시하는 해결책이 셋이다. 성격이 서로 다르므로 쓸 자리도 다르다.

2-1. 신뢰 출력물 재사용 — 우리가 만든 얼굴을 다시 넣는다

ModelArk 는 같은 계정이 이 플랫폼에서 만든 얼굴 있는 출력물을 30일간 신뢰한다. 그 기간 안에는 검열에 걸리지 않고 2.5·2.0 의 입력으로 다시 들어간다.

신뢰되는 출력물적용 시작유효기간
2.5 · 2.0 계열이 만든 얼굴 있는 영상2026-03-11생성 시각부터 30일
그 영상의 마지막 프레임 이미지2026-04-1630일
Seedream 5.0 lite 텍스트→이미지의 얼굴 있는 결과물2026-04-1630일

조건이 빡빡하다. 같은 플랫폼·같은 계정이어야 하고, 2차 편집을 거치면 신뢰가 깨진다. 압축이나 전달만으로도 검증이 무효가 될 수 있어, 문서는 원본을 BytePlus TOS 에 그대로 저장해 두라고 권한다. 신뢰는 입력에만 적용되므로 출력이 보안 검열에서 떨어지는 건 별개다.

우리 파이프라인에는 세 번째 줄이 가장 쓸모 있다. 원하는 인물을 Seedream 5.0 lite 로 만들어 두면 그 이미지가 곧바로 2.0 의 reference_image 로 들어간다 — 얼굴 검열과 컷 간 인물 일관성이 한 번에 풀린다. 30일 안에 그 회차를 끝내면 된다.

2-2. 프리셋 디지털 캐릭터 — 특정 인물일 필요가 없을 때

플랫폼이 공용 디지털 캐릭터 라이브러리를 무료로 제공한다. 자산마다 ID 가 있고 asset://<asset ID> 를 URL 자리에 넣어 쓴다. 실사풍 얼굴은 필요하지만 특정 인물이어야 할 이유가 없는 자리에 맞는다.

{
  "type": "image_url",
  "image_url": { "url": "asset://asset-20260410114236-8cdfz" },
  "role": "reference_image"
}
프롬프트에서 asset ID 를 그대로 부르면 안 된다. ID 는 자산을 넘기는 통로일 뿐이라 모델이 ID 와 내용을 연결하지 못한다. 본문에서는 Image 1 처럼 자산 종류 + 순번으로 지칭한다(순번은 요청 본문 안에서 같은 종류 자산끼리의 순서다).
맞는 표현 — “The beauty influencer in Image 1” · 틀린 표현 — “asset-2026**** is a beauty influencer”

2-3. 권리 확보 실인물 자산

실제 사람의 동의와 본인 인증을 받아 자기 계정의 비공개 자산 라이브러리에 올리는 경로다. 절차는 §3.

3. 자산 라이브러리에 직접 등록하기

등록할 수 있는 건 실제 사람뿐이다. 이 라이브러리는 초상권 동의를 받는 장치라, 절차의 중심이 당사자 본인의 얼굴 실인증이다. AI 로 만든 캐릭터는 인증할 사람이 없으므로 이 경로로 등록하지 못한다 — 그런 경우는 §2-1 이나 §2-2 로 간다.

3-1. 절차

세 사람 몫의 단계가 순서대로 있다.

  1. 자산을 쓸 쪽(우리) — ModelArk Model Playground 에서 My assets → Real-human → Add real-human assets → Create an asset group. 이 계정은 실명 또는 기업 인증을 먼저 마쳐야 한다. 권한 유효기간을 정하고 개인정보 처리 규칙에 동의하면 초대 QR 코드가 발급된다.
  2. 권한을 주는 쪽(출연자) — QR 을 찍어 자기 BytePlus 계정으로 로그인하고, 권한 주체와 사용 목적을 확인한 뒤 얼굴 정보 처리에 동의하고 실인증을 진행한다. 그다음 자기 사진·영상을 올린다. 올릴 때마다 얼굴 일관성 검사를 통과해야 저장된다.
  3. 다시 우리 — 실인물 자산 라이브러리에서 수령 대기 자산을 Accept 하고 위험 고지를 확인하면 상태가 Active 가 된다. Reject 하면 Rejected 로 바뀌어 쓰지 못한다.
한 자산 그룹은 한 사람 전용이다. 다른 사람의 자료를 같은 그룹에 섞지 못한다. 반대로 같은 사람의 다른 메이크업·스타일링은 계속 추가할 수 있고, 그때는 실인증을 다시 하지 않는다 — 배우 한 명당 인증 한 번이면 된다.

3-2. 올릴 자료의 규격

구도부터 정해져 있다. 전신은 세로 방향에 정면 전신, 얼굴은 세로 방향에 정면 무표정으로 어깨 위를 잘라 얼굴이 화면의 약 2/3를 차지하게 찍는다.

형식용량길이·크기
이미지jpeg · jpg · png · webp · gif · heic30MB 미만가로세로비 0.4~2.5 · 변 300~6000px
영상mp4 · mov50MB 이하2~15초 · 24~60fps · 비 0.4~2.5 · 변 300~6000px · 해상도 409,600~927,408
오디오mp3 · wav15MB 이하2~15초

인증 실패는 조명·각도 탓으로 종종 일어난다. 문서도 그때는 다시 시도하라고만 안내하며, 자료는 선명한 정면 사진을 권한다.

3-3. 등록한 자산 쓰기

자산 ID 를 확인한 뒤 세 역할 모두 같은 asset:// 형식으로 넘긴다.

"content": [
  { "type": "text",      "text": "<프롬프트>" },
  { "type": "image_url", "image_url": { "url": "asset://<asset ID>" }, "role": "reference_image" },
  { "type": "video_url", "video_url": { "url": "asset://<asset ID>" }, "role": "reference_video" },
  { "type": "audio_url", "audio_url": { "url": "asset://<asset ID>" }, "role": "reference_audio" }
]

4. 참조 이미지를 콘티처럼 쓰면 깨진다

여러 컷을 그린 콘티 한 장을 참조로 넣고 싶어지는데, 공식 문서가 말리는 형태가 정확히 그것이다. 이유가 셋이다.

4-1. 화풍까지 따라온다

reference_image 는 인물 생김새 · 화풍 · 화면 구도 셋을 물려받는다. 구도가 옮겨오는 건 우리가 노린 것이지만 화풍도 같이 온다. 문서의 “Style drifting” 항목이 그 반대 사례를 든다 — 애니를 원하는데 레퍼런스가 실사면 결과가 실사로 끌린다는 것이다. 뒤집으면 스케치를 넣으면 결과도 스케치로 끌린다. 해결책으로 문서가 권하는 건 스타일 제약어를 명시하거나, 레퍼런스를 먼저 목표 화풍으로 변환해서 넣는 것이다.

4-2. 한 장에 여러 컷을 담으면 인물이 복제된다

같은 인물을 여러 각도로 담은 자산(three-view · multi-view)을 문서가 명시적으로 비권장한다. 모델이 각 패널을 서로 다른 인물로 인식해, 한 프레임에 같은 사람이 둘 나오는 “Duplicated characters” 증상이 생긴다. 콘티 시트가 바로 그 형태다.

4-3. 자산은 많을수록 나빠진다

상한은 2.0 이 9장, 2.5 가 30장이지만 문서는 4~5장을 권하고 상한까지 쓰지 말라고 한다. 자산이 많으면 모델이 무엇을 우선할지 판단하지 못해 화풍 충돌과 주체 흐림이 일어난다. 자산의 역할은 넷으로 정해져 있고, “컷 순서”는 그중에 없다.

역할거는 것권장 구성
인물 고정캐릭터 외형이미지 1~2장(얼굴 클로즈업 + 전신)
장면 톤환경·스타일이미지 1장
카메라 무빙촬영 언어·동작 리듬영상 1편
분위기·리듬감정·음색오디오 1편
인물이 흔들리면 얼굴 비중부터 의심한다. 전신 사진 한 장에 얼굴·의상·포즈를 다 담으면 얼굴이 차지하는 면적이 작아 특징 추출 가중치가 떨어지고, 중간에 얼굴이 바뀌는 ID 드리프트가 난다. 문서의 처방은 머리만 담은 헤드샷을 따로 준비하고(무표정 권장, 어깨·목·배경 같은 방해 요소 최소화), 프롬프트에서 “Subject 1 의 얼굴은 Image 1, 스타일링은 Image 2” 로 역할을 나눠 지정하며, 중요한 자산을 앞에 배치하는 것이다.

4-4. 그림대로 정확히 가려면 참조가 아니라 프레임이다

문서 원문 그대로다 — “첫·끝 프레임이 지정한 이미지와 정확히 일치해야 한다면 언제나 image-to-video(first and last frame) 기능을 쓰라”(role 을 first_frame / last_frame 으로). reference_image 로 첫 프레임을 지정하는 건 간접적인 흉내라 보장이 없다.

그래서 콘티는 사람이 보는 설계도로 쓰고, 모델에는 그 컷을 목표 화풍으로 그린 그림을 first_frame 으로 넣는다. 인물 일관성은 reference_image 1~2장으로 따로 잡는다.

실측으로도 같은 답이 나왔다. 같은 장면을 글로 세 번(15초 t2v) 지시했을 때는 인물 배치가 매번 뒤집혔는데, 배치가 맞는 프레임 한 장을 first_frame 으로 넣자 카메라·구도를 한 줄도 쓰지 않고 그대로 유지됐다.

5. 컷 순서는 글로 준다

복잡한 영상의 이상적인 프롬프트 형태를 문서가 타임라인 콘티로 못 박는다. 영상을 컷으로 쪼개 Shot 1 · Shot 2 · Shot 3 으로 번호를 붙이고, 사건이 일어나는 순서대로 “누가 + 어디서 + 무엇을 + 카메라는 어떻게”를 쓴다.

Shot 1: 골목 측면. 남자가 천천히 뛰기 시작한다. 가쁜 숨소리.
Shot 2: 남자가 과일 좌판을 넘어뜨린다. 카메라가 빠르게 흔들리며 겁먹은 얼굴을 클로즈업.
Shot 3: 남자가 낮은 담을 넘어 사라진다. 카메라가 천천히 물러나 빈 거리에서 멈춘다.

같은 내용을 “남자가 초조하게 거리를 달린다, 매우 영화적인 느낌” 처럼 뭉뚱그린 산문은 문서가 든 나쁜 예다.

규칙내용
컷당 카메라 무빙 1종푸시·풀·팬·이동을 한 컷에 겹쳐 요구하면 화면이 불안정해진다
초 단위 지정 금지“0~3초” 같은 정밀 타이밍 지원이 불안정하다. 길이를 강제하면 생성이 망가질 수 있다
작고 느린 동작 우선전력질주·큰 점프·격한 구르기 같은 큰 동작은 피한다
감정은 몸으로“매우 슬프다” 대신 “고개를 숙이고 어깨가 살짝 떨린다”
동작 사이를 잇는다“돌아서는 관성을 이어 자연스럽게 손을 든다”

정보 종류를 기호로 나눠 준다 — 음악은 （ ）, 효과음은 < >, 대사는 { }, 자막은 【 】 다. 대사 언어를 섞지 않는다(고유명사 제외).

자막은 100% 막지 못한다. 요구하지 않아도 자막이 생성될 수 있고, 문서가 주는 건 확률을 낮추는 방법뿐이다 — 제약어를 명시하고, 레퍼런스에 든 불필요한 글자를 미리 지우고, 가능하면 가로로 만들어 나중에 세로로 자른다. 세로가 가로보다 자막 생성 확률이 유의하게 높다. 9:16 전용인 이 파이프라인에는 그대로 불리한 조건이다.

6. 함정

증상원인대응
i2v 결과의 일부 프레임이 늘었다 줄었다 한다 입력 이미지의 가로·세로가 출력 해상도와 다르다 입력을 출력 픽셀 크기에 맞춰 자르고 ratio 를 adaptive 로 둔다
i2v 소스가 가운데 띠만 남아 나온다 ratio 에 값을 박으면 서버가 중앙 기준으로 잘라낸다 i2v 에서는 ratio 를 아예 넘기지 않는다(기본 adaptive)
이어 붙인 지점에서 화면이 튄다 영상 연장 접합부의 프레임 불일치 앞 클립 끝 6프레임과 뒤 클립 앞 1프레임을 잘라 맞춘다. 그래도 미세한 튐이 남을 수 있어, 전환 컷 지점에서 끊는 편이 낫다
모델을 불렀는데 ModelNotOpen 콘솔에서 그 모델을 활성화하지 않았다 Model activation 에서 켠다. 과금은 붙지 않는다(2.0-fast 로 실측)
결과 URL 로 받으려니 사라졌다 생성 결과 URL 은 24시간짜리다 폴링이 끝나는 즉시 저장한다. 신뢰 자산으로 재사용할 원본은 TOS 에 보관한다
2.0 은 소리를 켜도 토큰이 오르지 않는다. 같은 프롬프트·같은 길이(1080p 15초)로 무음과 소리를 각각 뽑았더니 둘 다 731,025 토큰이었다(2026-08-15 실측). 1.5 pro 가 소리를 켜면 단가가 정확히 2배인 것과 다르다 — 2.0 에서는 소리를 끌 이유가 없다. 다만 이 판정은 응답의 completion_tokens 를 청구 근거로 본 것이라, 벤더가 오디오를 별도 항목으로 청구한다면 여기 잡히지 않는다.

참고로 해상도를 720p 로 내리면 같은 15초가 324,900 토큰으로 1080p 의 44% 다. 토큰 산식이 가로 × 세로에 비례하므로 예측대로 떨어진다.
