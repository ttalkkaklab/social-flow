Veo people and reference policy

Veo 3.1 takes adult faces as they are. We fed it the very close-up PNG Seedance 2.0 refused and got a 4-second clip out. The locked doors sit elsewhere — children's faces, style reference, and the asset registry itself. This page is a record of measuring Veo again from the same angle as the Seedance people and asset policy.

1. Measured — with the image Seedance blocked

We poked both engines with the same single file. It's a 1080×1920 portrait PNG, and the face of a Korean woman looking uneasy on a night street fills nearly the whole frame. It isn't a photo — it's a frame pulled from a video Seedance 2.0 made — and Seedance 2.0 still refused to take its own output back.

EngineCallResultCost
dreamina-seedance-2-0-260128 first_frame · 480p · 4s Refused — InputImageSensitiveContentDetected.PrivacyInformation
“input image ‘content[1]’ may contain real person”		 0 blocked before task creation
veo-3.1-lite-generate-preview veo_img2video · 9:16 · 720p · 4s Passed — 720×1280 · 24fps · 4.000s, with AAC 48kHz stereo attached (average −21.4 dB) about $0.20
The face held. Putting the input, the first frame, and the 3.6-second frame side by side and comparing by eye, the eyes, nose, jawline, and hair texture stay the same across the 4 seconds. A streetlight brightening in the background and a slight movement of the neckline are the whole of the change. This was measured on the cheapest tier (lite), so there's no reason the tiers above would be worse.
What this measurement covers is one mode: image-to-video. Reference-image mode (veo_reference) is documented under the same allow_adult policy, but we haven't paid to confirm it — using reference fixes the length at 8s and rules out lite, so it's fast at 8s, about $0.80. We don't write "it works" for a cell that isn't in the table on the strength of documentation alone.

2. The policy is expressed as a single value

Seedance runs the input image through a classifier and either refuses it or takes it. Veo works differently — a field called personGeneration has exactly one allowed value per mode, and that value is the policy.

ModeVeo 3.1 · 3.1 Fast · 3.1 LiteVeo 2 (for reference)
Text-to-video, extension"allow_all" onlyallow_all · allow_adult · dont_allow
Image-to-video, interpolation, reference images"allow_adult" onlyallow_adult · dont_allow
When there's one choice, it's a constant, not a parameter. That's why this server loses nothing by not passing personGeneration — in the 3.1 family it goes to the same value whether you pass it or not. If we ever bring Veo 2 back, that's when the value has to be chosen.

allow_adult means adults only. So what actually gets blocked in image-to-video is an image with a child in it. Permission-request posts pile up on the developer forum, and this is the error text attached to them.

The input image contains content that has been blocked by your
current safety settings for person/face generation.
— Support code: 17301594
Turning it into a drawing doesn't get you through either. The business owner in that request post converted a child's photo into a 3D storybook-style character illustration and fed in that drawing, and was blocked with the same text. The axis of judgment isn't whether the portrait is photorealistic — it's whether the subject looks underage. If we plan a cut with a child in it for one of our episodes, the Veo image-to-video lane isn't a candidate in the first place.

A permission path is open, but it isn't light. When a minor is involved it goes not to a standard permission request but to a policy review by the Vertex AI trust and safety team, filed through Google Cloud support channels. Google staff answers point at this path too.

Regional restriction

In the EU, UK, Switzerland, and MENA, Veo 3 and 3.1 allow only allow_adult. That means text-to-video's allow_all is narrowed to adults in those regions too. Korea isn't affected, but running this plugin on an account in those regions changes the results for cuts made from a text prompt alone.

What the API doesn't block — real people

Veo takes adult faces without distinction. The API never asked whether that face is an AI-made fictional person or someone who actually exists. Which means whether to feed in a real person's likeness isn't a gate, it's our judgment. The line Google's generative-AI prohibited use policy draws is this.
  • “Impersonating an individual (living or dead) without explicit disclosure, in order to deceive.” — undisclosed impersonation done to deceive
  • “using personal data or biometrics without legally-required consent” — using personal or biometric data without consent
  • “Facilitates non-consensual intimate imagery.”
The policy blocks impersonation and non-consent, not likeness itself. So not being refused doesn't mean you may use it. For real-person material we verify the rights ourselves and write down the basis.

Generated video carries an invisible SynthID watermark, and the output passes through safety filters and a memorization check (a check for reproducing training data verbatim). That isn't an option we can turn off.

3. There is no asset registry

The most useful find in the Seedance research was asset:// — a library where you register a person or character once and call it by ID every episode. Veo has no counterpart. Not because we failed to find it; the design is that way.

What you put inHow it's passedReuse
First and last frame imagesbase64 inline in the request bodyNone — uploaded again every time
1–3 reference imagesbase64 inline in the request bodyNone
Video to extendbase64 inline in the request bodyOnly video Veo made (official contract)

There is one path for "taking back what we made": extension (veo_extension). It serves the same purpose as Seedance's trusted-output path — the model recognizes its own output, so it doesn't run the person check again. But the window is short.

The server holds generated video for 2 days. That's midway between Seedance's 30-day trusted outputs and its 24-hour result URLs. Our client downloads a local .mp4 as soon as generation finishes, so we can still build an extension input after the 2 days are up — we re-upload the file as base64. That said, the official contract is "a Veo product, 720p, 141s or less" and our server only checks the extension. What happens if you feed in an mp4 Veo didn't make is unverified.
The Vertex AI path has an option to point storageUri at a GCS bucket, but that's an output store, not an asset registry. Reference images are bytesBase64Encoded inline on Vertex too. So the conclusion that there's no registry holds for both paths.

Translated into practice: don't leave character consistency to Veo — manage it ourselves as files. Keep front, side, and full-body PNGs of the channel character under data/<channel>/assets/characters/<id>/ and upload the same files as reference images every episode. The character row in catalog.md and resolve-asset.py find that sheet. No registry also means the versions are in our hands, so the accident where fixing a character quietly changes past episodes can't happen on this side.

4. Using reference images as scene frames breaks

The question from the Seedance research holds here too — if we draw the cut as a sketch or a toon and pass it as reference, does it build that composition? Veo's answer is the same "no" as Seedance's, but it gets blocked at a different point.

There are two reference kinds, and one of them is closed in 3.1

referenceTypeWhat it doesCountVeo 3.1 family
"asset"Preserves the appearance of one person, character, or product in the output videoUp to 3Supported (except lite)
"style"Applies the style of the uploaded image to the output video1Not supported
The Vertex docs nail it down — “Veo 3.1 models don't support referenceImages.style. Use veo-2.0-generate-exp when using style images.” The Gemini API side exposes only asset. The path for passing a sketch or toon style as reference is closed in 3.1, and what's open is only the experimental 2.0 model, which can't make audio. The reason our pipeline uses Veo is native audio, so that trade doesn't hold.

asset is appearance, not composition

The name is easy to misread: what asset looks at is "what appears", not "where and how it's placed". Put a scene frame in as asset and instead of imitating that layout, Veo puts the drawing itself on screen — line art on paper, moving inside the video. Google's own examples use it that way. They fed in one drawing of an anglerfish and one of a princess dress and asked for "a cartoon of a fish swimming in a dress", and got a video where the two subjects were combined, not one where the two drawings' layout was reproduced.

The source of truth for composition is the first and last frame. Put the opening cut in image and the closing cut in lastFrame, and it connects the two. Same conclusion as the Seedance measurements — draw the camera and composition instead of describing them in words, and they're kept. That said, the interpolation mode that takes two frames is also image-to-video and therefore allow_adult, and we haven't measured that combination yet.

Google's examples are all generated images

The reference-image examples in the official guide — the three of a dress, a person, and sunglasses, or the two of the anglerfish and the princess dress — are all drawings made with Nano Banana. There isn't a single example using a photo as reference. It isn't a prohibition, but it's signal enough that the standard flow the vendor has in mind is "make the asset with an image model and hand it to the video model". Our pipeline's gpt_image_text2img → veo_* order matches that flow.

Constraints that come with using reference

  • The length is fixed at 8s — even to fill a 4-second slot, it bills the 8-second amount.
  • lite can't use reference at all. You go up to fast at minimum.
  • The sharper the images and the more angles, the better the consistency. Filling the 3 slots with one person's front, side, and full body is the use case here.

5. How to write a people shot in words

Where we can't hand over the composition as a drawing, words are the only channel. The official guide names seven elements, of which only the first three are required and the rest are optional.

ElementWhat to write
Subject · requiredThe object, person, animal, or landscape to put on screen
Action · requiredWalking, running, turning the head
Style · requiredFilm noir, horror film, cartoon
CameraAerial shot, eye level, dolly shot, low angle
CompositionWide shot, close-up, single shot, two shot
Focus and lensShallow focus, macro lens, wide-angle lens
AmbianceBlue tones, night, warm tones
There's a separate way to raise facial detail — put portrait in the prompt to make the face the focus. Our measurement prompt didn't have that word and the face held anyway, so it isn't strictly needed when there's a first frame, and it would be worth more in text-to-video.

Sound

  • Wrap dialogue in quotes — unwrapped, it gets read as narration or leaks out as on-screen text.
  • Spell out sound effects and ambience — "tires screeching and the engine roaring", "a faint hum in the background".
  • To extend, there has to be speech in the last second. A clip that ends quietly won't carry its sound over.

English is the fully supported language and the rest aren't evaluated. A Korean prompt does work, but that means results can differ, so it's safer to write the prompt in English and wrap only the dialogue in Korean.

A new video model called Gemini Omni Flash (gemini-omni-flash-preview) is up on the Vertex-side Interactions API. It takes reference images, makes 3–10 seconds in 1-second steps, and infers the aspect ratio from the prompt — closer to Seedance's freedom than Veo's 4/6/8-second grid.
