공공데이터포털 — 정부 공식 데이터

콘텐츠의 수치 근거로는 기사 재인용보다 원천 데이터가 우선한다. 다만 이 포털은 API 하나가 아니라 성격이 다른 5개 경로이고, 그중 셋은 인증이 아예 필요 없다.

1. 5개 경로와 인증 요건

툴호출 대상응답인증
datago_searchwww.data.go.kr/tcs/dss/selectDataSetList.doHTML무인증
datago_detailwww.data.go.kr/data/{pk}/{fileData|openapi}.doHTML무인증
datago_file_downloadselectFileDataDownload.do → cmm/cmm/fileDownload.doJSON → 바이너리무인증
datago_file_fetchapi.odcloud.kr/api/{pk}/v1/{uddi}JSON키 + 활용신청
datago_api_callapis.data.go.kr/{path}XML 또는 JSON키 + 활용신청
키 없이도 파일데이터는 끝까지 받을 수 있다. 검색 → 상세 → 다운로드 3단계가 전부 무인증이므로, 인증키가 없거나 활용신청이 안 된 상황에서 datago_file_download가 가장 빠른 수집 경로다.

2. 활용신청 함정

인증키만으로는 부족하다. 포털에서 API별 활용신청(대부분 자동승인·즉시)을 해야 그 키가 해당 API에 등록된다. 마이페이지에서 발급한 키를 그대로 써도, 신청하지 않은 API를 호출하면 거부된다.
  • odcloud: code: -4
  • 표준 오픈API: SERVICE_KEY_IS_NOT_REGISTERED_ERROR 또는 플레인 텍스트 Unauthorized
이 두 응답을 "키가 틀렸다"로 번역하면 모델은 키를 다시 발급받으려 하고, 실제 해법(활용신청)에는 영원히 도달하지 못한다.

3. 검색·상세 (HTML 파싱)

포털은 검색·상세에 JSON API를 제공하지 않는다. 서버 렌더링 HTML을 정규식으로 파싱한다.

추출 대상패턴 근거
publicDataPk · type목록 항목의 fn_preview('12345', 'FILE') 호출
제목 · 설명 · 포맷 태그<span class="title"> · <dd class="ellipsis publicDataDesc"> · <span class="tagset…">
제공기관 · 수정일 · 키워드<span class="tit">라벨</span> 다음 값
타입별 총건수탭 라벨의 (N건)
상세 메타<th>라벨</th><td>값</td> — 화이트리스트 17종만 통과
다운로드 식별자 uddifileDataDown('{pk}', '{uddi}') — pk로 정확히 짚는다
오픈API 엔드포인트var swaggerUrl · var swaggerJson · 본문의 apis.data.go.kr URL
파싱은 포털 개편에 깨진다. 그래서 모든 파서는 예외를 던지지 않고 0건 + 원인 안내로 우아하게 실패한다 — "계속 0건이면 포털 개편으로 파싱이 깨졌을 수 있다: … 를 WebFetch로 직접 확인하고 서버 파서 수정을 사용자에게 보고할 것". 모델이 검색어를 바꿔가며 무한 재시도하는 것을 막는 안내다.

uddi 추출에서 pk를 정규식에 박아 넣는 이유: 상세 페이지에는 관련 데이터셋의 uddi도 함께 실려 있어, 첫 매치를 쓰면 엉뚱한 데이터셋을 받게 된다.

포털은 브라우저가 아닌 User-Agent를 차단할 수 있어 통상 UA를 보낸다(robots는 검색봇 대상).

4. 파일 다운로드 (2단계)

# 1단계 — 다운로드 티켓 (JSON)
GET /tcs/dss/selectFileDataDownload.do?publicDataPk={pk}&publicDataDetailPk={uddi}
→ { "status": true, "atchFileId": "FILE_00000…", "fileDetailSn": "1" }

# 2단계 — 실파일 (바이너리)
GET /cmm/cmm/fileDownload.do?atchFileId={atchFileId}&fileDetailSn={fileDetailSn}
함정대응
status: false — 로그인 필수·제공 중단 데이터셋"포털이 파일 티켓을 거부했다 … detailUrl을 브라우저로 확인할 것"
파일명이 깨져 온다fetch는 헤더를 latin-1로 노출하는데 포털은 UTF-8 바이트를 그대로 싣는다. filename*의 %-인코딩이면 URI 디코드, 아니면 latin-1 바이트를 UTF-8로 재해석하고, 그래도 깨지면 원문 유지
CSV 인코딩이 EUC-KR/UTF-8 혼재선두 4KB를 UTF-8로 읽어 �가 있으면 EUC-KR로 재해석. 판정 시 마지막 4글자는 제외한다 — 4KB 절단이 멀티바이트 문자를 잘라 생긴 �를 인코딩 오판으로 삼지 않기 위해
대용량100MB 상한. 초과 시 "odcloud API(datago_file_fetch)로 필요한 행만 조회할 것"
같은 이름 재다운로드-1·-2 접미어로 충돌 회피 (최대 99)

미리보기 encoding이 euc-kr이면 파일을 읽기 전에 iconv -f euc-kr -t utf-8 변환이 필요하다 — 응답이 이를 명시한다.

5. odcloud 행 조회

GET https://api.odcloud.kr/api/{publicDataPk}/v1/{uddi}?page=1&perPage=10&returnType=JSON
# 툴 인자는 limit — 서버가 odcloud 의 perPage 로 환산한다
Authorization: Infuser {인증키}
키를 Authorization 헤더로 보낸다. odcloud는 serviceKey 쿼리도 받지만, 헤더를 쓰면 에러 본문에 URL이 에코돼도 키가 새지 않는다.

uddi의 :는 리터럴로 통과해야 한다(실측) — 세그먼트를 인코딩한 뒤 %3A만 :로 되돌린다.

code의미서버의 안내
-1필수 파라미터 누락—
-2권한 없음—
-3등록되지 않은 서비스"uddi는 _YYYYMMDDHHMM 접미사까지 전체가 필요"
-4이 API에 등록되지 않은 인증키"활용신청(자동승인)을 먼저 … 활용신청 전에는 datago_file_download(무인증)로 원본을 받는 것이 빠르다"
-5트래픽 초과"오늘은 datago_file_download로 대체할 것"

응답은 12,000자에서 자르고 …(잘림 — limit 을 줄이거나 필요한 행만 page 로 짚어 조회할 것)을 덧붙인다.

6. 표준 오픈API

GET https://apis.data.go.kr/{path}?{params}&serviceKey={인증키}
# 예: 1360000/VilageFcstInfoService_2.0/getUltraSrtNcst
returnAuthMsg안내
SERVICE_KEY_IS_NOT_REGISTERED_ERROR활용신청 여부 + 키 일치 확인. "키 교정 전 재시도 금지"
DEADLINE_HAS_EXPIRED_ERROR활용기간 만료 — 포털에서 연장 신청
LIMITED_NUMBER_OF_SERVICE_REQUESTS_EXCEEDS_ERROR일일 트래픽 초과 — 오늘은 이 API 추가 호출 금지
SERVICE_ACCESS_DENIED_ERROR활용신청 승인 상태 확인
TEMPORARILY_DISABLE_THE_SERVICEKEY_ERROR일시 차단된 키
NO_OPENAPI_SERVICE_ERROR존재하지 않는 경로 — 활용가이드의 요청주소와 대조
게이트웨이가 미등록 키에 HTTP 200을 준다. 본문이 XML 에러이거나 플레인 텍스트 Unauthorized일 수 있어, 상태 코드만 보면 성공으로 오인한다. 본문 검사가 먼저다.
  • 응답이 XML인 API가 많다. dataType/_type=JSON을 지원하는 API는 JSON을 요청하는 편이 파싱이 쉽다.
  • serviceKey는 서버가 주입한다 — 호출자가 params에 넣으면 zod가 거부한다.
  • 응답은 8,000자에서 자르고 numOfRows/pageNo로 줄여 재조회하라고 안내한다.
  • 모든 출력 경로에 serviceKey=*** 마스킹.
파라미터를 추측해 반복 호출하면 안 된다. 표준 오픈API는 일일 트래픽 제한이 있고, 잘못된 파라미터 호출도 카운트된다. datago_detail의 endpoint/requestUrls/docs에서 계약을 먼저 확인하는 것이 툴 설명에 명시돼 있다.
