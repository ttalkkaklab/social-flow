2. P0 — 조용히 틀리던 것

에러도 예외도 내지 않으면서 결과를 무의미하게 만들던 두 가지. 툴 감사의 가치는 대부분 여기에 있다 — 실패하는 툴은 로그에 남지만, 그럴듯한 빈 결과를 반환하는 툴은 아무도 눈치채지 못한다.

P0-1 · serp_naver_search의 기본 경로가 항상 빈 결과였다

이 툴의 기본값은 where='web'이다. 코드는 응답에서 web_results와 news_results만 읽었는데, SerpApi가 where=web에 실제로 반환하는 키는 organic_results다. 그래서 기본 경로로 호출한 모든 검색이 "(검색 결과 없음)"을 반환했다.

그 응답은 진짜로 결과가 없는 경우와 글자 하나 다르지 않아, 모델은 검색이 고장 났다고 판단할 근거가 없었다. 툴 설명이 지시한 대로 "검색어를 바꿔 1회 재시도"한 뒤 주장을 본문에서 빼는 것이 합리적 행동이 된다 — 즉 있는 근거를 못 찾고 콘텐츠가 빈약해지는 방향으로 조용히 편향됐다.

whereSerpApi 문서실제 응답 키 (실측)
webweb_resultsorganic_results
newsnews_resultsnews_results ✓
nexearch여러 배열web_results · ads_results · inline_images_results

수정: 세 키를 모두 확인한다. 공식 문서만 읽고 구현했다면 이 결함은 그대로 남았다 — 실호출로 응답 키를 직접 확인해야 잡힌다.

P0-2 · 즉시 공개 게시 툴을 클라이언트가 구분할 수 없었다

이 서버에는 게시 전 검토 게이트가 없다. threads_publish를 호출하면 그 순간 공개 게시되고, 게시 API는 비멱등이라 재시도는 중복 게시가 된다. 이 사실은 각 툴의 description 산문에만 적혀 있었다 — 모델은 읽지만 클라이언트의 승인 UI는 읽지 못하는 형태였다.

MCP는 정확히 이 목적의 필드를 정의한다(annotations.destructiveHint). 비워두면 클라이언트는 tts_list_voices(상수 목록 반환)와 youtube_publish(즉시 공개 업로드)를 같은 위험도로 다루게 된다.

수정: 31개 툴 전부에 title과 annotations를 달고, 판정 기준을 판정표로 고정했다. 계약 테스트가 힌트와 설명의 모순(예: readOnly인데 설명이 "즉시 공개"라고 말함)을 매 빌드 검사한다.

// 실제 tools/list 응답
{ "name": "youtube_publish",  "annotations": { "readOnlyHint": false, "destructiveHint": true,
                                               "idempotentHint": false, "openWorldHint": true } }
{ "name": "tts_list_voices",  "annotations": { "readOnlyHint": true,  "openWorldHint": false } }

3. P1 — 수정한 결함

#결함영향수정
1 에러 접두어 이중 출력 — 클라이언트와 핸들러가 같은 접두어를 붙였다 (이미지 2곳 · 영상 4곳) Video generation failed: Video generation failed: … 클라이언트는 원인 메시지만 담는다 (TTS·음악 클라이언트와 같은 규약)
2 영상 출력 경로 미검증 — filename에 ../나 임의 확장자를 넣어도 통과했다 outputPath 밖으로 파일을 쓸 수 있었다. 오디오 경로는 이미 막혀 있었으나 영상만 누락 resolveOutputFile로 통합. 나아가 zod 스키마 단계에서 먼저 거부한다 — 저장 시점에만 막으면 1~6분짜리 생성이 끝난 뒤 거부되어 비용이 통째로 날아간다
3 sort_by 값 체계 오류 — SerpApi naver 엔진은 where=news에서 0/1/2를, 그 외에서 r/dd를 쓴다. 코드는 항상 r/dd를 보냈다 뉴스 최신순 정렬이 조용히 무시됐다 — 에러가 없으므로 오래된 기사를 최신으로 인용하게 된다 where별로 값을 매핑
4 YouTube categoryId가 25(News & Politics)로 하드코딩되고 노출되지도 않았다 모든 업로드가 시사·정치로 분류돼 추천·탐색에서 엉뚱한 관심사 집단에 노출된다 기본값 22(People & Blogs)로 바꾸고 파라미터로 노출
5 YouTube 쿼터 설명이 낡았다 — "업로드 쿼터 일 6건" 2026년 개편으로 videos.insert는 전용 버킷에서 호출당 1유닛(기본 일 100회)을 쓴다. 낡은 안내는 모델이 필요한 게시를 미루게 만든다 설명과 코드 주석을 현행 계약으로 교체
6 TTS 지원 언어 설명이 사실과 달랐다 — "103개 언어 … 번체 중국어 zh-TW는 미지원" 공식 문서의 언어표는 90여 종이며 zh-TW를 포함한다. 모델이 가능한 작업을 거절하게 만드는 오정보 사실대로 교정
7 Lyria RealTime이 요청 길이를 지키지 않았다 — 마지막 청크가 목표를 넘겨 도착해 30초 요청에 31초가 나왔다 이 툴의 존재 이유가 "길이를 지정할 수 있다"인데 그 계약을 어긴다. 내레이션에 정확히 맞춰야 하는 용도에서 매번 어긋난다 샘플 경계(채널 × 2바이트)에 맞춰 목표 길이로 정확히 자른다. 실측: 7초 요청 → 1,344,044바이트 = 44 + 7×48000×2×2 정확히 일치
8 Threads 본문 길이를 과소 계산 — JS .length는 이모지를 2로 세지만 플랫폼은 UTF-8 바이트(대개 4)로 센다 검증을 통과한 캡션이 플랫폼에서 거부된다. 게시 시점 실패라 승인 절차를 다시 밟아야 한다 BMP 밖 문자만 실제 UTF-8 바이트로 세는 계산으로 교체 (한글·ASCII는 그대로 1). 답글 길이 검증에도 적용
9 outputSchema·structuredContent 부재 게시 응답의 postId·permalink는 후속 호출(링크 답글, 첫 댓글)에 그대로 넘겨야 하는 값인데, 텍스트를 파싱해 꺼내야 했다 SNS 툴 9종에 outputSchema 선언 + fromApi가 성공 응답에 structuredContent를 싣는다. 실패 경로에는 싣지 않는다 — 스펙이 스키마 준수를 MUST로 요구하기 때문
10 응답에 "HTTP 200" 접두어가 JSON 본문 앞에 붙었다 본문이 유효한 JSON이 아니게 되어 호출자가 바로 파싱하지 못한다 성공 시 본문만 반환(상태는 성공으로 이미 함의). 실패 시에는 상태 코드를 유지 — 진단에 필요하다
11 계약 테스트 부재 라우팅 누락·enum 불일치·힌트 모순을 잡을 자동 수단이 없었다 server/test/contract.test.mjs — 239개 검사 (§4)

4. P2 — 정확도·안내 개선

  • Instagram 이미지 — "JPEG 권장" → "JPEG만"(플랫폼이 PNG·MPO·JPS를 거부). 게시 쿼터(24시간 100건) 명시.
  • Threads 영상 — "영상 불가"가 플랫폼 한계처럼 읽혔다. 플랫폼은 VIDEO·CAROUSEL을 지원하며, 미지원은 이 파이프라인의 전략적 선택임을 명시. 게시 쿼터(24시간 250건) 추가.
  • Google 뉴스 정렬 — 정렬 파라미터 so를 노출하려다 실호출에서 "`q` and `so` parameters can't be used together." 400을 받았다. so는 토큰 탐색 전용이라 검색어와 병용할 수 없다. 노출을 철회하고, 대신 대안 경로(serp_web_search의 recency, naver_search의 sort=date)를 설명에 적었다.
  • GPT Image 프롬프트 상한 — 32,000자 제한을 스키마와 설명에 명시.
  • Lyria 3 Clip — 가사 생성과 구조 태그([Verse]·[Chorus]·타임스탬프)를 안내하고, 정책 차단 시 "코드 문제가 아니라 프롬프트 문제 — 표현을 바꿔 1회 재시도"를 명시.
  • 댓글 인박스 응답 크기 — 상한(25 게시물 × 100 댓글)을 다 채우면 응답이 호출자 컨텍스트를 크게 잠식한다. 60,000자 상한을 두고 오래된 댓글부터 버린다(골든타임 댓글이 남아야 한다). 집계는 자르기 전 값을 유지한다 — 잘린 목록으로 다시 세면 "미응대 3건"처럼 실제보다 적게 보고되어 남은 응대를 놓친다.
  • Meta Graph 버전 상수화 — 두 곳에 흩어져 있던 v23.0을 상수 하나로. 고정 이유(2027년까지 유효 · 상위 버전의 파괴적 변경 차단)를 주석에 남겼다.
  • 버전 3중 불일치 — plugin.json 0.4.0 · server/package.json 0.3.0 · index.ts 0.3.0 → 전부 0.4.0.
  • tts_multi_speaker 설명의 이스케이프 — 예시의 \n이 실제 줄바꿈으로 렌더돼 형식을 잘못 보여줬다. 화자 이름이 speakers 배열과 일치해야 한다는 조건도 명시.

6. 남긴 것과 그 이유

항목이유
행동 평가(behavioral eval) 하네스 — 실제 모델로 다단계 워크플로를 돌려 툴 선택·호출 수·토큰을 측정하는 평가 베스트 프랙티스의 7번째 원칙이자 이 감사의 유일한 미달 항목이다. 게시 툴이 실호출로 공개 게시를 만들기 때문에, 안전한 평가에는 드라이런 계층이 선행해야 한다. 그 계층을 만드는 것은 이 감사의 범위를 넘는 설계 변경이다.
serp_*·datago_*의 outputSchema 이들은 JSON 텍스트를 반환하지만 응답 형태가 고정돼 있지 않다 — 특히 datago_*는 포털 HTML 파싱 결과라 필드 구성이 데이터셋마다 다르다. MCP는 outputSchema를 선언하면 준수를 MUST로 요구하므로, 지킬 수 없는 계약을 선언하는 것보다 선언하지 않는 편이 정직하다.
Meta Graph v23.0 유지 (최신 v25.0) Meta 버전은 릴리스 후 약 2년 유효하므로 v23.0(2025-05)은 2027년까지 살아 있다. 버전 고정은 상위 버전의 파괴적 변경이 게시를 조용히 깨뜨리는 것을 막는 장치다. 대신 상수 한 곳으로 모아 갱신 시점에 한 줄만 고치면 되게 했다.
Instagram 이미지 URL의 JPEG 검증 CDN URL에는 확장자가 없는 경우가 흔해, URL로 포맷을 판정하면 정상 요청을 거부하게 된다. 설명에 명시하되 강제하지 않는다.
lyria-3-pro-preview 미노출 1~2분 트랙은 쇼트폼 파이프라인에 쓸 자리가 없고 비용만 커진다.
Veo numberOfVideos · OpenAI n 미노출 쇼트폼은 컷 단위 1개 생성이 기본이고, N개 생성은 비용이 N배다.
skills/ingest의 mcp__fect-mcp__vision_analyze·vision_ocr 플러그인에 남은 유일한 외부 MCP 의존이다. 이번 감사는 이 서버가 제공하는 31개 툴이 대상이며, vision 모듈 이식은 별개 작업이다. npm 배포 시 완전 단독 동작을 원하면 이것부터 처리해야 한다.

7. 2차 감사 (같은 날, v0.4.1)

1차 감사 수렴 후 전체 소스를 다시 적대적으로 읽었다. 발견은 전부 1차에서 검증하지 않기로 한 경계 — 게시 경로(실호출 금지)와 극단 입력(최대 길이 캡션, 100MB 파일) — 에서 나왔다. 실호출로 눌러본 경로에서는 추가 결함이 없었다.

등급발견조치검증
P1 Meta POST 파라미터가 URL 쿼리스트링으로 전송 — 캡션 상한(IG 2,200자·FB 5,000자)이 %-인코딩(한글 ×9)되면 URL이 20~45KB가 되어, 스키마가 허용한 입력이 요청 라인 길이 한계에서 실패할 수 있다 POST는 application/x-www-form-urlencoded 본문으로 이동 (GET/DELETE는 쿼리 유지). 토큰도 URL에서 빠진다 Threads 미게시 컨테이너(생성만 하고 publish 안 함 — 외부 비공개, 24h 자동 만료)로 500자 꽉 채운 한글 캡션 실전송 성공
P2 selfDeclaredMadeForKids: false 하드코딩 — 아동 대상 콘텐츠를 올리면 COPPA 허위 선언이 된다 madeForKids 인자 노출(기본 false, 제재 사유 명시) stdio ListTools에서 파라미터·설명 확인
P2 serp_web_search·serp_news_search가 error 필드 없는 200+빈 결과에 빈 스켈레톤 JSON만 반환 — 1차 P0(빈 결과 구분 불가)과 같은 계열의 잔여 구멍 세 검색 툴 모두 동일한 "(검색 결과 없음 — 1회만 재시도…)" 안내로 통일 실호출로 무결과 검색 확인
P2 video-client만 API 키를 ?key= URL 쿼리로 전송 — serp/datago의 키 마스킹 철학과 불일치(로그·에러 에코 유출면) 폴링·다운로드 모두 x-goog-api-key 헤더로 이동 실측: 헤더 인증으로 unregistered-caller 게이트 통과 확인(비용 0 프로브)
P3 다듬기 5건 알 수 없는 툴 → JSON-RPC -32602 프로토콜 에러(2계층 에러 모델 정합) · 인박스 플랫폼 병렬 수집 · sns_account_check 병렬화(655ms 실측) · 인박스 상한 절단을 이분 탐색으로(과잉 절단 제거) · naver &#39; 복원 · datago 파일명 충돌 100회 초과 시 덮어쓰기 대신 에러 npm run check 239개 + stdio 스모크(-32602 확인) + sns_account_check 실호출

이번에도 남긴 것: 생성 이미지의 base64 image 블록 상시 반환(HITL 검토에 즉시 보이는 가치가 커 유지), 생성 오디오 filename 확장자와 실제 포맷 불일치 허용(생성 후 임의 개명이 더 나쁨), datago 다운로드의 전량 메모리 버퍼링(100MB 상한으로 유계). 점수는 96 유지 — 수정분은 1차 감점 항목이 아니라 신규 발견이며, 유일한 감점(행동 평가 하네스)은 그대로 남아 있다.
