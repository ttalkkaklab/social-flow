1. Tool definition fields

These are the fields of the Tool object carried in MCP's tools/list response. SDK 1.30.0's ToolSchema is the source of truth.

FieldRequiredPurposesocial-flow
namerequiredUnique identifier — the name the model callsused
titleoptionalDisplay name for humans. Clients show it in tool lists and approval dialogsused
descriptionoptionalUsage notes the model reads. In practice, a promptused
inputSchemarequiredJSON Schema for the arguments. Fixed at type: "object"used
outputSchemaoptionalJSON Schema for the structured result. Declare it and the server MUST return structuredContent matching itused on the 17 SNS and growth tools
annotationsoptional4 behavior hints + a display title (§2 below)used on every tool
executionoptionaltaskSupport — whether long work can be delegated to a taskunused
_meta · iconsoptionalImplementation-specific metadata · iconsunused
Declaring outputSchema makes it a contract. The spec is blunt: "Servers MUST provide structured results that conform to this schema." If there's any failure path where you can't fill structuredContent, you're better off not declaring it. This repo marks as required only fields that are always filled on the success path, and returns failures as isError: true plus text, which keeps the contract intact.

2. Behavior hints (annotations)

This is what a client uses to decide "does this call need user confirmation". The spec defines them as hints and warns that a client must not trust hints from an untrusted server — but if a trusted server leaves these fields empty, the client loses any way to tell a dangerous tool from a safe one.

HintDefaultMeaning
readOnlyHintfalseDoesn't modify its environment
destructiveHinttrueMay perform destructive or hard-to-undo updates. Only meaningful when readOnlyHint: false
idempotentHintfalseRepeated calls with the same arguments have no additional effect. Only meaningful when readOnlyHint: false
openWorldHinttrueInteracts with an open world (the internet, say)
title—Display name (the older location for the Tool's top-level title)
This server has no pre-publish review gate — the call is the publication. Eight tools take effect outside the moment they're called: threads_publish·instagram_publish·facebook_publish·facebook_comment·youtube_publish·youtube_update·sns_comment_reply·sns_comment_moderate, and among them the publish APIs are non-idempotent, so a retry means a duplicate post. That fact used to live only in each tool's description prose — a form the model reads but the client can't. Now it's declared machine-readably with destructiveHint: true + idempotentHint: false.

3. The CallToolResult contract

Unstructured results go in content[], structured ones in structuredContent. The two aren't exclusive but parallel — the spec recommends (SHOULD) that even tools returning structured results also carry the serialized JSON as a text block, for backward compatibility.

Content block types

  • text — { type, text }
  • image — { type, data(base64), mimeType }
  • audio — { type, data(base64), mimeType }
  • resource_link — { type, uri, name, description?, mimeType? }
  • resource — an embedded resource
When to return generated media as base64 and when to return only a path. Images (gpt_image_*) come back as an image block, because the model has to see the result to decide whether to regenerate. Video, voice, and music return the path only: several MB of base64 burns context, and the model can't evaluate audio or video directly anyway.

4. Two layers of error reporting

LayerFormWhen to use itThis server
Protocol errorJSON-RPC errorUnknown tool, bad arguments, internal server failureHandled by the SDK at the transport layer
Tool execution errorresult.isError: true + textAPI failure, bad input data, business-logic failureindex.ts converts every exception into this

Execution errors come back as isError so that the model can read them and correct itself. Thrown as protocol errors, the model learns only that something failed and never sees why. This server also converts zod validation failures into execution errors, complete with the field path.

Invalid arguments — durationSeconds: 1080p resolution is only supported at 8s duration (requested: 4s).

5. 7 principles for authoring tools

The principles from Anthropic's Writing tools for agents, and how this repo honors each.

① Consolidate around workflows

Don't wrap API endpoints one-to-one; bundle them into real units of work. One schedule_event instead of list_users+list_events+create_event.

Applied: a single instagram_publish handles six steps — /me lookup → create N child containers → poll all of them to FINISHED → bundle the carousel → media_publish → fetch the permalink. The model passes only the caption and the image URLs.

② Namespacing

Group tools under a shared prefix per service or resource so the model can tell similar ones apart.

Applied: serp_·naver_·datago_·gpt_image_·veo_·tts_·music_·sns_. Only publish tools lead with the platform name (threads_publish) — for publishing, choosing the platform is the decision, so the prefix has to be the platform or the model gets confused.

③ Return only high-signal context

Meaningful language over technical identifiers (UUIDs, MIME types). Relevance over flexibility.

Applied: raw SERP JSON is 20–60KB per search. Keeping only organic_results·answer_box·knowledge_graph·related_questions brings it to 2–4KB. sns_comment_inbox absorbs the per-platform field-name differences and computes derived values you can act on directly, like ageMinutes and withinGoldenHour.

④ Token efficiency — pagination, filters, truncation

Pick sensible defaults, and when output is cut, say so with actionable guidance.

Applied: datago_file_fetch cuts at 12,000 characters and appends …(truncated — lower limit, or point at the rows you need with page). tts_* doesn't echo back a 16,000-character script, only its length — the caller sent that string, so echoing it carries zero information and burns context.

⑤ Actionable error messages

Say what to fix and how, not just an error code.

Applied: an odcloud -4 isn't passed through raw; it's translated into "this auth key isn't registered for this API — file a usage application on the portal first (auto-approved). Before that, datago_file_download (no auth) is the faster way to get the raw file." SerpApi 401/429 go further and dictate the retry policy: "don't retry until the key is fixed", "stop further searches in this session".

⑥ Write descriptions like onboarding a new hire

Make implicit context explicit, and name parameters unambiguously (user_id, not user).

Applied: generation-tool descriptions keep a fixed three-part structure — Use when… / Do NOT use… / Returns:. This is what prevents the wrong-tool picks that "what it does"-only descriptions cause — a model reaching for veo_text2video when it should use veo_img2video fails for lack of a boundary, not for lack of a feature list.

⑦ Evaluate systematically

Evaluate with multi-step tasks drawn from real workflows, and watch runtime, call count, tokens, and errors alongside accuracy.

Applied (partly): this repo automatically verifies the static contract (schema validity, routing consistency, hint coherence) via server/test/contract.test.mjs. There's no behavioral eval that runs an actual model yet — because publish tools make real public posts, a safe eval harness needs a dry-run layer first.

6. Scoring rubric

This repo scores tool quality on the five axes below, out of 100. The audit report is the result of applying this rubric.

AxisPointsWhat's scored
A. API contract fidelity30 Do model IDs, endpoints, and versions match the current official docs / do parameter ranges, enums, and ceilings match the official values / are the facts stated in descriptions (quotas, limits, supported languages) true / are cross-constraints (resolution × length × model) enforced in the schema
B. MCP protocol compliance20 Use of the Tool fields (title·annotations·outputSchema) / hints matching actual side effects / structuredContent consistent with outputSchema / the two error layers kept separate / honesty in capability declarations
C. Tool design best practices25 Workflow consolidation / namespacing consistency / the Use·Do NOT·Returns three-part description / clarity of parameter names and descriptions / response token efficiency and truncation notices / how actionable error messages are
D. Implementation correctness & safety15 Path traversal and extension allowlists / closing off secret leaks (URL echoes, error bodies) / retry safety for non-idempotent operations / partial-failure isolation / no output pollution like duplicated error prefixes
E. Verifiability10 Tests that automatically verify the tool surface contract / routing consistency (definition ↔ handler, both directions) / build output in sync with source / single-source constants (no duplicated lists)

A P0 (a defect that fails the call or causes an accident) drops that axis to 0, a P1 costs points per item, and a P2 only shows up in the summary.

The three-part description

<one-line summary: what it does>

Use when the user asks to …  ← the basis for picking it (Korean trigger words alongside)
Do NOT use …                 ← the boundary against sibling tools
<one line on cost, time, limits>

Returns: <the exact shape of what comes back>

Publish tools put the HITL contract ahead of all that — the description opens with ⚠️ and says it posts publicly the moment it's called, so it may be called only right after the user has reviewed and approved the final copy and media, never without approval.

Single-source constants

List-shaped values (30 TTS voices, 13 keys, 3 generation modes) keep one constant in the client module as the source of truth, and the JSON Schema enum in tools.ts and the zod enum are derived from it. Copy a list into the schema and sooner or later a value gets added on one side only.

// tts-client.ts — source of truth
export const TTS_VOICES = { Zephyr: 'Bright', /* …30 of them… */ } as const;
export const TTS_VOICE_NAMES = Object.keys(TTS_VOICES) as [VoiceName, ...VoiceName[]];

// tools.ts — derived
enum: [...TTS_VOICE_NAMES]
// tts-client.ts — derived
const voiceSchema = z.enum(TTS_VOICE_NAMES);
