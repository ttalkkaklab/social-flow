1. There's no route to choose

Hybrid is the default — not by taste, but because Veo makes at most 8 seconds per call.

For a 30–60 second short, people assume there are three options: generate everything with a video model, lay narration over images like a slideshow, or mix the two. In practice there's nothing to choose.

Veo 3.1 makes 8 seconds at most per call. On top of that, Google's docs recommend putting "one moment per prompt" for short videos — cram several events into one prompt and the result often smears. The prescription in that same doc is to split generation into "Clip 1 / Clip 2 / Clip 3". Use it the way Google recommends and the output is a bundle of clips from the start: 4 of them for 30 seconds, 8 for 60.

Which means an editing layer that joins clips is needed either way. Once that layer exists, the only remaining decision is "which slots get generated video and which get stills". That's the hybrid.

A

Generated video only

Pull every clip from Veo. The 8-second ceiling means you end up joining clips anyway, so despite the name it isn't "only".

B

Images + TTS

Ken Burns over stills, plus narration, subtitles, and BGM. Widely shipped in practice, but we found no comparative evidence that it's better.

C · default

Hybrid

Pick generated video or a still per scene. The joining layer is needed on any route, so this option costs nothing extra.

added 2026-08-18 The engines that fill those slots have grown too. Still backgrounds default to on-device image_local_generate (Z-Image Turbo via mflux/MLX) — no API key, no network, no billing. Only frames carrying text go to gpt_image_text2img, because local generation breaks Korean jamo apart. Narration has the same shape: on-device by default (§5).

Confidence in this conclusion is low. derived inference The three facts under it (the 8-second ceiling, the one-moment rule, the split-into-clips prescription) each landed 3-0, but tying them into "hybrid is the default" is us, not the sources. And there's no comparative evidence for A over B or B over A — turning "where to use generated video" into a principle needs per-episode cost, and not one of those numbers passed verification in this round (§9).

Where Korean goes

The asymmetry in the docs is real. The Vertex model card lists English as the only prompt language for every Veo 3.1 variant, and the Gemini API docs say English is fully supported while other languages haven't been evaluated. The Gemini TTS docs, in the other direction, list Korean | ko explicitly in a table of 87 languages.

So write video prompts in English and keep Korean in the narration and subtitle layers. That's the only arrangement the docs support.

Overstate it and you're wrong. "Not evaluated" is not "doesn't work". Veo 3.x producing Korean speech is common in practice, so turning this into "Veo can't do Korean" makes it false. What the docs let you say stops at there's no vendor guarantee, and "generate TTS separately and mix it in" is an architecture decision of ours, not something Google said.
The docs disagree with each other in places. Vertex's "Generate videos from text" page lists 4K as "Preview models only", which collides with the GA model card (the model card wins), and the Sound generation: Not supported line on the veo-3.1-generate-001 card sits badly with other Google docs. Treating individual fields as spot-check material is the safe move. The 9:16 + 1080p combination is also worth generating once to confirm — the older Veo 3.0 had a constraint where 1080p was 16:9 only.

The axis that splits the cost isn't length, it's whether that segment uses its sound — motion backgrounds throw the sound away, so they go to Seedance silent; b-roll that uses the clip's own sound goes to Veo. 3. Prompt design — four official rules

These are the rules Google's docs state. The docs were last updated 2026-08-07, so they're current.

  1. 1 Break the prompt into slots. subject · action · scene/context · camera angle · camera movement · lens/optical · visual style (lighting · tone-mood · artistic style · ambiance) · temporal · audio. You don't have to fill them all — required, must, and mandatory appear nowhere in the whole document.
  2. 2 Don't use negation words in the negative prompt. Instead of "no cars", just describe what you don't want. Google's own example is urban background, man-made structures, dark, stormy, or threatening atmosphere — adjectives and "or". Narrowing this to "nouns only" gets it wrong.
  3. 3 Put dialogue in quotes and those letters get stamped on screen. To have the line only spoken, use the ~ says: colon form. This lever only applies to dialogue, though — it won't stop signage, posters, or UI text.
  4. 4 One moment per prompt. Bundle A→B→C into one call and the result often smears. The doc's phrasing is hedged as "often leads to", not stated flatly.
These rules are recommendations, not measured efficacy. The negative-prompt item reads "We recommend", not "must", and there's no A/B, no failure rate, no benchmark. The words storyboard and shot list never appear in the docs either — framing this as a storyboard pipeline is our reading, not Google's.

image-to-video is a different kind of prompt

This is the most frequently botched point. When making video from an image, write motion only. Don't re-describe the person, background, or lighting already visible in the source image.

Not recommended: Re-describe the character, the background, or the lighting depicted in the image. Redundant prompts confuse the model and lead to poor results.

Call the character by a generic name too — the subject, the woman, he/she — instead of a proper name. The source image is treated as the film's first frame, so its sharpness and composition set the floor for the result's quality.

The same document prescribes the exact opposite for text-to-video: give the character a name, build an unchanging appearance-description block, and paste it whole into every scene prompt. Two paths diverge inside one document, so merging prompt-generation logic into a single path guarantees one of them is wrong.

Watch the scope. The generic-name rule applies only to "a character inside the source image" — people the prompt newly introduces aren't covered. And the rule addresses the visual layer only (audio prompting is separate).

Make the TTS first, and its measured length sets the video's length.

added 2026-08-18 There are two engines making that narration too. Bodies go to on-device tts_local_generate (Supertonic 3 — no API key, no network) by default, and only cuts that need acting go to Gemini tts_generate, because the local side has no style or emotion controls. Measuring length got cheaper: tts_local_generate returns the audio duration in its response, so a scene-length check doesn't need a separate ffprobe call. The two engines differ in sample rate, though — local 44.1kHz, Gemini 24kHz — so mixing them in one video needs resampling.

Why subtitle timing is a re-transcription

Gemini TTS doesn't return word timestamps. So those pipelines transcribe their own generated speech (ASR) to get per-word start and end times. It's a detour, not a choice.

In Korean this path is risky. Re-transcription isn't aligning against the script, it's hearing it again, so it drifts from the script on numbers, loanwords, and proper nouns. And what gets stamped into burned-in subtitles is the misrecognition, not the script. Deepgram's docs also state that smart_format has its widest support in English. Korean accuracy is unverified.
This isn't comparative evidence. It's not "audio-first beats video-first", it's an existence proof that "this is how it actually ships". And both ShortGPT and MoneyPrinterTurbo use stock footage, so they've never hit the fragmentation Veo's 8-second ceiling creates — don't cite them as evidence that the same order carries over to a generated-video stack.

6. Should subtitles be burned into the video

Not burning them became this pipeline's rule. Platforms that take a subtitle file get one uploaded separately; only Instagram, which doesn't, gets its own burned-in copy. implemented

The problem with burned-in subtitles (baked into the video's pixels) is clear. You can't fix them after publishing. One typo brings a re-encode and a re-post. They can't be turned off, can't be translated, and don't show up in search. They also carry a standing risk of colliding with platform UI elements.

But whether an alternative exists differs per platform. That's the fork.

YouTube · Facebook — there's a subtitle-file path

  • YouTube: Data API captions.insert. Scope is youtube.force-ssl (or youtubepartner), quota 400 units
  • Facebook: Graph API POST /{video_id}/captions. SRT only, filename in name.locale.srt form, 200K limit
  • Subtitles can be fixed and re-uploaded after publishing — no video re-upload
  • Viewers can toggle them, and on YouTube they feed auto-translation

Instagram — burning them in is the only way

  • IG Content Publishing container parameters have no subtitle-file argument — caption is the text description
  • The app's automatic captions can't be controlled on an API-published post
  • Drop the burn-in and you just get a video with no subtitles
  • Threads doesn't apply — a video episode posts the body only and puts the video link in a self-reply. No cover image is attached either updated 2026-08-18
The API facts in this section were confirmed outside this round of research. checked separately · no 3-vote check They weren't among the 25 claims in the deep-research verification; the doc pages were opened directly (captions.insert · FB video captions · IG content publishing).

An earlier edition (morning of 2026-08-11) left FB as "Reels, so applicability unconfirmed" — that was us misreading our own implementation. facebook_publish uploads a regular video via POST /{page-id}/videos (not a Reel), so the caption edge applies as written. This is now confirmed against the code. That YouTube's docs don't mention Shorts stays unconfirmed.

So we make two copies of the video

Make one mp4 and post it everywhere and you can't take the subtitles back out. So the builder pulls two copies from the same source — a clean master and a burned-in one. The clean copy isn't re-encoded from the other; each comes from the source, so both are first-generation, and the builder verifies their lengths match.

SRT and ASS are stamped separately from the same origin. ASS is never converted back into SRT — the two formats differ in digit count and separator (h:mm:ss.cc vs hh:mm:ss,mmm), and a conversion leaves room for the burned-in copy and the subtitle file to disagree on timing. The builder writes both formats at the same spot where it makes each subtitle line.

The publish tools have subtitle arguments now. The earlier edition's "there's no subtitle-file argument anywhere in the publish tools" is resolved. youtube_publish takes captionFilePath+captionLanguage, and facebook_publish takes captionFilePath+captionLocale. Both validate the file before publishing (extension, size, existence), and if only the subtitle upload fails they downgrade it to a captionWarning — the video is already public, and re-publishing isn't idempotent, so it would create a duplicate post.

YouTube needs one more scope. captions.insert requires youtube.force-ssl, which the publishing scope youtube.upload doesn't include. Publish with an old upload-only token and the video goes up while the subtitles alone fail. The quotas differ too — 1 unit for the upload, 400 for the captions.

Neither side can be pushed with data. zero surviving evidence Not one claim about subtitle design passed verification in this round. "Subtitles raise retention" and "cut them at 15 characters" both died (§8). The judgment above is a feature comparison of what each platform accepts, not an answer about how subtitles affect performance.
Our subtitle placement is tuned from measurements. The band sits at y≈1380–1560, above the IG caption zone, with symmetric 250px side margins — at 168 a long single line crosses the action bar's start line (x≈890; measured 907px), and at 200 the clearance drops to 39–61px, the smallest of any on-screen element. Asymmetric margins push center-aligned subtitles 60px off the screen's center (measured).

What the zoompan trap was

We avoid it, but it's worth recording. The defaults of ffmpeg's zoompan filter are 1280×720 · 25fps · 90 frames per image. Leave out s= and fps= on a 9:16 source and the portrait video comes out landscape 720p without a single warning. And not as a center crop — the whole frame is squashed and stretched. A verifier confirmed it matched the output of scale=1280:720 at SSIM 1.000 (identical).

A summarizer hallucination was caught during the research. The WebFetch summarizer returned the same ffmpeg doc summarized wrongly as "d defaults to 1, s keeps the input size". Both the original text and the binary's -h filter=zoompan refuted it immediately. If a re-run meets the same summary, ignore it.
